브랜치 4계층 위계 구조 (§12-1)

정본: MASTER §12-1
main (배포 스냅샷) Release
• 누가: 김재웅 전담 (AWS / Pages 자동 배포)
• 머지 방식: Merge Commit (승인 1 + Code Owners 통과 필수)
• 수명: 영구
↑↓ Merge Commit
dev (통합 트렁크) Trunk
• 누가: 팀 전원 (항상 안정 동작 상태 유지)
• 머지 방식: Merge Commit (CI 검사 통과 필수, 승인 0)
• 수명: 영구
↑↓ Merge Commit
part/* (파트별 최신 통합) Staging
• 누가: gis(오창준, 우지혜) / cv(이가연, 백진욱) / infra(김재웅)
• 머지 방식: feat → part는 Squash / dev → part는 Merge Commit
• 수명: 영구 (직푸시 차단)
↑ Squash
feat/* (단기 작업 브랜치) Temporary
• 누가: 개별 작업자 (자유 생성)
• 머지 방식: Squash Merge 후 part/*에 흡수
• 수명: 당일 생성 · 당일 삭제 (< 1 Day)

1. 아침에 뭐 하나 — 원격 정렬 및 브랜치 분기 (§12-5)
아침 pull 조건 판단 (매일 의무 아님) 0 커밋이면 생략 가능 
git fetch -q && git rev-list --count part/gis..origin/dev   # 0 이면 안 해도 된다
상황 아침 pull 이유 및 작업 방향
origin/dev에 새 커밋이 있다 필요 통합 PR 담당자가 dev → part 동기화 후 최신 상태를 받아야 함
0 커밋 불필요 아무도 dev에 올리지 않았으므로 fetch 확인 후 바로 작업
어제 Draft를 이어간다 불필요 새 브랜치를 따지 않고 어제 작업하던 feat 브랜치로 바로 switch
새 작업을 시작한다 필요 남의 작업 위에서 시작해야 충돌이 최소화됨
★ 새 작업인데 건너뛰면 그날 밤 PR에서 충돌이 몰립니다. 아침 1분이 밤 30분을 아낍니다(§12-5).
새 작업 시작 시 브랜치 분기 (§12-5) 정본: MASTER §12-5 
git switch part/gis && git pull --ff-only   # 1. 원격 상태를 그대로 받는다
git switch -c feat/gis-오늘작업이름          # 2. 오늘 작업할 임시 브랜치 생성
왜 로컬 머지를 하지 않고 pull --ff-only인가? 모든 파트 브랜치는 직푸시가 차단되어 있습니다(§12-1). 로컬에서 dev를 merge하면 원격과 로컬이 어긋나 Behind 커밋이 쌓입니다. dev → part 흡수는 파트 통합 담당자가 올리는 PR로만 이루어집니다(§12-8c).
파트별 브랜치 GIS: part/gis | CV: part/cv | Infra: part/infra
2. 작업 끝났다 — PR 생성 및 커밋 접두사 규약 (§12-6)
작업 완료: 커밋 및 파트 브랜치로 PR 생성 정본: MASTER §12-6 
git add -A
git commit -m "gis: 세그먼트 폭 산출 파이프라인 보정"
git push -u origin feat/gis-오늘작업이름
# GitHub PR: base: part/gis  <--  compare: feat/gis-오늘작업이름
표준 커밋 접두사 (§12-6)
gis: 데이터·판정
cv: 비전·캘리브
ui: 화면·스타일
api: FastAPI·서버
fix: 버그 수정
docs: 문서 갱신
파트 통합 PR 담당 (§12-8c): part/* → dev PR은 충돌 방지를 위해 파트별 1인(GIS: 우지혜 / CV: 이가연 / Infra: 김재웅)만 올립니다.
정본: MASTER §12-8c
이어서 작업할 때 (Draft PR) 미완성 작업 머지 금지

미완성 작업은 part/*에 머지하지 않습니다. 팀원이 그 위에서 분기하므로 깨진 코드 위에서 시작하게 됩니다. Squash는 완성된 것에만 씁니다. 

# 오늘 못 끝냈다 — Draft 로 열어둔다
git push -u origin feat/gis-오늘작업이름
gh pr create --draft --base part/gis

# 다음날 이어가기 — 브랜치를 지우지 않았으므로 그대로 이어간다
git switch feat/gis-오늘작업이름

완성되면 GitHub에서 Draft를 해제(Ready for review)하고 Squash로 머지합니다.

rebase vs merge 선택 기준 상황별 동기화 방식
상황 무엇을 왜 그렇게 하는가
아직 push 안 한 feat git rebase origin/part/gis 내 로컬 브랜치라 이력을 깔끔하게 다시 써도 됨
이미 push한 feat (Draft PR) git merge origin/part/gis rebase 시 force push가 필요한데 룰셋이 막음
part/* · dev · main rebase 절대 금지 보호 브랜치임. 되돌리기는 오직 revert로만 수행
★ 이미 원격에 민 브랜치를 rebase하면 push가 거부되고, --force는 룰셋이 차단합니다. 밀기 전엔 rebase, 민 뒤엔 merge입니다.

6. 잘못 밀었다 — 비상 복구 및 롤백 (§12)
비상 복구 및 롤백 가이드 FORCE PUSH 금지
FORCE PUSH 절대 금지 (main / dev / part/*)

보호 브랜치에 강제 푸시를 시도하면 룰셋에 의해 차단됩니다. 원격에 푸시된 잘못된 커밋은 반드시 revert를 통해 역방향 커밋으로 취소해야 합니다.

1. 로컬 직전 커밋 수정 
git add .
git commit --amend -m "올바른 메시지"

푸시 전 로컬 커밋 메시지 및 누락 파일을 수정합니다.

2. 푸시된 커밋 취소 
git revert <커밋해시>
git push origin feat/내브랜치

원격에 푸시된 특정 커밋을 안전하게 취소합니다.

3. 잘못된 머지 취소 
git switch -c feat/gis-revert && git revert -m 1 <머지커밋해시>
git push -u origin feat/gis-revert   # PR 로 되돌린다

Merge Commit의 1번 부모를 기준으로 되돌립니다.

정규 릴리즈 4단계 절차 (§12-8b)

정본: MASTER §12-8b
3단계(main → dev 흡수)와 4단계(dev → part 정렬) 필수

뒤 둘을 빼먹으면 다음 릴리즈에서 조상 커밋 연결이 끊겨 대형 머지 충돌이 발생합니다. 

# 1단계: dev -> main PR (Merge Commit / 승인 1 + Code Owners 통과)
#      ★ 머지 완료를 확인한 뒤 2단계로 간다
git switch main && git pull --ff-only && git log --oneline -1

# 2단계: 태그 (그 머지 커밋이 보여야 붙인다)
git tag v<다음버전> && git push origin v<다음버전>

# 3단계: [필수] main -> dev 흡수 — 릴리즈 매니저
gh pr create --base dev --head main --fill && gh pr merge --merge

# 4단계: [필수] dev -> part — 각 파트 통합 담당이 자기 브랜치로
gh pr create --base part/<파트> --head dev --fill && gh pr merge --merge

머지 방식이 왜 다른가? (§12-2)

정본: MASTER §12-2
feat → part 는 왜 Squash인가?

feat은 당일 삭제되는 임시 브랜치이므로 커밋 이력을 남길 이유가 없습니다. 하나의 커밋으로 압축 병합합니다.

dev ↔ main 은 왜 Merge Commit인가?

양방향 부모 이력을 남겨야 다음 흡수 때 충돌이 안 나며, 롤백 시 revert -m 1이 정상 동작합니다.
