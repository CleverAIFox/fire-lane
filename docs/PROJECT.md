## 2. CCTV 데이터 확보 — ⚠ 확정: 실시간 API 직접 연동 불가

### 결론
동명동 골목 CCTV의 **실시간 스트림을 RESTful GET으로 직접 받는 것은 불가능**하다고 확정. 조사로 검증됨.

### 근거
1. 보유 중인 CCTV 좌표 CSV(`전남광주통합특별시_CCTV_20260630.csv`, 관리기관: 광주광역시 사회재난과)는 **"전국CCTV표준데이터"** 공공데이터포털 표준 규격 그 자체임 — 관리기관명/설치위치/설치목적/카메라대수/화소수 등 **메타데이터만** 제공. 영상 자체는 포함 안 됨.
2. 이 CCTV는 **방범·재난 목적**으로 설치된 것이라 개인정보보호법 제25조상 "범죄예방/시설안전/교통단속/교통정보수집 목적으로 정당한 권한을 가진 자"만 열람 가능. 권한 없이 영상을 보여주거나 시청하는 것 자체가 형사처벌 대상(대법원 판례 존재).
3. 국가교통정보센터(ITS, its.go.kr)가 실시간 CCTV 영상 API를 실제로 공개하고 있긴 하나(회원가입→인증키 발급), 이건 **고속도로·국도용**이라 동명동 같은 도심 골목은 커버 대상이 아님.

### 채택 방향 (합의 완료)
- **아키텍처**: RESTful CCTV 연동 인터페이스는 시스템에 정식으로 탑재. "소방청/지자체가 향후 권한을 부여하면 그대로 붙는" 구조로 설계 — 발표 포인트로 활용 (권한 문제를 인지하고 대응 설계했다는 스토리).
- **시연/개발**: 실제 실시간 스트림 대신, **사전 촬영한 프레임을 mock GET 서버(FastAPI)로 순서대로 반환**하는 방식으로 흉내. 실배포 시 이 mock 자리에 실제 CCTV API만 갈아끼우면 되는 구조.
- **[할 일]** mock 서버 코드 아직 미작성 — 다음 착수 항목.
- CCTV 좌표 CSV(동명동 52건 매칭)는 "골목 후보지 대비 카메라 물리적 존재 여부 시각화·pruning" 용도로만 활용 (실시간 스트림 목적 아님).

## 3. 캘리브레이션 방법론 — ⚠ 확정: 지적도(V-World) 방식 채택

### 결론
**줄자 실측 + 매번 4점 클릭 방식은 폐기. 국가 공식 측량 데이터(연속지적도)를 캘리브레이션 기준값으로 사용하는 방식으로 확정.** (팀원 이해도 낮음 → 아래 설득 논리 참고)

### 팀원 설득용 한 줄 논리
> `cv2.findHomography`는 픽셀좌표와 실제좌표를 대응시키는 함수다. "실제좌표"에 뭘 넣느냐만 바뀌는 거지 계산 원리는 완전히 동일하다. 줄자 실측은 카메라가 늘어나면 인건비가 선형으로 늘지만, 지적도는 국가가 이미 측량해둔 걸 API로 긁어오는 거라 카메라가 수백 대로 늘어도 사람이 할 일이 안 늘어난다. → 확장성이 핵심 차별점.

### 전체 흐름
```
① V-World 오픈API 인증키 발급 (무료, 즉시)
② 대상 골목 좌표(경위도)로 연속지적도 WFS 조회 → 도로 필지 폴리곤(경계좌표) 획득
③ 폴리곤 좌표를 카메라 픽셀좌표계와 대응시킬 기준점 선정 (건물모서리 등 사진·지적도 양쪽에 보이는 지점)
④ cv2.findHomography(픽셀좌표, 지적도좌표) → 카메라별 H행렬 산출·저장
⑤ 파일럿 사이트 최소 1곳은 줄자 실측과 대조해 정밀도 검증 (필수, 생략 금지)
⑥ 이후는 완전자동 (YOLO 자동탐지 → H 적용 → 등급판정)
```

①~④가 카메라 설치 시 1회 작업(기존 "캘리브레이션"과 동일 위치), ⑤는 파일럿 단계에서만 필요, ⑥부터 완전자동.

**클릭이라는 행위 자체가 완전히 사라지는 건 아님** — 뭘 클릭하느냐(줄자로 잰 임시 좌표 → 국가측량 기준 도로 경계선)가 바뀌는 것. 단안카메라의 스케일 모호성 문제는 물리법칙적 한계라 어떤 방식이든 1회성 대응은 필요.

### 데이터 소스
- V-World: https://www.vworld.kr → 오픈API → 인증키 발급 (✅ 발급 완료)
- 연속지적도 **데이터 API** 레이어 코드: **`LP_PA_CBND_BUBUN`** ✅ 확정 (V-World 공식 게시판으로 재검증 완료)
  - ~~`LT_C_LANDINFOBASEMAP`~~ ❌ 이건 WMS(이미지 타일, LX맵)용 코드였음 — 좌표 추출 목적엔 안 맞아서 폐기. 최초 문서 작성 시 WMS/Data API 코드를 혼동했던 것으로 확인됨.
  - 호출: `service=data&request=GetFeature&data=LP_PA_CBND_BUBUN&key={KEY}` (bbox 또는 attrFilter=pnu:=: 방식 둘 다 가능, bbox가 동명동 전역 조회엔 더 적합)
- 대안 경로(브이월드 막힐 시): 공공데이터포털 국토교통부_연속지적도 (data.go.kr/data/15056910/openapi.do)

### 좌표계 처리 (실수하기 쉬운 지점)
- 지적도 좌표는 보통 **EPSG:5186 (GRS80 중부원점)** 평면직각좌표계로 내려옴.
- 캘리브레이션엔 "미터 단위 상대좌표"면 충분하므로 **위경도(EPSG:4326) 변환 없이 EPSG:5186 그대로 사용하는 게 더 간단** (위경도는 각도 단위라 거리 계산에 바로 못 씀).
- 실제 API 응답의 EPSG 코드는 메타데이터에서 반드시 재확인 후 코드 교체.

### 알려진 한계 및 폴백
- 일부 지역은 일제강점기 측량 기반 원본 지적도가 갱신 안 돼 **좌표계 오차**가 있음 (국가 "지적재조사사업" 진행 중, 전국 미완료). **[할 일] 동명동이 이 케이스에 해당하는지 확인 필요.**
- 오차 1cm 이내면 지적도 방식 신뢰 가능. 오차가 크면 → 지적재조사 미완료 지역 가능성 → 해당 골목만 줄자 실측 폴백.
- **이중 구조로 설계**: "지적도 우선 시도 → 검증 실패 시 실측 폴백". camera_id별 `calibration_source`(지적도/실측) 필드 DB에 추가해 추적 관리.

### 구현 — cv2 핵심 API 3개
```python
# ① 대응점 → 호모그래피 (RANSAC이 잘못 찍은 점 하나 걸러줌)
H, mask = cv2.findHomography(src_px, dst_meter, cv2.RANSAC, 5.0)

# ② 점 변환 — 폭 계산에 실제 쓰이는 것 (이미지 전체 warp는 시각화용일 뿐, 계산엔 점만 변환)
pts_m = cv2.perspectiveTransform(pts_px.reshape(-1,1,2), H)

# ③ 렌즈 왜곡 보정 (체커보드 촬영했다면) — 순서 중요: 왜곡보정 → 대응점 → 호모그래피
undistorted = cv2.undistort(img, mtx, dist)
```

### 검증 방법론 (지적도 방식에도 그대로 적용됨)
- **재투영 오차**: `cv2.perspectiveTransform`으로 역산 후 실제값과의 유클리드 거리 평균/최대.
- **홀드아웃 검증(더 정직한 방법)**: 대응점 일부(예: 8/10)로만 H를 구하고 나머지로 검증. 모든 점을 다 써서 구한 H는 그 점들에 당연히 잘 맞으므로 재투영 오차만 보면 과대평가됨.
- 저장 포맷: 골목별 JSON에 `src_px`, `dst_m` 원본을 H와 함께 저장 — 점 하나 잘못 찍은 게 발견되면 그것만 빼고 재계산 가능.

## 4. 유효폭 계산 로직 — ⚠ 확정: 카메라 직접 측정 방식 (뺄셈 방식 아님)

### 결론
**"GIS 서류상 도로폭 − CCTV 감지 불법주차 차폭 = 유효폭"** 방식(뺄셈 방식)은 **채택 안 함**. 오차가 두 군데(GIS 서류값 자체의 부정확 + CCTV 차량폭 감지 오차)에서 이중으로 누적되기 때문. 대신 **호모그래피로 변환한 좌표계 위에서 차량 세그멘테이션 결과를 직접 측정**하는 방식 채택 (3장의 H행렬을 그대로 사용).

> 참고: `지도_API와_소방서_출동_정보.txt`의 "실제 소방 관제실은 GIS 포함 전문엔진 사용"이라는 문구는 **출처 미확인 전언**임 — 발표 자료에 그대로 인용 금지, 확인 필요 시 인터뷰로 검증.

### 계산 로직 (mvp_with_yolo.py 기준)
- YOLO11-seg (`yolo11n-seg.pt`, nano=속도 우선. 정확도 필요시 s/m로 교체)
- COCO 클래스 중 차량 취급: `{2: car, 3: motorcycle, 5: bus, 7: truck}` (오토바이는 통행폭 판정 대상 아니나 우선 포함, 필요시 제외 검토)
- **바닥 접지선 기준 계산**: 세그멘테이션 마스크 최하단(화면에서 가장 아래쪽) 픽셀 행의 좌/우 끝 좌표 사용 — 타이어가 지면에 닿는 지점에 가장 가깝다고 가정.
- **알려진 한계**: 사이드미러 등 바닥에서 뜬 부분은 이 방식으로 못 잡음 → 오차 발생. 이 오차는 아래 등급판정의 "판정보류" 버퍼가 흡수하도록 설계됨.
- 단일 카메라 + 평면(도로 바닥) 가정 → 굽은 도로는 하나의 평면 캘리브레이션으로 못 다룸. 직선 구간 위주 파일럿 권장 (단, 지적도 방식은 폴리곤 전체 구간 활용 가능해 완화됨).

### 등급판정 기준 — ✅ 6색 체계로 확정 (기존 4단계 문자열 판정에서 변경)
```
BLUE   : 주 도로, 계산 자체 불필요 (FIXED_PASS, ROAD_BT ≥ 12m)
GREEN  : 실시간 판정 결과 — 지금 여유 있음 (CANDIDATE+COVERED, YOLO 연동 후 등장)
YELLOW : 실시간 판정 결과 — 애매/판정대기 (CANDIDATE+COVERED, YOLO 미연동 시 잠정 기본값)
ORANGE : 실시간 판정 결과 — 지금 막힘 (CANDIDATE+COVERED, YOLO 연동 후 등장)
RED    : 절대 진입불가, 계산 불필요 (FIXED_BLOCK, ROAD_BT < 2m)
GRAY   : 사각지대 — CANDIDATE인데 CCTV 없어서 자동판정 불가
```
- RED(구조적 절대불가, 고정)와 ORANGE(지금 이 순간 막힘, 실시간 계산)를 분리한 이유: "원래 좁아서 못 가는 도로"와 "지금 순간적으로 주차 때문에 막힌 도로"를 같은 색으로 섞으면 발표에서 혼동됨.
- **현재 YOLO 미연동 상태라 GREEN·ORANGE는 아직 등장하지 않음(둘 다 0건)** — CANDIDATE+COVERED는 전부 잠정 YELLOW로 표기 중. 이건 버그 아니라 설계된 잠정 동작.

### 도로 3단 필터링(pruning) — ✅ 확정, 임계값 최종 조정 완료
호모그래피·CCTV 판정 대상을 줄이기 위해, 서류상 도로폭(`ROAD_BT`) 하나로 전수 도로를 1차 분류:

| Tier | 조건(ROAD_BT) | 처리 |
|---|---|---|
| `FIXED_PASS` | ≥ **12.0m** | 왕복 4차선급(차로폭 3~3.5m×4차로 추정치) → 호모그래피 불필요, 상시 BLUE 고정 |
| `FIXED_BLOCK` | < 2.0m | 물리적으로 소방차 진입 불가 → 계산 불필요, 상시 RED 고정, 경로탐색에서 처음부터 배제 |
| `CANDIDATE` | 2.0m ~ 12.0m | 등급판정 경계와 겹치는 구간 → **여기만** 카메라·호모그래피·CCTV 판정 대상 |

⚠ **임계값 변경 이력(문서화 목적)**: 최초 4.0m(1차선 수준이라 근거 부족) → 8.0m(여전히 보수적 재검토 필요) → **12.0m로 최종 확정**. 판단 근거는 "비용(계산량) 최소화가 아니라 안전(소방차 통행 불가 누락 방지) 최우선" 원칙 — 임계값을 낮게 잡을수록 CANDIDATE가 줄어 계산은 편해지지만, 실제로는 애매한 도로를 "안전"으로 잘못 분류할 위험이 커짐. **공식 규정 인용 아니고 팀 자체 추정치**임을 발표 시 명시할 것.

동명동 실제 데이터 기준(2026-08-05): 전체 222개 구간 중 **FIXED_PASS(BLUE) 9개 / FIXED_BLOCK(RED) 20개 / CANDIDATE 193개** — 대부분(87%)이 자동판정이 필요한 애매구간이라는 뜻, 임계값을 현실화할수록 이 비중이 커짐(4m 기준일 땐 BLUE가 86개였음 → 검증 없이 안전하다고 잘못 판정했었다는 반증).

`CANDIDATE`는 다시 CCTV 커버리지로 2차 분류. **1차 기준: 주소 텍스트 매칭**(CCTV의 `소재지도로명주소`에서 도로명 추출 후 `road_segment`와 직접 문자열 비교, 좌표 오차 영향 없음) → 매칭 안 되면 **2차 폴백: 좌표 버퍼 25m**(카메라 유효 인식거리 추정치, 기존 40m에서 하향 조정 — 거리가 멀수록 호모그래피 원근왜곡 오차가 커진다는 판단):
- `COVERED`(카메라 있음) → YOLO 판정 대상
- `BLIND`(카메라 없음) → 자동판정 불가, GRAY 고정 (사각지대)

동명동 기준(2026-08-05): CANDIDATE 193개 중 **COVERED 136개 / BLIND 57개**(주소매칭 우선 적용 후, 좌표버퍼 단독 대비 오탐 크게 감소 — 검증: 주소 파싱 성공 CCTV는 전부 정확 매칭, 결측치만 좌표 폴백으로 정상 처리 확인됨).

이 필터링이 "확장성"(전국 확장 시에도 수작업 없이 자동 적용됨)의 실질적 근거임.

### 경계 클리핑(trim) 방식 — ✅ 확정
juso.go.kr 도로구간을 동명동 경계로 자를 때, **순수 clip(경계선 정확히 절단)도 순수 intersects(경계에 걸치면 통째로 포함)도 아닌 절충안** 채택: 경계를 **10m만 버퍼링**한 뒤 그 확장된 경계로 클리핑. 순수 clip은 도로 중간이 뚝 끊겨 시각적으로 부자연스럽고, 80m 등 큰 버퍼는 간선도로가 인접 동까지 수백 m씩 끌려와 지저분해짐 — 여러 버퍼값(80m→10m) 실측 비교 후 10m로 확정.

### CCTV 좌표 정밀도 이슈 — ✅ 확인·개선 완료
공공데이터 CCTV 좌표를 실제 거리뷰와 대조한 결과 도로 중심선과 8~14m 오차 확인(카메라가 도로 중심선이 아닌 인도 폴대 설치+주소 기반 지오코딩 특성상 발생하는 정상 범위 오차, 25m 커버리지 반경 내). 판정 신뢰성 강화를 위해 좌표 버퍼 단독 판정을 폐기하고 주소 텍스트 매칭을 1차 기준으로 승격(위 문단 참고).

## 5. 경로탐색

| 구분 | 지도 API (TMAP/Kakao) | 공공 GIS (QGIS/V-World) |
|---|---|---|
| 역할 | 실시간 길안내, 화면 시각화 | 골목길 폭 데이터 분석, 위험도로 DB |
| 도구 | TMAP API(1순위, 대형차 연산) / KakaoMap API(2순위, UI) | QGIS(SHP 가공) / V-World·공공데이터포털 |
| 알고리즘 | 경로: A* / 다익스트라, 주소: R-Tree(Geocoding) | 공간 속성 분석(ROAD_BT=서류상 도로폭) |

- **경로탐색 알고리즘은 TMAP/Kakao에 위임하지 않고 자체 구현으로 확정.** 이유: TMAP/Kakao 경로탐색은 우리가 계산한 판정등급(진입불가/판정보류)을 반영 못 함(TMAP이 우리 CCTV 판정 결과를 모르니까). 대신 **networkx**로 자체 그래프(노드=교차점, 엣지=도로구간, 가중치=도로길이+판정등급 페널티)를 만들어 다익스트라/A*를 직접 호출. TMAP/Kakao는 **그 결과를 지도 위에 그려주는 시각화·SDK 용도로만** 사용 (Kakao Maps JS SDK, 프론트에서).
- GIS 서류상 도로폭(ROAD_BT)은 **4장 등급판정의 1차 입력값 그 자체**임(3단 필터링). `ROAD_BT`는 juso.go.kr `도로구간(TL_SPRD_MANAGE)` 테이블의 실제 속성 컬럼이며 이게 유일한 폭 소스임 (아래 8장 참고).

### 교통체증(Tmap/Kakao) 반영 방식 — ✅ 확정: 병합이 아니라 병렬 비교
팀 합의사항(교통체증 우회 + 불법주정차 우회 둘 다 반영)을 구현하는 방법: **Tmap의 혼잡도 모델을 우리 다익스트라에 억지로 합치지 않음.** 이유: Tmap API는 임의의 도로 링크 하나하나에 대한 혼잡도를 낱개 조회하는 구조가 아니라 "출발-도착지 하나에 대한 완성된 경로"를 반환하는 구조라, 우리 그래프의 모든 간선에 혼잡도 가중치를 채워 넣는 방식 자체가 API 구조상 깔끔하게 안 됨. 대신:

```
1. 같은 출발-도착지에 대해 Tmap API를 블랙박스로 호출 → "Tmap 추천 경로"(교통체증만 고려)
2. 우리 자체 다익스트라 호출 → "우리 추천 경로"(불법주정차 실시간 판정 반영)
3. 두 결과를 나란히 비교해서 제시
```

이 구조가 발표 포지셔닝과도 맞음: 교통체증 최적화는 Tmap이 이미 세계 최고 수준이라 우리가 재구현할 필요 없고, **우리 차별점은 "Tmap이 모르는 걸 우리는 안다"(실시간 불법주정차 감지)**라는 지점 하나에 집중.

### 그래프 설계 — 체크포인트 기반 (강사 피드백 반영)
- **노드 = 체크포인트**(교차점 등 주요 지점에 좌표 지정), **간선 = 도로 구간**, **가중치 = 팀이 정의**(거리 + 판정등급 페널티)
- DB에 `checkpoint` 테이블 별도 분리 예정: `checkpoint(id, geometry, road_segment_id FK)` — 시나리오 중 "갑자기 없던 주정차가 생김/사라짐" 같은 동적 이벤트를 체크포인트 단위로 시뮬레이션하기 위한 앵커
- **[할 일]** 현재 GIS 파이프라인은 동명동 경계(+10m)만 클리핑 대상 — 소방서(광주동부소방서)에서 동명동까지의 진입 경로도 그래프에 포함되도록 클리핑 범위 확장 필요(전체 juso 원본은 이미 보유, 클리핑 경계만 넓히면 됨). 아직 미착수.
- **소방서 위치는 별도 데이터셋 불필요** — 단일 지점이라 좌표 하드코딩으로 충분. 광주동부소방서: 전남광주 동구 제봉로 210, (126.922737, 35.136010)

- 국가 기관 시스템 소스·API 접근 권한을 획득할 가능성이 낮음
- 팀 역량 대비 기존 완성 체계 개조는 과도한 스코프
- **대신 완전히 독립된 웹 대시보드로 설계** — 119상황실 근무자가 기존 업무 화면과 별도로 참고하는 보조 도구로 포지셔닝. "알림이 상황실 단계에 전달되는 게 적절하다"는 인터뷰 결과는 **최종 사용자가 상황실 근무자(독립 대시보드 접속)라는 확인**으로만 반영, 기존 시스템 통합 의미 아님

## 7. 개발환경 / CI·CD — 저장소 초기 세팅 완료, CI 파이프라인은 미착수

### 결론
개발환경은 별개 트랙이 아니라 **팀 전체 통일 대상**. **저장소(fire-lane) 뼈대 세팅 완료, 첫 커밋 완료.** 아래 스택은 **오창준 개인 초안이며, 팀 전체 합의로 확정된 것은 아님** — 다만 Docker/devcontainer 구조상 팀 논의로 스택이 바뀌어도 `pyproject.toml`/`Dockerfile` 한 곳만 수정하면 전원에게 전파되므로, 지금 단계에서 팀 합의를 기다리지 않고 우선 진행해도 큰 손실은 없음.

### 구조
- **Dockerfile**: 실행환경 전체를 이미지로 포장. GDAL 등 geopandas 구동 시스템 라이브러리 포함.
- **`.devcontainer/devcontainer.json`**: VS Code "Reopen in Container" 한 번으로 팀원 전원 동일 환경.
- **호스트 전제조건**: Docker Desktop + WSL2는 각자 손으로 설치.
- **GPU 역할 분리**: 로컬은 CPU 전용, YOLO 파인튜닝은 Google Colab.

### 패키지 (`pyproject.toml`, 오창준 초안 — 팀 확정 필요)
```
fastapi, uvicorn[standard], opencv-python, numpy, python-multipart, ultralytics,
geopandas, shapely, pyproj, networkx, sqlalchemy, psycopg2-binary, geoalchemy2, requests
(dev: ruff, pre-commit, pytest)
```

### GitHub 워크플로우 — ✅ 확정
- 조직 생성 완료, 레포명 **`fire-lane`**
- 팀원별 개인 브랜치에서 작업 → `main` 직접 push 금지, **PR로만 병합**

- **[할 일]** `main ← 개인브랜치` PR 생성·팀 리뷰·병합

### CI 파이프라인 — ❌ 아직 미착수 (정정)
`.github/workflows/` 폴더 및 pytest+ruff 자동실행 워크플로 파일은 **아직 만들지 않음.** 실제로는 Dockerfile/devcontainer(로컬 개발환경 통일)만 완료된 상태고, GitHub Actions 자동화는 별도 착수 필요 (12장 할 일 반영).

- **[할 일]** 버킷 실제 생성·sync 아직 안 함

### AWS 계정/IAM 정책 — ⚠ 팀장 협의 필요

  - AWS Budgets 예산 알림 권장
- **[할 일]** 팀장과 최종 협의

### CI/CD 파이프라인 설계(목표, 아직 미구현)
학교 정식 커리큘럼(ch02-1~ch04-1)은 ECR·ECS·ALB·OIDC 풀스택을 가르치지만, **Fire-Lane는 4개월·5인 규모를 고려해 EC2 단일 인스턴스 + Docker Compose + SSH 배포로 의도적으로 스코프 축소**. CI(pytest+ruff)는 커리큘럼과 동일하게 유지.

| 단계 | 내용 |
|---|---|
| CI | push/PR마다 pytest(기능테스트) + ruff(린트) 자동 실행 |
| Docker | 코드+실행환경을 이미지로 포장, 커밋 해시로 버전 태깅 |
| 배포(Fire-Lane 채택) | EC2 한 대 + Docker Compose + SSH 배포 (ECR/ECS/ALB/OIDC 풀스택은 미채택, 학습 가치는 있으나 이번 프로젝트엔 과함) |
| ML 승인게이트 | 모델 검증(정확도 임계값) + GitHub Environment 승인 기능으로 사람이 최종 승인 버튼. Fire-Lane의 "판정보류(등급 경계 ±0.3m)면 사람이 확인" 철학과 동일한 논리 |
| MLflow | Tracking(실행 기록) + Model Registry(`challenger`→`champion` 승격 관리) |
| 운영관찰 | CloudWatch로 정상/에러 요청 및 추론 결과 로그 확인. 실습 종료 시 AWS 리소스 정리(삭제) 습관 포함 |

- **Frontend**: React(Vite) — 지도 엔진은 **⏳ 팀 결정 대기 중(Mapbox vs Naver Maps, 내일 확정 예정)**. Kakao Maps JS SDK 1차안은 재검토됨(아래 지도 엔진 비교 참고). Flutter는 실사용자가 소방관 개인 폰이 아니라 **119상황실/관제센터 데스크 근무자**(6장 인터뷰로 검증 예정)라는 판단하에 기각됨. 네이티브 앱 특유의 이점(백그라운드 GPS, 오프라인 대응 등)이 이 서비스엔 불필요.

### 지도 엔진 — Mapbox vs Naver Maps, 프로토타입 둘 다 완성 (⏳ 팀 결정 대기)

| | Mapbox GL JS | Naver Maps JS SDK v3 |
|---|---|---|
| 커스텀 스타일 도구 | Mapbox Studio(코드 없이 시각 편집, 성숙) | Map Style Editor(최근 추가, 상대적으로 이력 짧음) |
| 3D 건물 | ✅ 내장 벡터타일로 즉시 지원(추가 데이터 불필요) | 네이티브(Android/iOS) SDK는 지원 확인됨, **웹 JS SDK 3D 지원은 문서상 미확인** |
| 한국 로컬 데이터(건물명/POI) | 상대적으로 옅음(OSM 기반) | ✅ 확연히 풍부함(직접 확인됨) |
| 과금 | 무료 티어 월 5만 회 map load, 카드 등록 선택 | 무료 티어 월 **600만 회**, **카드 등록 필수**(NCP 정책), 가입 시 크레딧 10만원 지급 |
| 발표 포지셔닝 | — | "국가기관 서비스가 실제로 쓰는 엔진을 모사"라는 서사 가능 |

**결정: 아직 미확정.** 3D가 발표 핵심 요소가 아니라는 판단(실제 시연은 답사 영상+대시보드 조합으로 대체, 5번 참고)이 서면서 Mapbox의 3D 이점이 상대적으로 약해졌고, 팀은 로컬 데이터 풍부함을 이유로 Naver 쪽으로 기우는 중. **두 버전 다 실제 동작 확인 완료**(`dongmyeong_map.html`=Mapbox, `dongmyeong_map_naver.html`=Naver), 팀 결정 나오는 대로 한쪽으로 통합.

⚠ **Naver 통합 시 겪은 이슈 기록(재발 방지용)**:
- `naver.maps.Data.addGeoJson()`이 CRS 메타데이터 등으로 인해 에러 없이 조용히 실패하는 문제 확인 → 해결: GeoJSON 자동파서 대신 `naver.maps.Polyline`을 feature별로 직접 생성하는 방식으로 전환
- 지도 컨테이너가 `position:absolute; top/bottom` CSS로는 높이 0으로 렌더링되는 문제 확인 → 해결: JS로 `window.innerHeight` 기준 실측 픽셀값을 강제 주입
- Client Secret은 클라이언트 코드에 절대 포함 금지(서버사이드 전용), Client ID만 사용
- Web 서비스 URL 등록이 Mapbox와 달리 **필수**(등록 안 하면 지도 자체가 안 뜸)

- **Backend**: FastAPI
- **DB**: **PostgreSQL + PostGIS** — ✅ 확정. ~~Oracle~~(유료, 팀 논의 중 일시 언급됐다 정정됨), ~~MongoDB~~(CCTV 실시간 스트림 시나리오가 사라지면서 존재 이유 소멸, 폐기) 모두 미채택. PostGIS는 지적도 폴리곤 좌표를 geometry 타입으로 네이티브 저장·공간쿼리 가능해 GIS 파이프라인과 직결.

## 9. GIS 마스터 데이터 아키텍처 — ✅ MVP 완성

### 스키마 3계층 원칙
| 스키마 | 역할 |
|---|---|
| `raw` | 원본 그대로 적재(가공 없음), 나중에 원본 대조용 |
| `core` | 우리가 계산한 마스터 — `road_segment` 테이블. **진짜 "마스터 데이터"** |
| `serving` | API가 실제로 읽는 뷰/materialized view, GeoJSON 친화적 형태 |

원본 데이터가 매달 갱신될 때 `raw`만 갈아끼우고 ETL 재실행하면 되며, 손으로 보정한 캘리브레이션 결과 등이 함께 삭제되는 사고를 방지하기 위한 분리.

### `road_segment`(core) 핵심 컬럼
```
segment_id       -- 자체 PK (juso.go.kr ID 없는 구간은 우리가 시리얼 부여)
rds_man_no       -- juso.go.kr 원본 ID(있으면)
geometry         -- LineString
road_bt          -- 도로폭 (juso.go.kr 도로구간 ROAD_BT)
tier             -- FIXED_PASS / FIXED_BLOCK / CANDIDATE (4장 3단 필터링)
cctv_coverage    -- COVERED / BLIND (CANDIDATE에만 의미 있음)
nearest_cctv_id  -- FK, nullable
current_status   -- GREEN/YELLOW/RED/GRAY, 계산 컬럼
source_updated_at
-- ⚠ 백로그: nearest_hydrant_id, hydrant_distance_m (12장 소화전 항목 참고, 지금은 스키마에 미포함)
```

### 정적 계층 vs 동적 계층
- **정적 계층**(월 1회 갱신): `road_segment`의 도형·`road_bt`·`tier` — juso.go.kr 갱신 주기 따라감
- **동적 계층**(수 초~수 분 주기): `current_status` 컬럼만 — 브라우저가 API를 주기적으로 폴링(GET 반복)해서 최신 판정값을 받아 지도 색을 다시 칠함. **"동적"은 DB 엔진 성질이 아니라 클라이언트 폴링 루프 + 자주 바뀌는 얇은 상태 컬럼에서 나옴**
- 무거운 GIS 재계산(공간조인 등)은 정적 계층에서만, 실시간처럼 보이는 부분은 가벼운 상태값 업데이트로 분리 → 성능 부담 최소화

### 서빙 원칙 (반복 확인된 원칙)
FE(앱/대시보드)든 내부 시각화(QGIS/모니터링)든 **`serving` 스키마 하나만 보고 GeoJSON을 받는 구조로 통일**. 판정 로직을 프론트에서 재계산하게 하면 안 됨 — 로직은 백엔드에 하나만, 소비자는 여러 개여도 무방.

### CCTV 좌표 정밀도 이슈 및 해결 — ✅ 중요 결정사항

**문제 발견**: 공공데이터포털 CCTV 좌표(위경도)를 실제 거리뷰와 대조한 결과, 도로 중심선과 8~14m 오차 확인. 원인 분석:
- CCTV는 도로 중심선이 아니라 인도 옆 폴대에 설치됨 — 위치 자체가 다른 대상(juso.go.kr 도로구간은 중심선 데이터)
- 공공 CCTV 좌표는 GPS 실측이 아니라 주소 기반 지오코딩인 경우가 많아 태생적 오차 존재
- **다만 이 오차(8~14m)는 CCTV 커버리지 판정 반경(40m) 이내라 판정 로직 자체엔 영향 없음을 실측으로 확인함**

**개선 조치**: 좌표 버퍼 거리만으로 판정하지 않고, **CCTV의 `소재지도로명주소` 텍스트에서 도로명을 추출해 `road_segment`와 직접 문자열 매칭**하는 방식을 1차 기준으로 채택(공식 행정 주소 기준이라 좌표 오차의 영향을 받지 않음). 주소 결측 등으로 매칭 안 되는 경우만 좌표 버퍼(40m)로 폴백.
- 효과: CANDIDATE 98개 중 BLIND(사각지대) 53개 → **17개로 개선**(COVERED 45개 → 81개)
- 검증: 동명동 CCTV 53건 중 주소 파싱 성공 42건(정확 매칭), 결측 11건은 좌표 버퍼로 정상 폴백 확인

- **서빙 API**: `src/api/main.py` (FastAPI) — `/segments`, `/segments/{status}`, `/cctv`, `/boundary` 엔드포인트. **PostGIS 실쿼리로 전환 완료**(`src/etl/load_to_postgis.py`로 적재, `docker-compose.yml`로 로컬 PostGIS 기동). ⚠ 개발 샌드박스에 Docker가 없어 실제 기동 테스트는 못 함 — 로컬 환경에서 검증 필요.
- **시각화**: 지도 엔진 2종 프로토타입 완성, 8장 "지도 엔진" 참고. `outputs/dongmyeong_map.html`(Mapbox, 3D 건물 포함) / `outputs/dongmyeong_map_naver.html`(Naver Maps). 둘 다 소방서·CCTV·소화전 마커 포함, 클릭 시 도로 상세정보 팝업 확인 완료.

**juso.go.kr 신청서 작성 시 반복된 실수 기록(팀 공유용)**:
- 사이트 상단 탭 "공개하는 주소(속성)"과 "제공하는 주소(도형,좌표)"를 혼동해 텍스트DB(지번-도로명 매칭)를 여러 번 잘못 받음
- 신청 항목별로 승인이 개별 진행됨 — 승인키 발급 ≠ 전체 데이터 승인. "도로명주소 연계"(속성)와 "도로명이 부여된 도로 도형"(도형)은 별도 심사
- 승인 후 "변동자료 연계서비스"(ADSClient, 매일 자동갱신용 API)와 "전체자료 1회 다운로드"(우리가 실제 쓴 방식)는 다른 절차 — 상시 자동갱신이 필요없는 프로젝트는 후자로 충분
- 원본 SHP에 `.prj`(좌표계 정의) 파일이 누락되어 있었음 — 좌표값 범위로 역산해 EPSG:5179(UTM-K 전국 통합좌표계) 확인 후 처리
