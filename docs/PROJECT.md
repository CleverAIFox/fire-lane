# 0. 문서 규칙

## 0-1. 상태 표기

모든 수치와 결정에 **출처와 검증 상태**를 붙인다. 이게 이 문서의 유일한 규칙이다.

| 표기 | 뜻 |
|---|---|
| ✅ **검증** | 코드로 재현했고 산출 과정이 남아 있다 |
| 📄 **문서** | 결정은 됐으나 아직 코드/실측으로 확인 안 됨 |
| ⚠ **무효** | 근거를 추적할 수 없다. **인용 금지.** 재산출 대상 |
| ⏳ **대기** | 외부 승인·배송·인터뷰 등 우리가 못 당기는 것 |
| ⬛ **범위 밖** | 의도적으로 안 한다 |

## 0-2. 숫자를 문서에 박기 전 확인

```
1. 이 숫자를 만든 코드가 레포에 있는가
2. 그 코드를 지금 다시 돌리면 같은 값이 나오는가
3. 입력 원본이 sources.yaml에 등록되어 있는가
```

**셋 중 하나라도 아니면 ⚠로 표기하고 본문에 쓰지 마라.**

# 2. 아키텍처 · 모듈 경계

## 2-1. GIS ↔ 비전 — 접점은 정확히 두 개 📄

```
GIS ──[관측점 선정]──▶ 비전      어느 골목의 어느 지점을 찍을지 GIS가 정한다
GIS ◀──[판정 결과]──── 비전      seg_id + 통행폭 + 시각
```

계약 스키마:

```json
{
  "seg_id": "seg_2157",
  "passable_width_m": 2.8,
  "observed_at": "2026-08-09T14:03:00+09:00",
  "confidence": 0.82
}
```

**반대 방향이 없다는 것이 핵심이다.** GIS 도로폭은 호모그래피 입력으로 들어가지 않는다.
이 오해가 지적도 캘리브레이션 3주를 태웠다(§6-1).

## 2-2. 정적 계층 vs 동적 계층 📄

| 계층 | 갱신 주기 | 내용 |
|---|---|---|
| 정적 | 월 1회 | 도형, `width_min_m`, `tier`, `cctv_coverage` |
| 동적 | 수 초~분 | `current_status` 컬럼 **하나만** |

"동적"은 DB 엔진 성질이 아니라 **클라이언트 폴링 루프 + 얇은 상태 컬럼**에서 나온다.
무거운 공간조인은 정적 계층에서만 돌린다.

## 2-3. 서빙 원칙 📄

FE든 QGIS든 **`serving` 스키마 하나만 보고 GeoJSON을 받는다.**
판정 로직을 프론트에서 재계산하게 하면 안 된다. 로직은 백엔드에 하나, 소비자는 여럿.

# 4. 도로폭 — 판정의 입력값

## 4-1. `ROAD_BT` 사용 금지 ✅

도로명주소 `ROAD_BT`는 **명목 관리 폭**이지 실측값이 아니다.

```
정수 비율 90%
값의 30%(547/1,812)가 정확히 2.0에 몰림
```

같은 구간을 세 방법으로 재면:

| 소스 | `ROAD_BT`=2.0 구간의 실제 폭 |
|---|---|
| `ROAD_BT` | 2.00 |
| 실폭도로 `TL_SPRD_RW` 트랜섹트 | 1.76 |
| 수치지도 `NF_A_A01000` 트랜섹트 | 3.86 |

**`ROAD_BT`는 실제보다 크게 나오는 방향이다.** §4-4의 오류 비대칭에서 **미탐(막혔는데 통과 판정)** 쪽으로 편향된다. 가장 위험한 방향이다.

> `road_bt` 컬럼은 대조용으로만 남긴다. 컬럼명이 그럴듯해서 반드시 누군가 다시 쓴다.

## 4-2. 폭 산출 방식 📄

| 역할 | 소스 |
|---|---|
| **주 소스** | 수치지도 도로경계면 `NF_A_A01000` (1:5,000) |
| **폴백** | 실폭도로 `TL_SPRD_RW` |

두 소스는 경쟁이 아니라 **상보 관계**다. 수치지도는 넓은 길을 정확히 그리지만
**보행자 통로급 최협소 골목을 도로면으로 아예 그리지 않는다.**
표본 100개 중 수치지도 커버 **70개**(✅ 검증). 나머지를 실폭도로가 메운다.

### 산출 컬럼

```
width_m      = 중심선 샘플의 중앙값     (표시용)
width_min_m  = 같은 샘플의 하위 5%      (판정용) ★
width_src    = ngii | silpok
```

**최댓값이 아니라 하위 분위수를 쓴다.** 소방차는 가장 좁은 병목을 통과하지 못한다.

### ⚠ 교차로 blob 문제 — 미해결

```
천변좌로434번길   ROAD_BT 2.0 → 수치지도 트랜섹트 60.00m
필문대로          ROAD_BT 4.0 → 수치지도 트랜섹트 56.01m
```

중심선이 교차로 폴리곤 위를 지나며 폭이 폭발한다.

**해법은 최솟값을 쓰는 것이 아니라 교차로를 제외하는 것이다.**
노드(교차점) 반경 5m 안의 샘플을 버린 뒤 분위수를 잡아야 한다.
현재 `width_min_m` 정의에 이 조건이 빠져 있다. **구현 시 반드시 포함할 것.**

### ⚠ 계산 방식 검증 규칙

폭 계산은 **반드시 두 가지 방법(법선 트랜섹트 / 거리변환)으로 하고 불일치 구간을 먼저 본다.**
단일 방법 사용 시 인접 폴리곤 경계에서 교차선이 분할돼 **210개 구간의 폭이 절반 이하로 계산된 사고**가 있었고, 현장 답사에서야 발견됐다.

## 4-3. 등급 판정 — 6색 체계 📄

| 색 | 의미 | 확정 시점 |
|---|---|---|
| **BLUE** | 판정 불필요, 무조건 통과 (`FIXED_PASS`) | 정적 |
| **RED** | 구조적 진입 불가 (`FIXED_BLOCK`) | 정적 |
| **YELLOW** | 판정 대기 (`CANDIDATE` + CCTV 있음) | 정적 |
| **GRAY** | 사각지대 (`CANDIDATE` + CCTV 없음) | 정적 |
| **GREEN** | 비전 판정 = 통과 가능 | 실시간 |
| **ORANGE** | 비전 판정 = 불가 | 실시간 |

- RED(원래 좁아서 못 감)와 ORANGE(지금 주차 때문에 막힘)를 분리한 것이 핵심이다. 섞으면 발표에서 혼동된다.
- **7번째 색을 만들지 마라.** 애매한 경우는 `confidence`를 붙이고 §4-4에 따라 ORANGE로 떨어뜨린다.
- 현재 YOLO 미연동이라 GREEN·ORANGE는 0건이고 `CANDIDATE+COVERED`는 전부 잠정 YELLOW다. 설계된 동작이다.

### 3단 필터링

| Tier | 조건 (`width_min_m`) | 처리 |
|---|---|---|
| `FIXED_PASS` | ≥ 12.0m | 상시 BLUE. 호모그래피 불필요 |
| `FIXED_BLOCK` | < 2.0m | 상시 RED. 경로탐색에서 배제 |
| `CANDIDATE` | 2.0 ~ 12.0m | **여기만** 비전 판정 대상 |

**임계값 근거**
- **2.0m** — 소방청 진입불가 기준과 일치. 방어 가능
- **12.0m** — 팀 자체 추정치(4.0 → 8.0 → 12.0). **발표에서 자체 추정임을 명시할 것**

> **정밀도 경쟁을 하지 마라.** 폭의 용도 셋(1차 pruning / GRAY 판정 / 경로 가중치) 모두 ±0.5m면 충분하다.
> 방어해야 할 건 정밀도가 아니라 **임계값**이다. 경계 근처(1.8~2.2m) 구간이 몇 개고 그게 뒤집히면 결론이 바뀌는지 보이는 **민감도 분석**이 훨씬 가치 있다.

### ⚠ 판정 분포 — 전면 재산출 필요

이전 문서의 `BLUE 7 / RED 55 / YELLOW 98 / GRAY 62`는 **재현 불가**다.
행정구역경계 확보 → 노딩 → 폭 재산출 후 새로 뽑는다. **그때까지 이 숫자를 어디에도 쓰지 마라.**

## 4-4. 판정 오류의 비대칭 ★ 📄

| 오류 | 결과 | 비용 |
|---|---|---|
| **미탐** (막혔는데 통과 가능 판정) | 소방차가 골목에 갇힌다 | **치명적** |
| **오탐** (통과 가능한데 막혔다고 판정) | 조금 돌아간다 | 경미 |

**두 오류의 비용이 100배 차이다. 임계값을 대칭으로 두면 안 된다.**

```
안전 마진 = 차폭 2.5m + 여유 0.3m = 2.8m
```

**발표 방어 논리로 최강이다** — "우리는 틀릴 수 있다. 그래서 틀리는 방향을 설계했다."

⏳ 여유값 0.3m은 실운전자 인터뷰로 검증 필요(§9-2).

## 4-5. CCTV 커버리지 판정 📄

`CANDIDATE`를 CCTV 유무로 2차 분류한다.

```
1차: 주소 텍스트 매칭   CCTV 소재지도로명주소에서 도로명 추출 → road_segment와 문자열 비교
2차: 좌표 버퍼 폴백     1차 실패 시에만
```

주소 매칭을 1차로 올린 이유: **CCTV 좌표가 도로 중심선과 8~14m 어긋난다.**
카메라는 인도 폴대에 설치되고 좌표는 주소 기반 지오코딩이라 태생적 오차다.

⚠ **버퍼 반경이 이전 문서에서 25m와 40m로 충돌했다. 값을 하나로 정하고 근거를 적어라.** 미결정.

## 4-6. 인도 포함 문제 📄

수치지도 도로경계면은 포장면 기준이라 담장 안쪽이 안 들어간다.
동명동 도로 대부분이 좁아 인도가 물리적으로 존재할 수 없고, 인도가 있을 수 있는 5~8m 구간은 인도 2m를 잘못 포함해도 잔여 폭이 통과선을 넘어 **판정이 뒤집히지 않는다.**

# 5. 그래프 · 경로탐색

## 5-1. ★ 도로구간은 교차로에서 끊겨 있지 않다 ✅

**이것이 기존 MVP가 작동하지 않은 진짜 원인이다.**

| | 교차 노드(3분기+) | 미분할 접점 |
|---|---:|---:|
| 도로명주소 도로구간 | 19 | **2,338** |
| 표준노드링크 | 452 | 7 |

도로명주소는 "도로명 하나 = 선 하나"로 그려져 있다. 제봉로가 중앙로를 가로질러도 통짜 한 줄이다.
**노딩 없이 networkx에 넣으면 다익스트라가 "경로 없음"을 뱉는다. 코드 문제가 아니다.**

노딩 결과(bbox 기준, ⚠ 정식 경계 확보 후 재산출):

```
1,812 → 4,336 세그먼트 / 노드 3,702 / 연결요소 338개 (최대 80%)
```

진단: `python src/etl/probe.py topo data/processed/road_link.geojson`

## 5-2. 그래프 소스 선택 ✅

**표준노드링크를 그래프 뼈대로 쓰면 안 된다.** 골목을 담지 않는다.

```
표준노드링크 1,334개 중 폭 ≤2m :   42개 ( 3%)
도로명주소   1,812개 중 폭 ≤2m :  699개 (39%)
```

| 역할 | 소스 |
|---|---|
| **그래프 뼈대** | 도로명주소 도로구간 → **노딩 필수** |
| 폭 속성 | 수치지도(주) / 실폭도로(폴백) |
| **위상 정답지 · 간선망 대조** | 표준노드링크 |
| **회전제한** | `TURNINFO` (동명동 87건) |
| 차로수·제한속도 | 노드링크 `LANES` / `MAX_SPD` |

⚠ 노드링크 `REST_W`(제한폭)는 **전량 0**이다. 미기입 필드니 기대하지 마라.

## 5-3. 가중치 설계 📄

**곱셈형으로 확정.**

```
cost = length_m × (1 + α·판정페널티 + β·점유위험도)
```

덧셈이면 짧은 위험구간과 긴 안전구간의 비교가 왜곡된다.

| 판정 | 페널티 |
|---|---|
| RED | ∞ |
| ORANGE / YELLOW | 실측 기반 |
| GRAY | 0.5 (불확실) |
| BLUE / GREEN | 0 |

점유위험도 = 단속밀도(건/100m) 정규화값.

### ⚠ 길이는 지오메트리에서 재계산할 것

`ROAD_LT`(도로 연장)는 **클리핑 전 원본 도로 전체 길이**를 갖고 있다.
필문대로 25m 조각에 4,200m가 기재되는 식이다. **엣지 가중치에 절대 쓰지 마라.**

## 5-4. A* vs 다익스트라 📄

**둘 다 한다. 비용이 0이다.**

```python
nx.dijkstra_path(G, s, t, weight="cost")
nx.astar_path(G, s, t, heuristic=haversine, weight="cost")
```

이 규모에서 성능 차이는 무의미하다. **A*를 쓰는 이유는 속도가 아니라 발표 논거다** — "광주 전역 확장 시 탐색 공간이 커지므로 휴리스틱이 필요하다". 실행시간 비교 그래프 한 장이면 된다.

⚠ **휴리스틱이 실제 비용을 넘으면 최적해가 깨진다.** cost에 페널티 곱셈이 들어가므로 직선거리를 그대로 쓰면 안 되고 **최소 배율로 나눠야** 한다. 여기 틀리면 A*가 다익스트라와 다른 답을 낸다.

## 5-5. 체크포인트를 엣지 속성으로 📄

소화전·CCTV·단속밀도를 **엣지 속성**으로 붙인다. 노드가 아니다.

```
edge: seg_2157
  length_m, width_min_m, width_src, status, confidence,
  cctv_ids[], hydrant_dist_m, enforce_per_100m, turn_ok
```

경로 산출 후 "이 경로상 소화전 3개 경유"를 바로 뽑을 수 있다. 시연에서 강하다.

## 5-6. TMAP/카카오 — 병합이 아니라 병렬 비교 📄

```
1. 같은 출발-도착지로 TMAP API 호출  → "TMAP 추천 경로" (교통체증만 고려)
2. 우리 다익스트라 호출              → "우리 추천 경로" (통과 가능성 반영)
3. 두 결과를 나란히 제시
```

TMAP API는 링크별 혼잡도를 낱개 조회하는 구조가 아니라 완성된 경로를 반환하는 구조라, 우리 그래프의 모든 간선에 혼잡도를 채우는 방식이 API 구조상 성립하지 않는다.

포지셔닝과도 맞는다 — 교통체증 최적화는 TMAP이 이미 최고 수준이고, **우리 차별점은 "TMAP이 모르는 걸 우리는 안다" 하나에 집중한다.**

## 5-7. 미결정 🟡

|---|---|---|
| **그래프 방향성** | 무향 + "긴급차량 예외" 명시 ← 추천 / 유향 + 역주행 페널티 | **결정 안 하면 코드가 두 번 갈아엎힌다** |

### 회전 반경 기준 📄

**폭 3m 골목이라도 직각 코너면 소방차는 못 돈다.** 내륜차(off-tracking) 때문이다.

| 상황 | 기준 |
|---|---|
| 직진 | 유효 폭 3m 이상 |
| **회전(코너)** | 회전반경 차량 중심 10m + 곡선부 폭 4~6m |
| 진입 불가 | 폭 2m 이하 |

**설계 원칙**: `간선 = 직진 폭 판정 / 노드 = 회전 가능 판정. 둘 다 통과해야 유효 경로.`

⚠ 출처가 전부 블로그·기술사 정리다. 「소방청 건축위원회 표준 가이드라인 2021.10」 원문 확보 필요(§9-2).

발표 문구: "회전 제약을 모델에 포함했고 시연 경로는 검증했다. 전 구간 적용은 코너 실측 데이터 확보 후."

# 6. 비전 파트

## 6-1. 지적도 캘리브레이션 방식 — ⬛ 폐기 확정

**도로폭·지적도 같은 "기준 데이터"로는 대응점 자동화가 원리적으로 불가능하다.**

| 사유 | 설명 |
|---|---|
| **순환논법** | "이 골목은 3.2m"를 쓰려면 화면에서 어느 픽셀이 좌/우 연석인지 먼저 찍어야 한다. 그게 없애려던 수동 클릭이다 |
| **정보량 부족** | 폭은 스칼라 1개 = 점 2개. H는 자유도 8이라 점 4개를 요구한다 |
| **지적선은 안 보인다** | 소유권 선이라 담장 안일 수도 밖일 수도 있어 사진에서 특정 불가 |

> **대부분의 "기준"은 dst(실좌표)만 준다. src(어느 픽셀인지)는 안 준다.**

`cadastral_calibration_methodology.md` 폐기.

## 6-2. 캘리브레이션 ≠ 호모그래피 📄

| | 캘리브레이션 | 호모그래피 |
|---|---|---|
| 대상 | 카메라 내부(렌즈) | 카메라와 지면의 관계 |
| 구하는 것 | 초점거리, 주점, 왜곡계수 | 3×3 행렬 H |
| 방식 | 체커보드 20여 장 | 대응점 4쌍 이상 |
| 주기 | 카메라·렌즈당 1회 | **카메라를 옮길 때마다** |

**순서: 렌즈 왜곡 보정 → 대응점 → 호모그래피.** 왜곡을 먼저 펴지 않으면 H를 잘 구해도 화면 가장자리에서 틀어진다.

```python
undistorted = cv2.undistort(img, mtx, dist)
H, mask = cv2.findHomography(src_px, dst_meter, cv2.RANSAC, 5.0)
pts_m = cv2.perspectiveTransform(pts_px.reshape(-1,1,2), H)
```

**대응점은 4쌍이 최소조건이지 권장값이 아니다.** 실무는 6~8쌍 + RANSAC.

## 6-3. 대응점을 지면에 고정한다 ★ 📄

> **폐기된 1차안**: "CCTV는 고정이므로 카메라당 평생 1회 클릭."
> **폐기 사유**: 우리는 CCTV가 아니라 **CCTV 모사**다. 삼각대를 매번 들고 나가므로 카메라는 전혀 고정이 아니다.

**카메라 위치·높이·각도를 재현하려는 시도를 포기한다.**

```
관측점당 1회 (영구)   지면 영구 지물 4~6개의 실세계 상대좌표 실측
매 세션              같은 지물의 이미지 좌표만 다시 얻음 → H 재계산
```

기준 지물 후보: 맨홀 뚜껑 모서리, 보도블록 줄눈 교차점, 전주 밑동, 연석 이음매, 배수구 격자.

**카메라가 어디 서 있든 같은 지면 점들이 프레임에 보이기만 하면 H가 매번 정확히 나온다.**
"매번 동일 위치에서 찍어야 한다"는 제약이 통째로 사라진다.

| 세션 | 방법 |
|---|---|
| 1회차 | 수동 클릭 + 지물 실측 |
| 2회차~ | 1회차 기준 이미지와 특징점 매칭(ORB/SIFT + RANSAC) → 자동 정합 |

**실제 CCTV 배포에서도 쓸모가 있다** — 카메라 흔들림·재설치 시 자동 복구. 발표 논거로 강하다.

이 결정이 §7-2 관측점 개체화를 강제한다.

## 6-4. 오차 구조 ★ 📄

초점거리 f(px), 카메라 높이 h, 대상 거리 d일 때 1픽셀 오차의 실제 크기:

```
깊이 방향   d² / (f · h)      ← 거리의 제곱. 급격히 나빠짐
가로 방향   d / f             ← 거리에 비례. 완만함
```

f=1000px, h=1.5m 기준:

| 거리 | 깊이 1px | 가로 1px |
|---|---|---|
| 10 m | 0.067 m | 0.010 m |
| 20 m | 0.27 m | 0.020 m |
| 30 m | 0.60 m | 0.030 m |

> **골목을 따라 정면으로 촬영할 것. 옆에서 가로지르며 찍지 말 것.**

정면이면 도로 폭이 **가로 방향**이 되어 15m 앞 차량을 5px 틀려도 오차가 0.08m다. 옆에서 찍으면 같은 5px이 1m 이상 벌어진다. 분모에 h가 있으므로 **카메라를 높일수록 깊이 오차가 줄어든다.**

### 오차 요인 순위

| 요인 | 영향 | 대응 |
|---|---|---|
| 대응점 실측 오차 | 최대 | 레이저 거리계 |
| 대응점 배치 | 큼 | 화면 넓게 분산. 한 줄 배열 금지 |
| 지면 평탄 가정 위반 | 큼 | 경사 골목 회피. 관측점 선정 시 고려 |
| 렌즈 왜곡 미보정 | 중 | 체커보드 선행 |
| 카메라 높이 오차 | 중 | 삼각대 고정이면 설정값이라 작음 |

| 2 | 광각(0.5배) 금지 | 왜곡이 커 가장자리 크게 틀어짐 |
| 3 | 렌즈 왜곡 보정 먼저 | 체커보드 20여 장, 카메라당 1회 |
| 4 | 대응점을 넓게 분산 | 몰리거나 일직선이면 H 불안정 |
| 5 | 4점보다 많이 + RANSAC | 이상치 자동 제거 |
| 6 | 근경~중경에서 측정 | 원경은 d² 때문에 오차 폭발 |
| 7 | 삼각대 필수 | 조금만 움직여도 H 무효 |
| 8 | 평평한 구간 선택 | H는 평면 가정 |
| 9 | 줄자를 지면에 펴놓고 함께 촬영 | 사후 검증용 정답지 |
| 10 | **사진 메신저 전송 금지** | EXIF 소실·리사이즈 → 초점거리 증발 |

## 6-6. 유효폭 계산 📄

**뺄셈 방식("GIS 도로폭 − 감지 차폭") 미채택.** 오차가 두 군데(GIS 서류값 + 차폭 감지)에서 이중 누적된다.
대신 **호모그래피 변환 좌표계 위에서 세그멘테이션 결과를 직접 측정**한다.

- YOLO11-seg (`yolo11n-seg.pt`). COCO `{2:car, 3:motorcycle, 5:bus, 7:truck}`
- **세그멘테이션 필수.** bbox는 비스듬한 차량에서 폭을 크게 과대추정한다
- **바닥 접지선 기준** — 마스크 최하단 행의 좌/우 끝. 타이어 접지점에 가장 가깝다
- 한계: 사이드미러 등 뜬 부분은 못 잡는다. §4-4 안전마진이 흡수하도록 설계

## 6-7. CCTV 실시간 스트림 — ⬛ 불가 확정

| 사유 | |
|---|---|
| 데이터 | 공공데이터 CCTV는 **메타데이터만**. 영상 미포함 |
| 법률 | 개인정보보호법 §25 — 정당한 권한자만 열람. 무단 시청도 형사처벌 대상 |
| ITS API | 실시간 영상 API는 있으나 **고속도로·국도용**. 도심 골목 미커버 |

**채택 방향**
- RESTful 연동 인터페이스는 정식 탑재. "권한이 부여되면 그대로 붙는" 구조 → 발표 포인트
- 시연은 사전 촬영 프레임을 **mock GET 서버(FastAPI)** 가 순서대로 반환

## 6-8. DL 투입 지점 — AI 사관학교 방어선 ★

YOLO11-seg 하나로는 "가져다 쓴 것"이라 주인공이 못 된다.

| 우선 | 항목 | 억지 없음 정도 |
|---|---|---|
| 1 | **프라이버시 파이프라인** (번호판·얼굴 마스킹) | 없으면 프로젝트가 법적으로 성립 안 함 |
| 2 | **주정차 vs 주행 판별** (시간축) | 아키텍처가 이걸 요구함 |
| 3 | **야간 강건성** (저조도 향상/도메인 적응) | 실제 문제에서 출발 |
| 4 | 소방관 선호 경로 학습 | 인터뷰 성공이 선행 조건. 리스크 큼 |

### 프라이버시는 엣지에서 ★

**원본이 서버로 넘어가는 순간 개인정보를 "수집"한 것이 된다.**
엣지에서 마스킹 후 전송하면 서버는 애초에 개인정보를 보유하지 않는다.
**발표에서 이 논리 하나로 개인정보 질문을 다 막을 수 있다.**

### 주정차 판별은 시간축으로

**가상 중앙선은 버려라.** 골목엔 중앙선 개념이 없다. 나쁜 휴리스틱이다.
정답은 **연속 프레임에서 정지 = 주차**다.

이것이 아키텍처를 강제한다 — **mock 서버가 단일 이미지가 아니라 프레임 시퀀스를 반환해야 한다.**

```
관측점에서 삼각대 고정 → 30초~1분 동영상 1개
→ 프레임 추출 + 타임스탬프 → mock 서버가 순서대로 반환
```

주행 차량은 5초면 화면을 벗어난다. 30초면 충분하다.
**"24시간 연속 관측 불가"와 "시퀀스 확보 불가"를 혼동하지 마라.** 전자만 사실이다.

보조 신호: 도로 축과의 각도(주차는 대개 평행), 연석과의 거리, 시동/제동등.

### 답사 1회로 셋을 해결한다 ★

**같은 관측점을 오전/오후/야간 3회 촬영한다.**

- "14시 통과 가능 / 19시 불가" → 서비스 필요성 최강 소재
- 관측 신선도(§8-3) 근거 데이터 동시 확보
- 야간 성능 데이터 동시 확보

# 7. 실측

## 7-1. 실측 프로토콜 📄

**8/6 실측은 GPS를 기록하지 않아 대조에 쓸 수 없다.** 세그먼트 중심선과 최대 23m 어긋났고, 그날 산출된 소스별 오차 수치는 전부 무효다. 같은 실수를 반복하지 않기 위한 필수 항목:

```
1. seg_id + 관측점 ID
2. ★ 기준 지물 서술 — "서쪽 끝에서 세 번째 맨홀 중심"
3. GPS 좌표 (보조. 지물이 우선)
4. 기준 사진 (기준 지물이 프레임에 보이게)
5. 측정 종류: 담~담 / 연석~연석 / 통행폭 / 코너폭
6. 시각 · 날씨 · 조도
```

### ⚠ GPS로는 지점 특정이 안 된다

도심 골목 폰 GPS 오차 **5~15m**, 골목 폭 **3m**.

| GPS로 되는 것 | 안 되는 것 |
|---|---|
| 어느 세그먼트 위인가 | 세그먼트 내 어느 지점인가 |

**지점 특정의 해법은 지물 기준이다.** 기준 지물을 적고 그것이 프레임에 보이게 찍으면 재방문 시 재현된다.

### 장비 📄

- **레이저 거리계** (20~30m급, 5만 원 내외) — ⏳ 미구매. **없으면 §7-1이 막힌다**
- 30m 줄자 (백업)
- 반사 대상 없을 때: A4 클립보드/흰 폼보드를 팀원이 들고 선다
- **차량 간 거리는 차체가 아니라 지면 마킹 간 거리를 잰다.** 곡면이라 레이저가 튄다

> 줄자 U자 처짐 오차는 5m 구간에서 수십 cm다. **안전마진(0.3m)보다 오차가 크면 실측이 무의미하다.**

## 7-2. 관측점을 GIS 1급 개체로 📄

§6-3 재설계가 이걸 강제한다. 지금 설계에 **"우리가 카메라를 세우는 지점"이라는 실체가 없다.**

```json
{
  "obs_id": "OBS-001",
  "seg_id": "seg_2157",
  "geom": [x, y],
  "landmark_desc": "장동로 서쪽 끝에서 세 번째 맨홀",
  "ref_points": [
    {"id": "R1", "desc": "맨홀 북동 모서리", "local_xy": [0.0, 0.0]},
    {"id": "R2", "desc": "보도블록 줄눈 교차", "local_xy": [2.4, 0.0]}
  ],
  "ref_image": "obs001_ref_20260810.jpg",
  "sessions": [
    {"at": "2026-08-10T09:30", "video": "...", "H": [[]], "illum": "day"},
    {"at": "2026-08-10T19:40", "video": "...", "H": [[]], "illum": "night"}
  ]
}
```

따라오는 것: 세션 간 H 재계산 / 시간대별 통행폭 비교 / **관측 커버리지 레이어**(GRAY 구간 중 어디를 실제로 덮었는지) / 발표에서 정량 제시.

**관측점으로 CCTV 좌표를 그대로 쓰지 마라.** 시나리오 경로 위에서 골라야 한다.

## 7-3. 실측 보조 앱 📄

**네이티브 앱 금지.** 기존 지도 HTML에 얹는다.

| # | 기능 |
|---|---|
| 1 | 현재 GPS + 최근접 세그먼트 자동 판별 |
| 2 | 관측점 등록 → 좌표·시각·seg_id 자동 기록 |
| 3 | 사진 첨부 + **기준 지물 서술 입력(필수 필드)** |
| 4 | 측정값 입력 |
| 5 | JSON 내보내기 |

**전제**: HTTPS가 아니면 `navigator.geolocation`이 동작하지 않는다. Netlify 배포 선행.

**설계 원칙**: GPS는 보조다. 가장 중요한 입력은 **기준 지물 서술과 기준 사진**이다.

## 7-4. 안전 — 타협 대상 아님

- **오전 9~11시 고정.** 8월 광주 오후 아스팔트 답사는 실제로 위험하다
- 야간 답사는 별도 일정
- 도로 한복판 실측 시 **2인 1조, 1명은 차량 감시**

# 8. 시나리오 · 평가

## 8-1. 시나리오를 손으로 고르지 마라 — 그래프에서 역산 📄

```python
for (출발, 도착) in 조합:
    d1 = 최단경로(제약 없음)
    d2 = 최단경로(RED 제외)
    if d2 / d1 > 1.5 and d2 < inf:
        후보에 추가
```

**"우리 시스템이 없었으면 소방차가 갇혔을 출발-도착 쌍"을 자동으로 찾는 것이다.**
시나리오 선정 자체가 GIS 산출물이 되고, "임의로 고른 것 아니냐"는 질문을 막는다.

출발점은 대인/지산 119안전센터(§1-4). 여기에 실제 화재 출동 통계를 얹으면 "실제로 일어날 법한 시나리오"까지 방어된다.

**선정 조건**: 코너 통과 가능 / CCTV 커버 구간 포함 / 우회로 존재.

## 8-2. ★ 평가지표 — 최대 구멍. 담당자 없음 🔴

> **우리 시스템이 잘 작동한다는 걸 무엇으로 증명하나. 지금 답이 없다.**

발표에서 반드시 나오는 질문인데 준비가 0이다.

| 지표 | 측정 방법 |
|---|---|
| 판정 정확도 | 실측 대비 통행폭 오차 (MAE) |
| 진입 실패 회피율 | 시나리오에서 RED 진입 0건 |
| 우회 비용 | 최단경로 대비 거리·시간 증가율 |
| **베이스라인 대비** | **현행 최단경로 방식과 정량 비교** |

**베이스라인 비교가 핵심이다.** "우리 시스템 vs 아무것도 안 했을 때"가 없으면 효용을 못 보여준다.

**회의에서 담당자를 배정해라. 이게 지금 가장 급하다.**

## 8-3. 관측 신선도 🔴

마지막 관측이 40분 전이면 그 판정을 믿고 소방차를 보낼 수 있나. **지금 설계에 시간 개념이 없다.**

```
신뢰도 = f(경과시간, 해당 도로 단속밀도)
30분 전 관측 + 상습주차 구간 = 사실상 GRAY
```

**이게 없으면 "실시간이라면서 얼마나 실시간인가요?"에 답을 못 한다.**

## 8-4. GRAY 구간 대책 📄

CCTV가 없는 구간은 관측이 불가능하다. 대신 **사전확률**을 제시한다.

| 신호 | 출처 | 논리 |
|---|---|---|
| 단속밀도 | `enforcement` (건/100m) | "관측 불가하나 연 N건 단속되는 상습 점유 구간" |
| 상가 밀도 | `poi_store` | 상가 앞 = 주차 압력 |
| 음식점 비율 | `poi_store` (동명동 39%) | 야간 집중, 배달 이륜차 |
| 도로폭 | `width_min_m` | 좁을수록 1대만 세워도 막힘 |

### ⚠ 단속 이력을 시간대 가중치로 쓰지 마라

```
14시 → 33,412건 (전체의 39%)
```

주차 패턴이 아니라 **입력 기본값**이다. 발표에서 방어할 수 없다.
**시간대 근거는 답사 촬영으로만 확보한다(§6-8).**

### ⚠ 단속 이력에 좌표가 없다

`위반장소명`이 도로명주소다. **도로명(RN)으로 도로구간에 조인한다.**
단 절반이 랜드마크 명칭("문화전당 부설주차장" 3,137건 등)이라 필터가 필요하다.
동명동권 도로명 1차 매칭 2,379건.

## 8-5. 장애물(전봇대) — ⬛ 종결

- **"도로선 밖 돌출 여부·돌출 폭"을 담은 공개 데이터는 어디에도 없다**
- 전주는 한전 전산화번호만 공개, 좌표 미공개
- 특허 KR101515811B1 변환 알고리즘을 오차 0m로 재현했으나 **인코딩 해상도가 50m 격자**라 687개가 227개 점에 뭉쳤다. 골목 폭 3m에 오차 50m → 사용 불가

기술적으로 성공, 목적에는 사용 불가. **별도 확보 중단.**

**★ 버리지 말 것**: 특허 본문에 **한전이 재난 구조 목적으로 소방(119)에 전주 실측 TM 좌표를 제공한다**는 근거가 있다. 인터뷰 질문에 추가하고 확장성 논거로 쓴다.

## 8-6. 소화전 📄

동명동 법정경계 내 공개 소화전 **1건**.

**이 숫자를 그냥 쓰지 말고 이렇게 써라:**

```
동부소방서 관할 실제 소방용수    588개 (지상식 431 + 지하식 157)
공개 표준데이터의 광주 동구       31개
                                 → 공개율 5%
```

**"1개밖에 없다"보다 "588개 중 31개만 공개돼 있다"가 훨씬 강하다.**
발표에서는 *"공개 데이터만으로는 소방 인프라 레이어를 구축할 수 없다. 이것이 실무 연계가 필요한 이유다"* 로 쓰고, 인터뷰 협조요청 근거로도 쓴다.

**소화전 레이어는 좌표 확보 전까지 지도에서 뺀다.** 1개짜리 지도는 안 만드느니만 못하다.

활용 근거(좌표 확보 시): NFTC 401 수평거리 140m, NFSC 109 옥외소화전 40m —
"도로엔 못 들어가도 근처 소화전이 있으면 호스로 대응 가능"이라는 RED 구간 세분화 로직.

# 9. 외부 의존

## 9-1. 소방관 인터뷰 1차 — ✅ 완료

응답자는 **구급차 근무 경력 중심, 펌프차 운전 경험 없음.** 이 한계를 감안한다.

| 질문 | 답변 |
|---|---|
| 불법주차 방해 흔한가 | 흔함. 원룸촌·구축 단독주택 밀집지 특히 심함 |
| 방해 위치·형태 | **골목 양옆 + 코너에 바짝 붙인 주차**가 최악 → 교차점 근접 가중치 |
| **최소 여유공간(m)** | **미확인** ← 핵심 미해결 |
| 강행 진입 | 인명 위급·대형화재 아니면 조심스럽게 대응 |
| 기존 MDT 실시간 정보 | **없음** — 우리 서비스 필요성 재확인 |

| 알림 전달 지점 | **119상황실 단계가 가장 적절** |

### ⚠ 포지셔닝 정정

기존 태블릿 네비게이션 시스템의 존재가 확인됐으나 **직접 연동·수정하지 않는다.**
국가 기관 시스템 접근 권한 획득 가능성이 낮고, 팀 역량 대비 과도한 스코프다.

**독립 웹 대시보드로 설계한다.** 119상황실 근무자가 기존 화면과 별도로 참고하는 보조 도구.
"알림이 상황실 단계에 전달되는 게 적절하다"는 답변은 **최종 사용자 확정**으로만 반영한다.

# 10. 개발 환경 · 스택

## 10-1. 지도 엔진 — ✅ MapLibre + V-World로 확정 (2026-08-09)

Mapbox도 Naver도 아니다.

| | 문제 |
|---|---|
| Mapbox | 한국 배경이 OSM 파생이라 골목 이름·건물이 비어 있다. 유료 토큰 |
| Naver | Map Style Editor로 커스텀은 가능해졌으나 GeoJSON 데이터 기반 스타일링이 약하다. 지도 로딩 1회당 과금 |
| **MapLibre + V-World** | ✅ |

**MapLibre GL JS는 Mapbox GL v1 포크라 API가 사실상 동일하다.** 기존 코드가 거의 그대로 붙는다.
상가 POI는 `poi_store`로 직접 얹으므로 Naver의 로컬 데이터 이점이 사라진다.

```js
sources: {
  vworld: {
    type: 'raster',
    tiles: ['https://api.vworld.kr/req/wmts/1.0.0/{KEY}/Base/{z}/{y}/{x}.png'],
    tileSize: 256,
    attribution: '공간정보 오픈플랫폼(브이월드)'
  }
}
```

⚠ **WMTS 축 순서가 `{z}/{y}/{x}`다.** `{z}/{x}/{y}`로 쓰면 타일이 어긋난다.
⚠ 인증키 신청서에 **WMTS/TMS API + 배경지도 API** 체크 필요. 브라우저 호출 시 `&domain=등록URL` 필수.

`dongmyeong_map_naver.html`은 갱신 중단. **두 벌 유지가 UI가 구버전 폭을 물고 있던 원인이다.**

## 10-4. 데이터 관리 ✅

```
data/raw/        불변. git 제외. 출처별 하위폴더 + 명명규칙
data/processed/  git 포함 (용량 작고 팀 공유 필요)
sources.yaml     대장. 여기 없으면 파이프라인에 못 들어온다
```

**명명 규칙**: `{기관}_{데이터}_{범위}_{기준일}.{zip|csv|tif|xml}`
한글·공백·괄호·대문자 금지. CSV는 UTF-8. 상세는 `data/raw/README.md`.

# 11. 우선순위

## 11-1. 지금 막혀 있는 것

```
⏳ juso 전자지도 심사        ← 행정구역경계 + 건물. 세그먼트 수 확정의 전제
⏳ 레이저 거리계 미구매       ← 실측 프로토콜(§7-1)이 막힘
🔴 평가지표 담당자 없음       ← 뭘 만들어도 증명 못 함
```

## 11-2. 순서

```
STEP 1  행정구역경계 확보
        → 동명동 정식 경계로 재클립
        → 노딩 → 세그먼트 수 확정 → 전 문서의 "222" 교체

STEP 2  폭 산출 (수치지도 주 / 실폭도로 폴백 / 교차로 5m 제외)
        → tier 재분류 → 6색 분포 확정

STEP 3  그래프 구축 + 다익스트라/A*
        → 시나리오 자동 탐색(§8-1)

STEP 4  관측점 선정 → 기준점 실측 → 오전/오후/야간 3회 촬영

STEP 5  mock 서버 / 프라이버시 파이프라인 / 야간 강건성
```

**의존 관계**: `경계 → 노딩 → 폭 → 그래프 → 시나리오 → 관측점 → 촬영`

**시나리오 자동 탐색이 답사보다 먼저다.** 순서가 꼬이면 엉뚱한 골목을 찍고 답사가 통째로 날아간다.

## 11-3. 병렬로 돌릴 수 있는 것

STEP 1 대기 중에 막히지 않는 것들:

- 평가지표 정의(§8-2) ← **가장 급함**
- 소방서 인터뷰 전화(§9-2)
- 그래프 방향성 결정(§5-7) ← 안 정하면 코드 두 번 갈아엎힌다
- CCTV 커버리지 버퍼 반경 확정(§4-5)
- mock 서버 프레임 시퀀스 구조 설계
