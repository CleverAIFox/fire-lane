### 2-1. `unknown` 354 의 사유

폭 산출 불가는 **0** 이다. 회색은 한 가지 뜻만 갖는다 — 카메라가 없어 못 본다.

| 사유 | 구간 | 뜻 |
|---|---:|---|
| `no_cctv_band` | 152 | 3~7m 대역. 주정차 여부로 갈리는데 CCTV 25m 밖 |
| `no_cctv_thin` | 128 | 노면 3m 미만 · 도로대장폭은 3m 이상 — 근거가 하나뿐 |
| `no_cctv_narrow` | 62 | 노면도 도로대장도 3m 미만이나 벽 사이는 여유 있음 |
| `no_cctv_single` | 12 | 7m 이상이나 표본 부족으로 통과 확정 보류 |

**색은 4종 고정이다.** 사유는 회색의 하위 구분이지 다섯 번째 색이 아니다.
범례에 별도 줄로 올리지 않는다 — 색이 5종으로 보이고 합계도 안 맞아 보인다.
하위 구분은 툴팁과 상세 패널에 넣는다.

### 2-2. 판정 기준의 출처

임의 임계값이 아니다. 소방청 「2025 화재현장 골든타임 확보 종합대책」을 따른다.

```
진입불가   폭 2m 이하, 또는 이동불가 장애물로 진입 불가. 구간 100m 이상
진입곤란   폭 3m 이상 + 장애물·상습주차로 상시 장애. 구간 100m 이상
기준 차량  중형펌프차량 전폭 2.5m
```

```
TRUCK = 3.0     차량 전폭 2.5 + 미러·조향 여유 0.5   (2026-08-06 답사)
PARK  = 2.0     주차 1대 노면 점유
blocked   최대 폭(벽~벽) < 3.0
clear     최소 폭 >= 3.0 + 2 x 2.0 = 7.0            양쪽 주차를 가정한다
```

`clear` 가 양쪽 주차를 가정하는 이유는 양방 주차가 상시인 골목에서 한쪽만
보는 것이 낙관 방향이기 때문이다. 임계값 정본은 `src/firelane/seg/params.py` 다.

## 3. 판정의 근거

이 절은 판정이 무엇 위에 서 있는가를 적는다. 그렇게 되기까지의 경위는
DECISIONS 소관이다.

### 3-1. 구간 수는 고정값이 아니다

```
도로명주소 도로구간    206
실폭도로               219
노딩 후 (동명동)       641
스코프 확장 후       1,266     접근 회랑 포함
노드접합 · 병합 후   1,101     ← 현재 판정 단위
```

노딩 규칙이 바뀌면 `seg_id` 가 전부 밀린다. 외부 참조에는 `seg_uid` 를 쓴다.

기존 문서의 "222구간"은 출처를 찾지 못해 폐기했다. 206도 219도 222가 아니다.

### 3-2. 도로명주소는 위상이 보장되지 않는다

원본은 "도로명 하나 = 선 하나"라 교차로에서 분할되지 않는다. 노딩 후에도
밀리미터 단위 좌표 오차로 구간이 분리된다(**T자 접합**).

| 처리 | 연결요소 | 최대요소 연장비 |
|---|---:|---:|
| 원본 | 40 | 93.29% |
| `set_precision(0.5)` | 22 | 97.74% |
| **끝점 투영 스냅 0.5m** | **6** | **99.76%** |

잔여 5구간(77m)은 알고리즘 한계가 아니라 **도로명 미부여 구간**이다.
그중 3곳이 관리폭 1.0~1.5m 로 소방차 진입이 원천 불가하다.
**데이터의 공백 자체가 위험구간 지표다.**

노드 식별에도 같은 관용을 준다 — `NODE_TOL 0.5m`. 밀리미터 반올림으로
식별하면 4cm 떨어진 두 점이 별개 노드가 되고 길이 0.04m 짜리 엣지가 생긴다.

### 3-3. `ROAD_BT` 는 폭 값으로 쓰지 않는다

도로대장의 명목 폭은 **171구간(84%)에서 실측 트랜섹트보다 넓다.**
중앙 차이 +1.00m. 못 지나가는 길을 지나간다고 판정하는 방향이다.

★ **예외는 하나뿐이다.** 폭을 끝내 못 잰 구간에 한해, 명목폭이 `TRUCK` 미만이면
`blocked` 으로 확정한다. 폭이 안 나오는 것과 잴 만한 도로가 아닌 것은 다르다.
명목폭 1.0m 짜리 부속 통로를 회색으로 두면 영상판정으로 메울 수 있다는 뜻이
되는데, 카메라를 갖다 대도 소방차는 못 들어간다. 실측값이 하나라도 있으면
그쪽이 항상 우선하므로 이 규칙은 폭 미산출 구간에만 걸린다.

### 3-4. 폭은 하나로 못 정한다

| 화면 표기 | 필드 | 데이터 | 뜻 |
|---|---|---|---|
| 최소 폭 | `width_min_m` | 실폭도로·수치지형도 도로경계 | 확실히 비어 있는 폭 |
| 최대 폭 | `width_max_m` | 건물 폴리곤 | 벽에서 벽까지. 물리적 최대 |

최대 폭이 전 구간에서 넓고 중앙 차이 **+2.08m** 다. 그 사이에 전신주·화분·
실외기·계단·주차 차량이 들어 있다. 3.0m 임계로 보면 최소 폭 기준 125구간 대
최대 폭 기준 35구간이 걸리며, **90구간(47%)은 어느 쪽을 믿느냐에 따라 판정이
뒤집힌다. 이 밴드를 좁히는 것이 영상판정과 실측의 역할이다.**

`width_max_m` 은 **496 / 1,101 (45%)이 결손**이고 도로 폭대별로 고르게 퍼져 있다.

```
0–3m    160 / 413   38.7%      ← 1.5m 골목에 건물이 40m 밖일 수는 없다
3–5m     44 / 113   38.9%
5–7m     67 / 155   43.2%
7–10m   119 / 206   57.8%
10m+    104 / 212   49.1%
```

재현 — `uv run python tools/wmax_audit.py`

### 3-5. 구간 폭은 단일 소스의 표본만으로 낸다

표본마다 다른 소스를 채택하면 `min()` 이 혼합 집합의 최솟값을 뽑는다. 표본 1이
1:1,000 의 3.2m, 표본 2가 실폭도로의 1.8m 인데 그 둘의 최솟값을 구간 폭이라고
부르게 된다. 값을 낸 최우선 소스 하나로 고정하고 그 소스의 표본만 쓴다.

```
채택 소스   ngii1k 1,014 · silpok 84 · ngii 1 · 미산출 2
소스 순위   1:1,000 도로경계 → 1:5,000 도로경계면 → 실폭도로
자격 조건   커버율 COV_MIN 0.5 미만이면 탈락. 다음 순위가 올라간다
```

커버율이 높은 소스를 고르지 않는다. 실폭도로가 0.955 로 가장 높은데 그것을
채택하면 소스 우선순위 결정을 정면으로 뒤집는다. 커버율은 **선택 기준이 아니라
자격 기준**이다.

### 3-6. 교차로 안에서는 그 도로의 폭을 잴 수 없다

교차로 안의 한 점에서 도로 A 에 수직으로 법선을 그으면, 그 법선은 **교차하는
도로 B 를 따라 길이 방향으로 달린다.** 나오는 값은 폭이 아니라 "도로 B 가
60m 안에서 얼마나 뻗어 있나"다.

```
제봉로           3.3m 구간 → 폭 55.39m
필문대로218번길   4.2m 구간 → 폭 45.63m
경양로           7.3m 구간 → 폭 45.33m
```

기하학적으로 정의되지 않는 것이지 측정 기법의 한계가 아니다. 그래서 교차로
파편은 독립 피처로 두지 않고 동일선상(30° 이내) 이웃과 하나의 산출단위로 묶는다.
그래프 `G` 는 라우팅·교차로 노드의 정본이므로 손대지 않고 산출 단위만 병합한다.

교차부 제외 범위는 고정 반경이 아니라 `A0080000` 평면교차점 실형상으로 판정한다.
폴리곤이 10m 안에 있으면 폴리곤만 신뢰하고, 없는 교차로만 반경으로 폴백한다.

### 3-7. 골목의 65%는 영상판정이 불가능하다

CCTV 유효범위를 25m 로 잡으면(초과 시 호모그래피 오차 급증) 이렇게 된다.

```
CCTV 유효범위 안      380 / 1,101   (34.5%)
CCTV 거리 중앙값       39.3 m
최대                   140 m
영상판정 불가          354구간 · 14,505m   (전체 연장의 30%)
```

★ **영상 기반 진입 판정 시스템을 만들어도 골목의 65%에는 적용할 수 없다.
알고리즘의 한계가 아니라 인프라의 한계다.**

완화 요소 — 영상판정 불가 구간이 담당하는 소방 통행량은 18% 다. 주요 동선에는
대체로 CCTV 가 있다.

`CCTV_RANGE = 25.0` 의 근거는 §16-1 에 적는다. **실측 전에는 바꾸지 않는다.**

### 3-8. 출동은 소방서가 아니라 119안전센터에서 나간다

대인(서 1.0km) · 지산(동 1.2km). 둘 다 동명동 밖이다.

```
동 경계 진입점               60곳
실사용 진입점                23곳
출동 통행의 80%를 담당        5곳
출동 통행의 50%를 담당        2곳
```

**진입점 5곳에 대책을 집중하면 출동의 80%가 개선된다.**

### 3-9. "못 간다"는 세 가지 값이 있다

세 값은 산출 경로가 다르다. **같은 이름으로 부르면 반드시 섞인다.**

| 값 | 수 | 무엇을 세나 | 어디서 나오나 |
|---|---:|---|---|
| `verdict` 통행 불가 | 159 | 구간 자체의 폭이 모자란다. 지도의 빨강 | `seg/geom.py::verdict()` |
| 차량 비용 통행 불가 | 416 | 폭 여유 · 내륜차 · 회전반경까지 넣으면 비용이 무한대다 | `seg/vehicle.py::edge_cost()` |
| 도달 불가 | 414 | 구간은 지나갈 수 있어도 안전센터에서 거기까지 길이 끊긴다 | 막힌 엣지를 뺀 Dijkstra |

```
도달 가능   687 / 1,101  (62%)   안전센터에서 막힌 길 없이 갈 수 있다
도달 불가   414          (38%)
경로에 쓰인 구간  587            route_vehicle.csv
```

★ **416 이 동명동 구간 수(`in_emd`)와 우연히 같다.** 두 값은 아무 관계가 없다.
2026-08-25 문서 재편에서 이 우연 때문에 416 을 오기로 판단해 지웠다가 되살렸다.
숫자만 보고 같은 것이라고 판단하지 않는다.

**막힌 구간 하나가 뒤쪽 골목 여러 개를 통째로 끊는다.** 폭 15m 대로라도
진입로가 막히면 소방차가 못 간다. 구간의 성질과 망 위에서의 도달 가능성은
다른 값이다.

★ 차량 비용 통행 불가 416 은 **판정에 반영되지 않는다.** 지도는 여전히
`verdict` 넷만 그린다. 반영하려면 `route_usage` 를 대체해야 하고 그러면
golden 재잠금이 필요하다(PLAN §1 #27).

★ 막힌 엣지는 **그래프에서 뺀 뒤** Dijkstra 를 돌린다. 큰 비용을 주고 남겨두면
다른 길이 없을 때 그 엣지를 쓴다 — "막힌 길로라도 도달"은 답이 아니다.
`reachable` 은 **양 끝 노드가 모두 도달 가능할 때만** 참이다.

### 3-10. 경로가 둘인 이유

```
route_usage        weight="length"       회랑 산정용. 폭을 모른다
route_vehicle.csv  vehicle.edge_cost()   폭 · 내륜차 · 회전반경 반영
```

`access_corridor()` 는 **폭 산출보다 먼저** 돈다(`segments.py` 194줄 대 435줄).
그래서 거리만 쓸 수 있고, 그 결과가 `route_usage` 다. 순서를 바꾸지 않는 이유는
회랑 산정(표출 스코프)이 폭에 의존하면 계보가 꼬이기 때문이다.

★ **`route_usage` 는 통행 가능성을 뜻하지 않는다.** `route_usage > 0` 인
579구간 중 `blocked` 이 41, 폭 3.0m 미만이 168이다. 스키마도 "최단경로
사용횟수"라고만 적는다.

119안전센터 2곳에서 모든 노드까지 **단일 출발 Dijkstra** 를 돌린다. 목적지가
다수이므로 A* 의 이점이 없다 — 휴리스틱의 이득은 목적지가 하나일 때 나온다.

### 3-11. 런타임 프루닝은 폭이 아니라 경로로 한다

정적 폭 기준으로는 61%가 영상판정 대상으로 남는다(동명동이 원래 좁다).
반면 실제 최단경로에 등장하는 엣지는 이렇다.

```
1회 이상 사용        665 / 4,227  (15.7%)
통행량 80% 담당      177개  (4.2%)
통행량 50% 담당       71개  (1.7%)
```

**71개 엣지가 출동 통행의 절반을 처리한다.** 영상판정은 여기부터 건다.

### 3-12. 소화전은 동명동에 1개뿐이다

```
동부소방서 관할 소화전        지상식 418 + 지하식 171 = 589
소방용수시설 총계             589 + 저수조 32 + 급수탑 1 + 비상소화장치 32 = 654
공개된 것(표준데이터)         광주 동구 31개
그중 동명동                   1개
```

★ **"소화전"과 "소방용수시설"을 구분해 말한다.** 분모의 출처는
`hydrant_summary`(동부소방서 관내 지역별 소화전 현황)이며, 발표에 쓸 때 함께
인용한다. **공개 데이터에는 분모가 없다.** 데이터 공백 자체가 결과다.

### 3-13. 차량 제원

판정과 경로 비용의 기준 차량이다. `sources.yaml` 의 `vehicle_spec` 이 정본이고
**기본값을 두지 않는다** — 없으면 `seg/vehicle.py` 가 죽는다.

출처는 소방청 「소방장비 기본규격」 소방펌프차 **KFS-1-0073-2025-00 §3.3**
(2025-12-24 고시)이다. 원문 표기는 "이하"다.

```
구분   전장(m)    전폭(m)    전고(m)   물탱크(ℓ)
대형   8.5 이하   2.5 이하   3.4 이하   4,500 이상
중형   8.0 이하   2.5 이하   3.2 이하   2,800 이상   ← 현재 기준
소형   6.8 이하   2.2 이하   2.8 이하   1,200 이상
경형   5.2 이하   1.9 이하   2.8 이하     500 이상
```

★ **축거와 최소회전반경은 공식 규격에 없다.** KFS-1-0073 ·
KFS-1-0030(소형사다리차) · 2025년 MAS 차종별 제작규격 셋을 전수 확인했다.
내륜차 계산에 그 둘이 필요하므로 지금 값은 추정이며 `wheelbase_verified: false`
가 그 표시다. D-30 소방서 인터뷰에서 확정한다.

#### 내륜차

회전 시 뒷바퀴가 앞바퀴보다 안쪽으로 도는 폭 차이다.

```
Δ = R − √(R² − L²)        R = 회전반경 · L = 축거

     R      내륜차    필요폭
   직선      0.00     3.00
     20      0.40     3.40
      8      1.07     4.07
      6      1.53     4.53   회전 불가
```

1차 근사 `L²/(2R)` 를 쓰지 않는다. R=8 · L=4 에서 근사 1.000 대 정확 1.072 로
7cm 차이가 나고, 그것이 3.0m 임계 근처에서 판정을 가른다.

### 4-1. ★ 이 대조는 검증이 아니라 적합이다

절대편차를 12.6 → 7.24m 로 줄이는 과정에서 이 표를 **게이트로 썼다.**
게이트로 쓴 자료는 그 순간부터 외부 검증 수단이 아니다.


소방서 7구간은 "기존 행정자료와 대체로 일치한다"는 정합성 근거로는 유효하지만
"우리가 옳다"는 증거로는 쓸 수 없다.

### 4-2. 대조의 한계

소방서 데이터에 **좌표가 없다.** 도로명으로만 매칭되므로 도로 전체(대로 구간
포함)를 잡는다. 그래서 구간 대표폭인 중앙값과 비교하며, 최솟값으로 비교하면
교차로 근처 극협소 지점을 잡아 -3~-7m 로 벌어진다. 정밀 대조에는 구간 좌표가
필요하며 D-30 인터뷰 요청 항목이다.

필문대로289번길은 본선과 측도가 한 폴리곤인 구간이다. 정보공개청구 17337943
도로대장이 여기에 걸려 있다.

### 4-3. ★ 이 표는 파일로 남지만 봉인 사본이 낡았다

`segments` 단계가 매 실행 `data/processed/nfa_compare.json` 을 쓴다. 현재 값은
절대편차 합 8.99m · 7구간이며 위 표와 같다. `tools/docnum_check.py` 가 실행할
때마다 이 값을 띄우므로 서술과 대조할 수 있다.

다만 이 파일은 **커밋되지 않는다.** `.gitignore` 가 `data/processed/*.json` 을
막고 예외 넷(`segments.schema.json` · `_manifest.json` 등)에 들어 있지 않다.
그래서 저장소만 받은 사람에게는 이 값이 없다.

★ **`data/baseline/*/nfa_compare.json` 세 벌은 전부 2026-08-13 자 판이다**
(절대편차 합 7.24m · `as_of` 도 그 날짜). <!--stale-ok--> 봉인 시점의 파이프라인

```
interim      탐색·대조 산출물. 대장에 없고 지워도 된다
processed    저장소 안. 4개만 커밋하고 나머지는 재생성
field        실측 원자료. ★ 재생성 불가. raw 와 같은 등급. 저장소 안
_quarantine  대장에 없는 파일. 삭제하지 않고 격리
web/data     표출용. 커밋한다
data/baseline  ★ 예외. 원본이 소실돼 재생성 불가가 된 산출물만 봉인
```

**심링크는 쓰지 않는다.** `data/raw` 를 심링크로 걸었더니 git 이 추적했고,
exFAT 에서 `git reset --hard` 시 경로 문자열 파일로 체크아웃되면서 원본이
소실됐다. `src/firelane/paths.py` 의 환경변수 방식으로 대체했다.

```bash
export FIRE_LANE_DATA="<raw 상위 폴더 경로>"      # 리눅스
setx FIRE_LANE_DATA "<raw 상위 폴더 경로>"        # 윈도우
```

미설정 시 `<repo>/data/raw` 를 쓴다. 단일 머신이면 그걸로 충분하다.

★ **`FIRE_LANE_RAW` 는 폐기됐다.** `paths.py` 가 레거시로 처리하며, 설정돼
있으면 `FIRE_LANE_DATA` 를 덮어써 기계 간 산출물이 갈린다. 실행 시 경고가
나온다. 셸 프로필에 남아 있으면 지울 것.

`field` 와 `processed` 는 환경변수를 타지 않는다. 야장은 수십 KB 이고 UI
담당·심사위원이 clone 만으로 봐야 하는 자료다.
강제자 — `tests/test_reproducibility.py::test_paths_match_layer_table`

### 6-3. 폭 주 소스 — 1:1,000 수치지형도

```
V-WORLD SHP 74도엽 (2026-03) + 국토정보플랫폼 NGI 보완분 143도엽
→ ngii1k_5186.gpkg          도로경계  A0010000
→ ngii1k_center_5186.gpkg   도로중심선 A0020000 (도로폭 · 일방통행 · 차로수)
→ ngii1k_walk_5186.gpkg     보도      A0033320
→ ngii1k_xsec_5186.gpkg     평면교차점 A0080000
→ 가로등·보안등 점           C0220000
```

폴더명 `ngii1k` 는 기관명 규칙의 의도된 예외다. `ngii/` 로 합치면 `rglob` 이
연속수치지도 294MB × 2 까지 집어 파싱하려 든다.

★ **행정구역 단위 다운로드는 스코프를 보장하지 않는다.** V-WORLD 동구 SHP
판(74도엽)이 1:50,000 경계에 걸친 도엽 12장을 흘려 스코프의 69%가 도로경계
폴리곤 밖이었다. 북·남·서구 상품도 그 띠를 비껴간다. 취득 후 반드시 스코프
bbox 와 교차 검증한다. 강제자 — `guards.coverage_check`(상한 10%)

### 6-4. 가로등 — 두 데이터가 서로를 대체하지 않는다

```
streetlights   46지점 · 573등    지번 대표점(±50m). 등 수 · 관리번호가 정본
lightpoles   1,143점             실제 폴 위치. 구분만 있고 등 수는 없다
```

위치를 보려면 폴, 등 수를 보려면 지점이다. 좌표가 지번 대표점 하나로 뭉쳐
있으므로 그대로 점을 찍으면 "여기 가로등 1개"라는 거짓말이 된다. 그렇다고
`distinct` 로 좌표당 1행만 남기면 등 수의 93% 가 사라진다. **중복 행이 아니라
좌표만 뭉쳐진 서로 다른 등이다.** group-by + count 로 등 수를 보존하고,
지주 굵기 √n · 반경 50m 점선 원으로 불확실성을 드러낸다.

★ 이 원은 CCTV 커버리지 원과 의미가 정반대다. CCTV 는 "이 범위를 본다"이고
가로등은 "이 범위 안에 있다"이다. 색과 선 종류를 다르게 쓰고 범례에 명시한다.

### 7-1. 알려진 근사

- `length_m` 은 **수평거리**다. 경사 보정 전이며 실주행거리는 0.05~1.2% 더 길다.
  동명동 평균 경사 1.8° · 최대 9.0°. 보정에는 5m DEM 이 필요하다.
- 폭은 경사 영향을 받지 않는다. 다만 횡단경사가 있으면 유효폭이 줄어드는데,
  90m 격자로는 잡을 수 없다.
- 지도의 지형은 공개DEM 90m 를 보간한 **표현용**이다. `exaggeration` 기본값은
  1.0(실제 비율)이며, 올리면 표고가 왜곡되므로 발표에 쓸 때 명시한다.
- 정사영상의 미터 단위 정합은 **미검증**이다. TIF 에 경계좌표가 없어 도엽
  bbox(5179→5186) + 사방 균등 pad 를 가정했고 조대 정합만 확인했다.

### 7-2. 아직 검증되지 않은 것

- **폭 실측 0건.** `width_verified` 는 전건 `false` 다. 2026-08-06 답사는
  GPS 미기록으로 무효다.
- **`CCTV_RANGE` 25m 는 미확인 값이다.** 이 값 하나가 354구간의 판정을 가른다.
  §16-1 이 그 근거를 다룬다.
- **`width_cov` 0.5 미만 4구간.** 채택 소스가 그 구간의 절반도 못 덮었다는
  뜻이다. 표본 축 소스 혼합을 없앤 대가이며(§3-5), 혼합할 때는 다른 소스 값에
  섞여 보이지 않던 것이다. **D-25 실측 1순위.**
- `width_max_m` 이 교차로에서 46~57m 로 샌다. `min(B)` 라 판정 영향은 작지만
  필드 자체는 신뢰할 수 없다.
- `inherited` 는 더 이상 쓰지 않는다(항상 `false`).
- `road_side`(`RDS_DPN_SE` 0/1/2)는 **의미 미확정**이다. 폭과의 상관만 확인됐다.

```
골목의 49.5%(545구간)는 도면만으로 판정이 안 된다   → 주황·회색으로 표시한다
```

**새 D 번호를 만들지 않는다.** 남은 결정은 PLAN 에 절 번호로 쓴다.

### 10-1. 지금 어디까지 왔나

```
1단계  도면 프루닝     완료      ← 지금 지도에 보이는 색
2단계  영상판정        미착수    ← 호모그래피. 주황색이 여기서 갈린다
3단계  현장 실측       D-25      ← 레이저 거리계. 폭 값이 확정된다
```

**지금 색상은 최종 판정이 아니다.** 도면(공공 GIS 데이터)만으로 낼 수 있는
1차 분류이며, 그 단서는 화면 상단 `#warn` 이 유지한다.

### 10-2. 판정 4종

| 색 | 라벨 | 기준 | 뜻 |
|---|---|---|---|
| 초록 | 통행 가능 | 최소 폭 ≥ 7.0m | 양쪽에 주차가 있어도 통과. 영상판정 불필요 |
| 주황 | **판정 보류** | 그 사이 | **상습주차 여부로 갈린다. 영상판정 대상** |
| 빨강 | 통행 불가 | 최대 폭 < 3.0m | 중형펌프차 폭 미달. 장애물이 없어도 못 지나간다 |
| 회색 | 영상판정 불가 | — | CCTV 25m 밖. 카메라가 없어 못 본다 |

주황 191구간이 이 프로젝트의 미완성 부분이며 전체의 17.3% 다. 영상판정이
붙으면 이 191이 초록·빨강으로 갈린다. 회색 354는 영상판정으로도 안 갈린다 —
CCTV 배치가 선행돼야 한다.

★ **다섯 번째 색을 만들지 않는다.** `out_of_scope` · `conflict` · CCTV 사각
갈색 줄로 세 번 시도했고 세 번 다 지웠다. `web/config.js` 에서
`noCctvColor` 도 제거됐다. 되살리지 않는다.

### 10-3. 연속 구간 (`run_length_m`)

소방청 지정 기준의 "구간 100m 이상"은 세그먼트 하나가 아니라 같은 판정이
이어지는 **연속 구간 전체**의 길이다. 5m짜리 조각 하나로는 지정되지 않는다.

```
소방청 지정 기준 충족   158구간
연속 구간 최장          505.5 m
구간 길이               중앙 36.3m · 최대 282.1m · 100m 초과 52개
```

`nfa_designated` 가 참이면 툴팁에 표시된다.

### 10-4. 폭이 왜 두 개인가

같은 골목을 두 가지로 잰다. 하나로 못 정하는 게 아니라 **둘 사이가 답이기
때문**이다. 상세는 §3-4 에 있다.

> 이전에 쓰던 "노면폭 하한 / 담~담 상한"은 **최소 폭 / 최대 폭**으로 통일했다.
> 문서·UI·발표 자료 전부 이 표기를 쓴다.

### 10-5. 소방 동선 (`route_usage`)

**이 골목이 최단경로에 몇 번 등장하는가.** 119안전센터 2곳에서 동명동
건물출입구 358곳까지 최단경로를 전부 계산한 뒤 센 값이다.

```
1,101개 중 실제로 쓰이는 것        579개
출동 통행의 50%를 담당하는 골목     64개
출동 통행의 80%를 담당하는 골목    157개
```

★ **통행 가능성이 아니다**(§3-10). 선 굵기도 이 값이 아니다 — 선 굵기는
최소 폭이며 미터 단위로 그려지므로 확대·축소해도 실제 비율이 유지된다.

현재 지도 화면에서는 빼두었다. 필드는 데이터에 남아 있으므로 필요할 때 다시
꺼내 쓸 수 있고, 프루닝 근거로는 계속 유효하다.

### 10-6. 세그먼트 · 노딩 · 스코프

**세그먼트** = 교차로에서 잘라낸 도로 조각. 판정의 기본 단위다.
**노딩** = 통짜 도로선을 교차점마다 잘라 그래프로 만드는 것.

**스코프** = 동명동 + 접근 회랑 + 안전센터 반경 300m, 약 2.8 × 1.4km.
동명동만 보면 안 되는 이유는 119안전센터가 동 밖에 있어 출동 경로가 화면에서
잘리기 때문이다. **접근 회랑**은 광주 전체가 아니라 얇은 리본이다.

```
동명동      밝게        판정 대상
접근 회랑   살짝 어둡게  오는 길
그 밖       덮음        스코프 밖
```

이 범위 밖으로는 이동도 축소도 안 된다. 작업 범위가 구조적으로 고정된다.

### 10-7. 시설 마커

마커는 전부 **3D 입체**다. 2D 점은 기울인 화면에서 지면에 붙어 안 보인다.
원기둥 3~4개를 쌓아 실제 시설의 실루엣을 근사한다.

| 마커 | 색 | 형상 | 건수 |
|---|---|---|---|
| **119안전센터** 출동 시작점 | 빨강 | 기둥 + 헤드 + 첨두 | 2 |
| 동부소방서(본서) | 주황 | 본체 + 안테나 | 1 |
| 소화전 | 파랑 | 받침 + 몸통 + 플랜지 + 캡 | 11 (동명동 **1**) |
| CCTV | 노랑 | 지주 + 하우징 + 렌즈 + 간판 | 104지점 312대 |
| 가로등 | 회색+주황 | 지주 + 암 + 등기구. **굵기 = √(등 수)** | 46지점 573등 |
| 가로등 폴 | 회색 | 실제 폴 위치 | 1,143점 |

**비율은 실물을 따르되 크기는 약 5배 과장한다.** 소화전 실물은 0.9m 라 실제
치수로 그리면 1km 시야에서 점 하나가 되어 안 보인다.

CCTV 원본은 설치연도별로 행이 쪼개져 있어 좌표로 묶어 지점 단위로 집계했고,
`설치회차` 에 증설 횟수가 남는다. 촬영방면이 전부 360도라 방향 콘이 아니라
원으로 그린다.

## 11. UI 인수인계

★ 이 절은 **UI 담당이 작업 지시로 그대로 쓴다.** 구조를 바꿀 때 §11 을 같이
고치는 것을 기본 절차로 한다. 어긋나면 UI 가 없는 필드로 코드를 짜게 된다.

### 11-1. 30초 안에 띄우기

```bash
git checkout gis && git pull
uv run python tools/serve.py        # 캐시 없는 개발 서버
# http://localhost:8000
```

**`index.html` 을 더블클릭하면 빈 화면이 뜬다.** `file://` 에서는 `fetch()` 가
CORS 로 막힌다. 설치할 것은 없다. MapLibre 와 deck.gl 은 CDN 에서 온다.

### 11-2. 파일 구조 — 충돌이 경로로 갈린다

| 경로 | 주인 | 내용 |
|---|---|---|
| `web/style.css` | **@marscoolcat 단독** | 색·간격·타이포·애니메이션·레이아웃 |
| `web/index.html` | 공동 | 뼈대 마크업. 거의 안 바뀐다 |
| `web/config.js` | **공동** | 판정 색상·마커 스펙·카메라·출동모드·미니맵 |
| `web/js/` | @AIMasterFox | 로직·레이어 27개 모듈 |
| `web/js/icons/` · `ui/` | 공동 | 캔버스 그림 · 범례·검색·테마·토글 |
| `web/data/` | 생성물 | `publish_web.py` 산출. 손으로 고치지 않는다 |

**UI 작업은 `style.css` 와 `config.js` 두 파일이면 된다.** `web/js/layers/` 를
건드려야 하는 상황은 로직 문제이므로 GIS 담당에게 넘긴다.

`app.js` 는 없다. 1,260줄이던 그 파일은 `web/js/` 27개 모듈로 갈렸다.
모듈 구조는 `web/README.md` 가 정본이다.

### 11-3. `config.js` — UI 담당이 조정하는 값

**마커에 관한 모든 것이 `config.js` 한 곳**에 있다. `web/js/` 는 이 선언을
읽어 실행만 한다.

```js
verdict: {
  blocked : { color:[255, 77, 61], lightColor:[224, 53, 38], label:"통행 불가",  desc:"…" },
  needs_cv: { color:[255,171, 46], lightColor:[212,124, 10], label:"판정 보류",  desc:"…" },
  clear   : { color:[ 74,209,143], lightColor:[ 26,150, 96], label:"통행 가능",  desc:"…" },
  unknown : { color:[ 90, 98,114], lightColor:[110,120,138], label:"영상판정 불가", desc:"…" },
},

reason  : { no_cctv_band, no_cctv_thin, no_cctv_narrow, no_cctv_single },  // 툴팁 문구
cctvCov : { colorDark:"#ffd24a", colorLight:"#d69600", opacityDark:0.42, opacityLight:0.30 },

dispatch: { clearWidthScale:1.6, dimAlpha:102, pulseMs:1200 },  // 출동 모드
minimap : { showFromZoom:16 },
terrain : { enabled:true, exaggeration:1.0 },
markers : [ … ],
```

★ `color` 는 다크 모드용, `lightColor` 는 라이트 모드용이다. 다크용 색은 검은
배경에 올리려고 밝고 채도 높게 고른 것이라 흰 배경에 그대로 쓰면 대비는
떨어지고 채도만 남는다.

#### 마커 스펙 — 한 덩어리가 자기 것을 전부 든다

```js
{ id:"m-light",              // 레이어 식별자. 토글 data-t 와 같은 값
  label:"가로등",             // 범례·토글에 뜨는 이름. 여기가 정본
  data:"streetlights",       // web/data/{이름}.geojson 을 자동으로 읽는다
  kind:"center",             // (선택) 같은 파일에서 properties.kind 로 거를 때

  scale:{ by:"n_lights", mode:"sqrt", k:0.28 },   // (선택) 값에 따라 굵기
  cover:{ by:"pos_accuracy_m", style:"dashed", color:"#ffd678" },  // (선택) 반경 원
  sign :{ draw:"cctv", top:13.0 },                // (선택) 간판. draw 는 icons/ 이름
  popup: p=>`<b>가로등</b> ${p.n_lights}등`,       // (선택) 클릭 팝업. 여기가 정본

  parts:[ {r:0.35, z:0, h:11, c:[120,124,138]}, … ] }   // 3D 형상. z=바닥, h=높이
```

**마커를 추가하려면 두 곳이면 된다** — 데이터를 `web/data/{이름}.geojson` 으로
발행하고(GIS 담당), `config.js` 의 `markers` 에 스펙 한 덩어리를 넣는다.
토글 행·팝업·데이터 로딩은 `web/js/` 가 선언을 읽어 자동으로 만든다.

강제자 — `tests/test_contract.py::test_marker_spec_self_contained` 가 손딕셔너리
(`MK_SRC` · `POPUP`)나 마커 id 특수분기의 부활을 막는다.

#### 굵기와 원의 뜻

```
scale mode:"sqrt"   반지름 ∝ √값. 면적이 값에 비례해 보인다
CCTV  cover 실선    "이 범위를 본다"           radius 25m
가로등 cover 점선    "폴이 이 안 어딘가에 있다"  by pos_accuracy_m (50m)
```

★ **등 수를 높이로 표현하지 않는다.** 가로등 41등을 높이로 그리면 "41층짜리
가로등"이 되어 시설 위계가 무너진다. 원의 의미가 정반대이므로 선 종류로
구분하고 범례에도 같은 구분을 적는다.

**임계값(3.0 / 7.0 / 25.0)의 정본은 `src/firelane/seg/params.py` 다**(§18-5 R3).
`config.js` 의 같은 숫자는 화면 설명용 사본이라 바꿔도 판정은 안 바뀐다.

### 11-4. 값은 바뀌고 구조는 안 바뀐다

폭 값은 아직 **미검증** 상태이고(`width_verified: false`) 실측 후 일부 구간의
`verdict` 가 바뀐다. 그때 UI 를 다시 만들지 않으려면 셋만 지키면 된다.

**1. 숫자가 아니라 `verdict` 문자열로 분기한다**

```js
if (p.verdict === "blocked") …     // 이렇게
if (p.width_max_m < 3.0)  …        // 이러면 안 된다
```

**2. 색 매핑은 `config.js` 한 곳에만 둔다**

**3. `verdict` 는 네 개가 전부다**

| 항목 | 보장 |
|---|---|
| 좌표계 | `EPSG:4326` 고정 |
| 필드명·타입 | 고정 |
| `verdict` 어휘 | 4종 고정 |

깨지면 CI 에서 머지가 막힌다.

## 12. 협업

브랜치는 `gis` 하나가 정본이다. 각자 작업 브랜치를 파서 PR 로 합친다.

```
gis ─────────────────────── 정본. 여기가 항상 동작해야 한다
 ├ gis-*   오창준 (@AIMasterFox)   데이터·판정·경로
 └ ui/*    우지혜 (@marscoolcat)   화면·3D
```

★ `gis/*` 는 `gis` 브랜치와 ref 충돌로 생성 불가하다. `gis-*` 를 쓴다.
`gis` 는 보호 브랜치이며 직푸시가 막힌다 — **오창준도 PR 이 필요하다.**

### 12-1. 하루 흐름

```bash
git checkout gis && git pull
git checkout -b ui/오늘작업이름          # 또는 gis-오늘작업이름
git add -A && git commit -m "ui: 판정 색상 대비 조정"
git push -u origin ui/오늘작업이름
```

미완성이면 Draft PR 로 열어둔다. **하루 안에 머지하고 브랜치를 지운다.**
브랜치가 오래 떠 있으면 같은 파일이 양쪽에서 바뀌어 충돌이 커진다.

매일 푸시를 권장하는 이유는 셋이다 — 로컬에만 있는 작업은 없는 것과 같고,
상대가 뭘 하고 있는지 보여야 하고, CI 가 매번 돌아 계약이 깨졌는지 즉시 안다.
완성해야 푸시하는 게 아니라 **동작하는 지점마다 푸시한다.**

### 12-2. 커밋 메시지

```
gis:  데이터·파이프라인·판정
ui:   화면·스타일·인터랙션
docs: 문서
fix:  버그
```

한 줄이면 충분하다. 무엇을 왜 바꿨는지만 남긴다.

### 12-3. 자동으로 도는 것

| 워크플로 | 시점 | 하는 일 |
|---|---|---|
| `contract` | `main` · `gis` 로 push · PR | 계약·위생·문서 검사. 깨지면 머지 차단 |
| `pages` | `main` · `gis` 의 `web/**` 변경 | GitHub Pages 갱신 |

★ **두 워크플로의 브랜치 목록이 같아야 한다.** 배포되는 브랜치가 검사되지
않으면 검사를 비껴간 코드가 그대로 공개된다.
강제자 — `tests/test_guards.py` 의 트리거 대조

CI 가 데이터를 다시 만들지는 **않는다.** `data/raw` 가 저장소에 없기 때문이다.
파이프라인은 GIS 담당 로컬에서만 돈다.

### 12-4. 충돌이 나면

거의 안 난다. 파일이 갈려 있다. `web/data/` 에서 충돌이 나면 손으로 풀지 않는다.

```bash
git checkout --theirs web/data/      # gis 쪽을 취한다
uv run fire-lane --only publish      # 또는 재생성
```

### 12-5. 락이 3중인 이유

| 층 | 막는 것 | 한계 |
|---|---|---|
| `.gitignore` · `tools/commit_policy.py` | 산출물·비밀값 커밋 | 훅을 안 걸면 로컬에서는 안 돈다 |
| `.github/CODEOWNERS` | 코어 무단 수정 | 리뷰 강제일 뿐, 승인하면 통과 |
| **계약 테스트** | **구조 파괴** | **실제로 막는 건 이것** |

CODEOWNERS 는 "누가 봐야 하는가"를 정하고, 계약 테스트는 "무엇이 깨지면 안
되는가"를 정한다. 후자가 본체다. 브랜치 보호 규칙에서
`Require review from Code Owners` 를 켜지 않으면 CODEOWNERS 는 효력 없는
텍스트 파일이다.

### 12-6. 데이터를 저장소에 넣는 기준

| 경로 | git | 이유 |
|---|---|---|
| `data/raw/` | ✗ | 저장소 밖. 재취득 가능 |
| `data/processed/*.gpkg` · `*.tif` | ✗ | 재생성 가능 |
| `data/processed/segments.geojson` | ✓ | 재생성에 raw 가 필요하다 |
| `data/processed/segments.schema.json` · `_manifest.json` · `seg_uid_map.csv` | ✓ | 재현성 기록 |
| `data/field/` | ✓ | 재생성 불가. 사람이 만드는 유일한 데이터 |
| `web/data/` | ✓ | UI 담당이 raw 없이 작업할 수 있어야 한다 |

`web/data` 는 **40MB 상한**이다. 세 곳이 같은 값을 본다 —
`.github/workflows/contract.yml` · `tools/commit_policy.py` ·
`pipeline.WEB_MAX_MB`. 현재 28.7MB 다.
강제자 — `tests/test_guards.py::test_webdata_limit_is_one_number`

### 12-7. 한글 파일명

`docs/기획서_Fire-Lane.docx` 가 윈도우/리눅스를 오가면서 삭제 + 미추적으로
갈린 적이 있다. git 이 한글 파일명을 escape 로 저장하는데 두 OS 의 정규화
방식이 다르기 때문이다.

```bash
git config --global core.quotepath false
git config --global core.precomposeunicode true
```

`git status` 에 `#Uae30#Ud68d...` 같은 것이 뜨면 이 설정이 안 된 것이다.
**앞으로 새로 만드는 파일은 영문 파일명을 쓴다.**

## 13. 봉인 베이스라인

원본이 소실돼 재생성 불가가 된 산출물, 그리고 판정이 바뀌기 직전의 상태를
`data/baseline/<태그>/` 에 봉인한다. 재생성 가능한 것은 봉인하지 않는다 —
전량 재실행이 약 285초이고, raw + 코드 + 대장이 있으면 결정론적으로 나온다.

| 태그 | 무엇 | 판정 |
|---|---|---|
| `20260814-ngii-ngi20` | 구 원본(국토정보플랫폼 NGI 20도엽)으로 낸 마지막 산출 | 재생성 불가 |
| `20260818-pre-btfix` | `ROAD_BT` 예외를 CCTV 강등보다 앞세우기 직전 | 재생성 가능 |
| `20260824-pre-nreg` | `verdict` 가 시도표본 대신 정규표본을 받도록 고치기 직전 | 재생성 가능 |

```bash
uv run python tools/baseline.py diff 20260814-ngii-ngi20
uv run python tools/baseline.py diff 20260824-pre-nreg
```

각 태그의 `meta.json` 이 그 시점의 판정 분포·git sha·sha256 을 든다.
구 원본 대비 `seg_uid` 유지율은 99.1% 이고 총연장은 변하지 않았다.

★ **봉인은 백업이 아니다.** 백업은 소실 대비이고 봉인은 **전이 대조용**이다.
"판정이 왜 달라졌는가"에 답하지 못하는 산출물 변경은 받아들이지 않는다.

## 14. 실행

### 14-1. 받자마자 한 번

```bash
uv sync
git config core.hooksPath .githooks   # 커밋 시점 방어. 클론 후 1회
export FIRE_LANE_DATA="<raw 상위 폴더 경로>"
```

`uv pip install -e .` 은 치지 않는다. `[build-system]` 이 있으므로 `uv sync` 가
editable 로 알아서 깐다.

### 14-2. 파이프라인은 한 명령이다

```
ingest → segments → streetlight → terrain → ortho → publish → 계약 테스트 → 지문 대조
```

```bash
uv run fire-lane                     # 전체
uv run fire-lane --check             # 실행 없이 상태만
uv run fire-lane --from segments     # 그 단계부터 끝까지
uv run fire-lane --only publish
```

★ **`uv run` 을 빼면 `command not found` 다.** 진입점은 `.venv/bin/fire-lane`
에 설치되고 그 폴더는 PATH 에 없다. `uv sync` 가 editable 로 깔아주지만
셸에 노출하지는 않는다.

**단계를 하나씩 손으로 치지 않는다.** 순서가 중요하고 빠뜨리기 쉽다 —
`terrain` 을 건너뛰면 지형이 안 뜨고, `publish` 를 건너뛰면 지도가 옛 데이터를
본다. `--only` · `--from` 으로 일부만 돌리면 하류가 낡으므로 파이프라인이
무엇을 다시 돌려야 하는지 알려준다.

단계 모듈(`python -m firelane.ingest` 등)은 **파이프라인이 부르는 대상이지
사람이 치는 명령이 아니다.** 직접 부르면 대장은 갱신되고 계보 기록은 빠져
다음 실행이 교착한다.

전량 재실행 약 285초. 몇 번을 돌려도 결과가 같고, 두 번째부터는 캐시가 걸린다.

### 14-3. 원본을 새로 받으면

```bash
uv run python tools/acquire.py                  세 판정만 (아무것도 안 옮긴다)
uv run python tools/acquire.py --stage --yes    landing → raw 편입 + sha 기록
uv run python -m firelane.normalize_raw <다운로드폴더> --dry-run
python -m firelane.contract                     대장 선언 ↔ raw 실물 대조
```

### 14-4. 검사

```bash
bash tools/verify.sh          # 전부. 실패해도 끝까지 돌고 표로 보여준다
bash tools/verify.sh --fast   # 파이프라인 전량 생략
```

`verify.sh` 는 의존성 동기화 · 패키지 import · 진입점 · pytest · 계층 · ruff ·
CI 환경 재현 · 커밋 정책 · 인코딩 · 문서 숫자 · web/data 계보 · 로컬 찌꺼기 ·
web/data 용량 · JS 문법·순환 · JS 부팅 · 파이프라인 전량 · golden 지문을 밟는다.

```bash
uv run python tools/ship.py              # 내보내기 전 검사만
uv run python tools/ship.py --fix --push # 정리 + 검사 + push
```

```
verify.sh   코드가 도는가
ship.py     내보내도 되는가 (위 + 문서 4축 + 위생 + git 상태)
```

`ship.py` 가 `verify.sh` 를 부르므로 중복이 없다. CI 가 지금 브랜치를
감시하는지도 확인하므로 검사 없이 머지되는 일이 없다.

머지 뒤 로컬 찌꺼기는 `uv run python tools/tidy.py --yes` 로 정리한다.
죽은 upstream · 머지된 브랜치 · 백업 폴더 · 캐시를 본다.
**데이터 계층은 건드리지 않는다** — `raw` · `norm` · `field` · `web/data` 는
`NEVER` 로 막혀 있고 규칙에 실수로 넣어도 안 지워진다.

★ **마지막 하나는 사람이 봐야 한다.** WebGL 렌더링은 스크립트가 못 본다.
지도가 실제로 그려지는지, 판정 색·표지판·미니맵·검색이 눈으로 멀쩡한지는
`tools/serve.py` 로 직접 확인한다.

### 14-5. 대조 도구 — 아무것도 안 바꾼다

읽고 표를 내거나 페이지를 만들 뿐이라 golden 지문에 영향이 없다.

```bash
uv run python tools/width_fn.py         폭을 함수 w(s) 로 — min 대 통과폭
uv run python tools/jijeok_probe.py     연속지적도(세 번째 계보)로 폭 대조
uv run python tools/jijeok_review.py    갈리는 구간을 정사영상 위에서 판정
uv run python tools/lanes_probe.py      표준노드링크 차로수로 폭 하한 대조
uv run python tools/route_probe.py      소방차 통행 비용으로 경로 — 거리만 대 차량
uv run python tools/clearance_probe.py  최대내접원 방식 (2026-08-22 기각)
uv run python tools/corner_probe.py     코너 꺾임각·반경 — 회전 가능성 대조

uv run python tools/wmax_audit.py       width_max_m 결손이 판정에 미치는 규모

uv run python tools/naver_check.py      네이버 지도 준-실측 표본 + 봉인
```

**측정하고 대조한 뒤에 판정을 바꾼다.**

### 14-6. 진단 스위치

`/tmp` 일회성 스크립트를 만들지 않는다. 진단 도구는 저장소에 있다.

않는다.**

지형 표현에 `exaggeration` 을 1.0 이외로 올려 캡처했다면 그 사실을 캡션에 적는다.

### 16-1. `CCTV_RANGE` 는 거리 상수가 아니라 촬영 기하의 함수다

`unknown` 354구간(전체의 32%)의 사유가 전부 CCTV 사각이고, 그 경계가
`CCTV_RANGE = 25.0` 한 줄이다. 이 값에는 근거가 없다.

**전제부터 틀려 있다.** 이 상수를 "기존 CCTV 인프라까지의 거리"로 읽어왔는데,
영상판정은 **직접 삼각대를 세우고 찍는다.** 그러면 유효 범위를 정하는 것은
카메라 제원이 아니라 **높이와 부각**이다.

    GSD_지면 = R² · IFOV / h        R = √(h²+d²) · h = 카메라 높이

**거리 제곱에 비례하고 높이에 반비례한다.** 지배 요인은 부각이고 `1/sinθ`
배율이 낮은 각도에서 폭발한다 — 30° 에서 ×2.0, 10° 에서 ×5.8, 5° 에서 ×11.5.

광각 70° · 1920px 기준으로 폭 오차가 0.3m(3.0m 임계가 뒤집히는 크기)를 넘는
수평거리는 이렇다.

    h = 1.5m  →  11.0m       (부각  7.8°)
    h = 2.5m  →  14.0m       (부각 10.1°)
    h = 4.0m  →  17.5m       (부각 12.9°)
    h = 10.0m →  26.5m       (부각 20.7°)

**25m 는 두 번 틀렸다.** 삼각대 1.5m 로는 11m 가 한계라 너무 넓고, 높이를
올리면 늘어나므로 너무 좁다. 단일 상수로는 못 잡는다.

한편 CCTV 최단거리 중앙값은 39.3m 이고, 임계를 60m 로 열면 `unknown` 이
354 에서 139 로 줄어든다. 이 상수 하나가 215구간의 운명을 쥐고 있다.

★ **그럼에도 실측 전에는 바꾸지 않는다.** 위 계산은 광학 상한이고, 실제로는
지면 평면 가정 · 세그멘테이션 경계 흔들림 · 캘리브레이션 오차 · 가림이 더 크다.
**계산으로 예상한 값을 그대로 상수에 박으면 그 순간 근거 없는 상수가 하나 더
생긴다.** 실측 설계와 촬영 계획은 PLAN §1-23 · §1-24 에 있다.

재현 — 위 공식과 `web/data/cctv.geojson` 의 제원으로 계산한다. 전용 도구는 두지 않는다.

### 16-2. 근거 없는 상수

| 상수 | 값 | 상태 |
|---|---:|---|
| `CCTV_RANGE` | 25.0 | 354구간의 판정을 가른다. §16-1 |
| `WMAX_CAP` | 60.0 | ★ 주석에는 40m 로 적혀 있다. 문서-코드 불일치 |
| `SNAP_MAX` | 6.0 | 눈대중 |
| `MIN_SEG_LEN` | 3.0 | 눈대중 |

`XSEC_EXCL 5.0` 은 2026-08-17 에 해소됐다. `A0080000` 평면교차점 2,025개
실형상으로 대체된 것이며, **근거 없는 상수가 실제 데이터로 교체된 첫 사례**다.
나머지 넷도 같은 길을 찾는다.

`SNAP_TRUST` · `COV_MIN` 에는 근거가 붙어 있다. **상수만 보면 눈대중처럼
보이지만 근거가 붙어 있으면 함부로 못 건드린다.**

## 18-1. 계층

★ **정본은 `sources.yaml` 의 `layers` 블록이다.** 이 절은 그것을 가리키기만
한다. 표를 여기 두면 세 번째 정본이 된다.

    sources.yaml layers    정책. base · required · mutable · committed ·
                           backup · regenerable · naming · status
    src/firelane/paths.py  경로 해석. 환경변수를 탄다(기계마다 다르다)
    src/firelane/layers.py 둘을 이름으로 묶는다
    datalog fsck           선언과 실물을 대조한다

```bash
uv run python -m firelane.datalog fsck
```

### 계층이 여덟인 이유

| 계층 | 왜 있나 |
|---|---|
| `landing` | 다운로드 원본. 규칙 없이 던져두는 곳이 하나는 필요하다 |
| `raw` | 받은 그대로. 인코딩조차 고치지 않아야 원본이 원본이다 |
| `norm` | 형식만 통일. **미구현** — 선언의 `status` 가 그것을 밝힌다 |
| `interim` | 탐색·대조 산출물. 대장에 없고 지워도 된다 |
| `processed` | 파이프라인 정본. 손으로 만들지 않는다 |
| `field` | 실측 원자료. 사람이 만드는 유일한 데이터 |
| `quarantine` | 대장에 없는 파일. 판단 보류지 폐기가 아니다 |
| `web` | 표출용. UI 담당이 raw 없이 작업해야 한다 |
| `golden` | 판정 불변 증명. 재생성 불가라 저장소 안에 둔다 |
| `baseline` | 봉인 스냅샷. 실행 간 판정 전이를 대조한다 |

`base` 가 둘뿐인 것이 요점이다 — `data`(SSD)냐 `repo`(저장소 안)냐.
그것이 곧 **"이 계층이 왜 거기 있나"** 의 답이다.

**계층이 없으면 파일은 아무 데나 떨어진다.** 규율이 아니라 구조의 문제다.

### 18-1a. 그라운드 룰

**R2. 재생성 가능성이 `.gitignore` 의 근거다**

산출물을 제외하는 이유는 단 하나 — **한 명령으로 다시 만들 수 있어서**다.
재생성이 안 되는 파일을 ignore 하면 그 파일은 사실상 소실된다.
**ignore 목록에 넣기 전에 파이프라인으로 재생성되는지 먼저 확인한다.**

**R3. 등록되지 않은 데이터는 없는 데이터다**

`sources.yaml` 에 항목이 없으면 파이프라인이 모른다. raw 폴더에 있어도 없는
것이다. 새 데이터를 받으면 **파일을 옮기기 전에 대장부터 쓴다.**

**R4. `feeds` 를 못 채우면 raw 에 둘 이유가 없다**

모든 항목은 `feeds`(어느 산출물의 입력인가)를 갖는다. 채울 수 없으면
`kind: raw_only` + `feeds: 미투입 — <언제 쓸지>` 로 명시한다.
**문제는 데이터를 모은 데서 안 나오고 안 치운 데서 나온다.**
강제자 — `tests/test_guards.py::test_every_dataset_says_where_it_is_used`

## 18-2. 파일명 규칙

### 18-2a. raw

원본 파일명을 그대로 둔다. 대신 **폴더**로 구분한다.

```
juso     도로명주소(주소기반산업지원)     its      국가교통정보센터
ngii     국토정보플랫폼                  vworld   브이월드
safety   공공데이터포털(안전)             gjcity   공공데이터포털(광주 동구)
sbiz     공공데이터포털(소상공인)         eais     건축HUB
```

★ `ngii` 와 `vworld` 를 나눈다. 같은 수치지형도라도 **원천이 다르면 폴더가
다르다.** 섞으면 어느 판인지 파일명만으로 구분되지 않는다.

```
data/raw/{제공기관}/{download_date}/{원본파일명 그대로}
```

원본 파일명을 안 바꾸는 이유는 제공기관 문의나 재다운로드 때 대조가 안 되기
때문이다. 한글·괄호·공백이 있어도 그대로 둔다. 어차피 코드가 직접 열지 않는다.

### 18-2b. norm 이후 — 여기서 규칙을 강제한다

```
{dataset_key}_{region}_{vintage}_{crs}_v{n}.{ext}

ngii1k_gwangju-donggu_2026q2_5186_v1.gpkg
streetlight_gwangju-donggu_2025_4326_v1.csv
```

| 토큰 | 규칙 |
|---|---|
| `dataset_key` | `sources.yaml` 의 키와 **문자열까지 동일**. 다르면 대장이 무의미해진다 |
| `region` | 소문자 로마자, 하이픈. 한글·공백 금지 |
| `vintage` | 데이터 기준 시점. 다운로드 날짜가 아니다 |
| `crs` | EPSG 숫자만. **이게 제일 자주 나는 사고이기 때문에 파일명에 박는다** |
| `v{n}` | 같은 소스를 다시 받았을 때 증가. 덮어쓰지 않는다 |

**금지** — 한글, 공백, 대문자, `final`, `최종`, `수정본`, `real_final2`.
`v{n}` 이 있는데 `final` 을 쓰면 어느 쪽이 최신인지 모른다.

### 18-2c. 확장자 정규화

| 원본 | → | 이유 |
|---|---|---|
| `.shp` (+dbf/shx/prj) | `.gpkg` | 4파일 세트라 하나만 빠져도 못 읽는다 |
| `.xlsx`, `.xls` | `.csv` (UTF-8) | 수식·서식이 값처럼 읽힌다. diff 가 안 된다 |
| `.csv` (cp949) | `.csv` (UTF-8, BOM 없음) | **인코딩은 norm 에서 한 번만 처리한다** |
| `.json` (좌표 포함) | `.geojson` | 도구가 공간 데이터로 인식 |
| `.tif` (미압축) | `.tif` (COG, DEFLATE) | 타일이 통째로 메모리에 안 올라간다 |

★ **인코딩 변환은 값 변경이 아니라 형식 변경이다.** 그래서 norm 에서 허용한다.
결측 처리, 컬럼명 변경, 좌표 변환은 **값 변경**이라 norm 에서 금지하고
`interim` 이후로 미룬다. 이 선을 흐리면 "원본이 뭐였는지" 추적이 끊긴다.

## 18-3. 대장 — `sources.yaml` 하나

사람이 손으로 쓰는 대장은 이것 하나다. 사이드카 `.meta.json` 도, 스크립트 주석
메타데이터도 쓰지 않는다. **손대장이 둘이 되는 순간 반드시 어긋난다.**

```yaml
datasets:
  ngii1k:
    title: 1:1,000 수치지형도 도로경계
    provider: 브이월드 · 국토정보플랫폼
    license: 공공누리 제1유형
    vintage: 2026q2
    acquired: 2026-08-17
    crs_native: 5186          # 선언 근거를 함께 — prj/xml 명시 vs 추정
    kind: shp_dir
    what: 74 + 143도엽 병합. 도로경계 폴리곤. 폭 산출 주 소스
    feeds: [segments]
    used_for: [width_primary]
    caveats:
      - 도엽 경계에서 폴리곤이 끊긴다. 병합 후 노딩 필요
      - 실폭도로와 정의가 다르다(경계면 vs 노면). 대조 시 주의
    refresh: 연 1회
    verified: false

outputs:
  segments:
    produced_by: src/firelane/segments.py
    path: data/processed/segments.geojson
    inputs: [ngii1k, ngii_road, road_rw, building, boundary_emd, cctv]
    stable_key: seg_uid
    consumers: [web, src/firelane/publish_web.py, tests/test_contract.py]
    verified: false
    known_issues:
      - 폭 실측 검증 0건. 소방서 7구간 대조는 게이트로 썼으므로 검증이 아니다
```

### 18-3a. 필드의 의무

| 필드 | 없으면 생기는 일 |
|---|---|
| `what` | 3개월 뒤 이 파일이 뭔지 아무도 모른다 |
| `used_for` / `consumers` | 소스 하나 바꿀 때 뭐가 깨지는지 모른다 |
| `caveats` | 같은 함정에 두 번 빠진다 |
| `crs_native` | 좌표계 사고. 이 프로젝트에서 이미 겪었다 |
| `verified` | 미검증 값이 검증된 값처럼 쓰인다 |
| `feeds` | 못 채우면 raw 에 둘 이유가 없다(R4). 안 치운 소스가 쌓인다 |
| `license` | 발표·공개 때 막힌다 |

★ `juso` 전자지도는 도로명주소법 시행령 제46조 **심사 승인** 데이터다 —
승인 당사자의 사용과 제3자 재배포는 다르다. 퍼블릭 버킷·공개 저장소에
올리지 않는다.

## 18-3b. 계약 — 사람을 언제 부르는가

대장에 **기대를 선언**하고, 어긋날 때만 사람을 부른다.

```yaml
ngii1k:
  contract:
    crs:      5186
    layers:   [A0010000, A0020000, A0033320, A0080000, C0220000]
    fields:
      A0020000: [도로폭, 일방통행, 차로수, 도로명]
    rows_min: {A0020000: 400}

```

```
계약 일치              통과. 로그만 남긴다. 사람 개입 0
컬럼 추가              통과 + 알림
컬럼 소실 · 타입 변경   ★ 중단. 합의 필요
건수 ±30% 초과         ★ 중단. 합의 필요
CRS 변경               ★ 중단. 무조건
```

## 18-4. 매니페스트 — 사람이 안 쓰고 파이프라인이 쓴다

`data/processed/_manifest.json` 이 매 실행의 원본 sha256 · 건수 · 상태를
축적한다. `web/data/_manifest.json` 은 `publish_web.py` 가 직접 쓴다.

- `git_dirty: true` 로 만들어진 산출물은 **재현 불가**다. 커밋 안 한 채로 돌린
  결과가 발표 자료가 되는 것을 막는다.
- `input_shas` 가 있으면 "이 산출물이 어느 버전의 입력으로 나왔는가"가 남는다.
  입력이 바뀌었는데 산출물이 안 바뀌었으면 파이프라인이 안 돈 것이다.
- `params` 를 박는 이유는 임계값을 바꾼 뒤 옛 산출물과 비교할 때 어느 쪽이
  어떤 임계로 나왔는지 알아야 하기 때문이다.

★ **`generated_at` 은 "마지막 실행 시각"이 아니라 "내용이 마지막으로 실제
달라진 시각"이다.** 두 매니페스트는 커밋되는 파일이라, 매 실행 시각만 바뀌면
검사를 한 번 돌릴 때마다 워킹트리가 더러워지고 `git checkout` 이 막힌다.
`src/firelane/manifest.py::write_stable` 이 시각을 뺀 내용을 대조해 같으면
아예 쓰지 않는다. 시각을 지우는 것이 아니라 **안 바뀌었을 때 갱신하지 않는
것**이며, 재현성 기록으로는 이쪽이 옳다.
강제자 — `tests/test_guards.py::test_manifest_write_is_idempotent` ·
`test_manifest_writers_go_through_write_stable`

**R1. 스크립트는 입력과 출력을 상단에 선언한다**

```python
"""
segments.py — 도로 중심선 + 폭 → 구간 판정

IN    norm/ngii1k_*.gpkg · norm/building_*.gpkg · processed/cctv_5186.gpkg
OUT   processed/segments_5186.gpkg · processed/segments.geojson
PARAM TRUCK=3.0 PARK=2.0 CCTV_RANGE=25.0
"""
```

**R2. 파라미터는 전부 파일 상단 대문자 상수. 함수 안에 숫자를 쓰지 않는다**
`if w < 3.0` 이 함수 중간에 박히면 임계 변경이 누락된다.

**R3. 상수를 옮길 때는 정본을 하나만 둔다**
`config.js` 의 3.0/7.0/25.0 은 **표시용 사본**이고 정본은 `seg/params.py` 다.

**R4. 랜덤이 들어가면 시드를 파일 상단에 고정하고 매니페스트에 기록한다**
시드 없는 표본 설계는 표본 설계가 아니다.

**R5. 단계 스킵은 캐시로 하되 캐시 키에 입력 sha 를 넣는다**
`if out.exists(): return` 은 금지다. 입력이 바뀌어도 안 돈다 — 즉 낡은 산출물을
새것이라고 주장하게 된다.

**R6. 실패는 조용히 넘기지 않는다**
대체가 일어났다는 사실이 **산출물에 남아야 한다.** `width_src` 컬럼이 그
역할을 하고, 매니페스트의 `warnings` 에도 쌓는다. 콘솔은 사라진다.

**R7. 새 파생 컬럼은 스키마에 동시에 추가한다**
컬럼 집합과 스키마 키 집합이 **정확히 같아야 한다.** 부분집합 검사로는
processed 전용 필드가 웹 필드처럼 서술되는 것을 못 잡는다.

**R8. 일회성 스크립트는 돌리고 지운다. 날짜를 파일명에 박지 않는다**
적용 뒤에는 no-op 이고, 앵커가 깨지면 재실행조차 불가능하다. 남길 값이 있으면
**이유만** `DECISIONS.md` 로 옮긴다.

**R9. 소스는 직접 고쳐서 커밋한다. 고치는 스크립트를 커밋하지 않는다**
문자열 치환 패처는 git 이 이미 수행하는 일의 열등한 사본이다. 실제 코드가
어디 있는지 두 곳이 되고, 리뷰어가 diff 대신 문자열 쌍을 읽어야 한다.

**R10. 취득 범위가 스코프를 덮는지는 따로 센다**
건수·컬럼·CRS·인코딩이 전부 맞아도 공간이 안 맞을 수 있다. 행정구역 단위
취득이 공간 스코프를 보장하지 않는다(§6-3).

**R11. 코드를 옮길 때는 산출물이 같다는 것을 증명하고 옮긴다**
`baseline.py` 는 *소스가 바뀌었을 때* 판정이 어떻게 달라졌나를 본다.
`golden.py` 는 반대로 *아무것도 달라지면 안 되는 상황*에서 쓴다. 리팩 시작 전에
`lock`, 한 덩어리 옮길 때마다 `check`. 다르면 그 자리에서 되돌린다.

**R12. 방어를 넣을 때는 그 방어가 실패하는 경로도 한 번 태워본다**
계약 테스트도 golden 도 **성공 경로의 산출물**만 보므로 방어의 실패 경로에
있는 `NameError` 같은 것을 못 잡는다.

**R13. 계보 검사는 key 가 아니라 파일 단위로 한다**
한 key 가 여러 파일을 낸다. key 만 보면 그중 하나가 옛 실행 것으로 남아도
통과한다. `_manifest.json` 의 `outputs` 목록과 디스크를 대조한다.

**R14. 한 항목은 한 문서에만 산다**

    PLAN(미래)  →  도래  →  MASTER(현재)  →  회고  →  DECISIONS(과거)

두 곳에 있으면 생애주기 단계가 둘인 셈이고, 한쪽만 고치는 날이 온다.
남은 일 목록은 `PLAN §1` 하나뿐이고, MASTER §7 은 "현재 산출물의 한계"만 적는다.

**R15~R18. 문서도 코드처럼 어긋남을 검사한다**
문서가 낡는 것을 사람의 성실성에 맡기면 반드시 낡는다. 없앨 수 없는 중복이라면
최소한 어긋남은 잡는다.

**R19. 문체와 절 번호도 검사 대상이다**
어미만 기계 치환하면 활용이 깨진다. 같은 번호가 두 곳을 가리키면 인용이
성립하지 않는다. 두 가지 다 사람 눈으로는 오래 안 보인다.

## 18-6. 메타데이터를 어디에 붙이나

| 형식 | 메타 부착 | 방식 |
|---|---|---|
| GeoPackage | **가능** | `gpkg_metadata` 테이블 |
| GeoParquet | **가능** | 파일 헤더 key-value. 권장 |

| CSV | 불가 | → 매니페스트로 |

```
기계가 쓰는 것        _manifest.json        전부. 자동으로
파일에 박히는 것      gpkg / parquet 헤더    자동으로 (매니페스트와 동일 내용)
```

파일에 박는 게 필요한 이유는 **파일이 저장소 밖으로 나갈 때** 매니페스트가
안 따라가기 때문이다. `.gpkg` 하나를 받았는데 좌표계와 출처를 모르면 그 파일은
쓰레기다.

## 18-8. 백업

```
1벌  작업 노트북 (git + 로컬 디스크)
2벌  외장 SSD    (raw + field + processed 전체)
검증 sha256 매니페스트 대조
```

3-2-1 은 이 규모에 오버다. **2벌 + 검증**이면 된다. 핵심은 벌수가 아니라
**검증**이다. 원본을 날렸을 때 문제는 백업이 없어서가 아니라 백업이 깨진 걸
몰랐던 것이다.

- `raw` 와 `field` 는 **매 실측 당일** 백업한다. 다시 못 만드는 데이터다
- `processed` 는 주 1회. 재생성 가능하지만 재생성에 시간이 든다
- **월 1회 복원 훈련.** 복원해 본 적 없는 백업은 백업이 아니다

### 백업과 기기 간 이동은 다르다

**SSD 를 이동 수단으로 쓰면 단일 장애점이 된다.** 이동은 **축소본을 각 기기에
복제**하는 것으로 대신하고, 동일성은 파일을 옮겨서가 아니라 해시로 본다.
전국판을 들고 다니지 않는다 — 광주 축소 시 645MB 가 약 70MB 가 된다.
축소 후 파이프라인을 재실행해 산출물이 동일한 것을 확인하고 나서 교체한다.

## 18-9. DB 확장

지금은 파일로 충분하다. 옮길 시점은 **네비 API 가 붙을 때**다.
`sources.yaml` 이 곧 DDL 이 되도록 설계한다.

```sql
CREATE SCHEMA core;      -- 파이프라인 산출. 읽기 전용
CREATE SCHEMA field;     -- 실측. 사람이 쓴다
CREATE SCHEMA serving;   -- API 노출. core+field 의 뷰

CREATE TABLE core.segment (
  seg_uid      TEXT PRIMARY KEY,        -- ★ seg_id 가 아니다
  run_id       BIGINT REFERENCES core.run(run_id),
  geom         geometry(LineString, 5186),
  width_min_m  REAL, width_max_m REAL,
  width_src    TEXT, verdict TEXT
);
CREATE TABLE core.run (                 -- 매니페스트가 그대로 테이블이 된다
  run_id BIGSERIAL PRIMARY KEY,
  git_sha TEXT, dirty BOOL, ran_at TIMESTAMPTZ, params JSONB
);
```

1. **PK 는 `seg_uid` / `obs_id`.** `seg_id` 를 PK 로 쓰면 다음 실행에 전부 깨진다
2. **파이프라인 결과는 append + `run_id`.** 덮어쓰지 않는다
3. **API 는 `serving` 스키마만 본다.** 프론트가 판정을 재계산하지 않는다

## 18-11. 획득 · 업서트 게이트

```
landing (외장 SSD)                     다운로드 원본. 손 안 댐
        ↓  tools/acquire.py --stage  — 대장 매칭 + sha 기록
data/raw/<제공기관>/                    매칭됨. 원본 파일명 유지
data/_quarantine/                      매칭 안 됨. 삭제하지 않고 격리
        ↓  normalize_raw.py
data/norm/                             규칙 파일명 + 인코딩·확장자 통일
        ↓  contract.py — 계약 대조(§18-3b)
data/processed/
```

### 세 판정

```
대장에 있음 + 파일 있음   →  raw 편입
대장에 있음 + 파일 없음   →  ★ 결손 경고
대장에 없음 + 파일 있음   →  _quarantine. 사람이 대장 추가 또는 retired 등재
```

★ **두 번째가 제일 중요하다.** 외장 백업이 중단됐는데 아무도 몰랐고, raw 7개
폴더 중 4개만 넘어간 상태로 다른 기기에서 파이프라인을 돌린 적이 있다.
**"없는 것을 없다고 말하는 것"이 안 돼서였다.**

적재 판정은 크기가 아니라 **내용(sha256)** 으로 한다. 313MB 정사영상이 전송
중 잘려도 크기 비교로는 통과한다. §18-8 이 백업에 대해 적은 문장이 획득에도
그대로 적용된다.

### 원칙 다섯

```
1. 원본 파일명을 바꾸지 않는다        재다운로드·문의 때 대조가 안 된다
2. 기존 판을 덮지 않는다              "언제부터 값이 달라졌는가"에 답할 수 없다
3. 받은 즉시 대장을 고친다            나중에 적으면 틀린다
4. 계약 대조를 통과해야 편입이다      §18-3b
5. 편입 후 impact 를 돌린다           재생성 대상이 전부 나온다
```

### CRS 검증 3단계

```
1. 선언 확인   .prj · .xml 을 읽는다. 있으면 그게 정답
               수치지형도 xml → EPSG:5186 명시
               연속수치지도 prj → EPSG:5179 명시  ★ 둘이 다르다
2. 범위 검사   5186 은 X 190k~210k · Y 260k~300k (광주)
               5179 는 900k~1100k · 4326 은 126~127 / 35~36
3. 교차 정합   서로 다른 소스를 겹친다. 건물 폴리곤 위에 CCTV 점이 얹히는가
```

**3번이 실질 검증이다.** 1·2번은 형식 검사이고 3번은 물리 검사다.
`crs` 는 **"명시"와 "추정"을 구분해서 적는다.**

| 필드 | 뜻 |
|---|---|
| `passable_width_m` | HARD + VEHICLE 기준. 지금 상태로 지나갈 폭 |
| `passable_width_hard_m` | HARD 만 기준. 차를 빼면 나오는 폭 |
| `at_offset_m` | 최솟값이 나온 위치(구간 시점 기준). 실측 갈 때 쓴다 |
| `masked` | 거짓이면 GIS 가 받지 않는다 |
| 아래 다섯 | 오차 보정 단위 식별. §19-3 |

폭이 둘인 근거는 소방청 기준 문구다. "폭 2m 이하 **또는 이동불가 장애물**로
진입 불가"라고 쓴다. 이동 가능한 것은 장애물로 치지 않는다. 두 값을 나눠 받으면
"지금은 막혔지만 치우면 뚫린다" 판정이 가능하다.

`seg_id` 를 쓰지 않는다. 파이프라인을 돌릴 때마다 번호가 갈린다.
`seg_uid` 는 GIS 가 관측점 등록 때 발급한다.

### 19-2. GIS 가 주는 것

```
GET /obs/{obs_id}
{ "seg_uid": "...", "bearing_deg": 118.4, "ref_points": [...], "length_m": 42.7 }
```

★ **도로폭은 주지 않는다.** GIS 폭을 먼저 알고 재면 그 값 근처로 수렴하고,
그러면 영상이 GIS 를 검증하는 의미가 사라진다. GIS 폭 자체가 미검증 상태라
그것을 물려주면 틀린 값이 재생산된다. 방향은 폭이 아니므로 순환하지 않는다.

### 19-3. 오차를 계통오차로 몬다

ArUco 실측은 현실적으로 3~5회다. 그 몇 번으로 파이프라인 오차를 잡으려면
오차가 진동하면 안 된다.

    계통오차   방향과 크기가 일정하다   → 3~5회로 추정해서 빼면 된다
    우연오차   실행마다 진동한다        → 수십 번 재도 특성만 알 뿐 못 없앤다

**"정확하게"보다 "일관되게"가 먼저다.** 0.4m 만큼 항상 크게 나오는 파이프라인은
고칠 수 있지만 ±0.4m 로 흔들리는 것은 못 고친다.

    H 는 세션당 1회               프레임마다 풀면 RANSAC 이 매번 다른 인라이어를
                                 골라 결과가 진동한다
    대응점 지물을 관측점별로 고정   세션마다 다른 지물을 쓰면 보정 기준이 바뀐다
    모든 지물은 같은 지면 평면      벽 위·계단·턱을 섞으면 평면 호모그래피가
                                 성립하지 않는다
    RANSAC 시드 고정              재현 안 되면 어느 실행의 오차를 보정하는지 모른다

프레임 집계는 **중앙값**이다. 최솟값의 최솟값을 취하면 한 프레임 튄 것이
결과가 된다. 중앙값은 우연오차를 억제하고 계통오차는 그대로 남긴다.

반환에 `calib_id` · `h_id` · `params_ver` · `n_ref` · `h_rms_px` 를 싣는 이유가
이것이다. 보정계수를 얻어도 **어디에 적용할지** 모르면 못 쓴다. 폰 · 렌즈 ·
해상도 · 촬영모드가 다르면 다른 오차이고 섞으면 안 된다.

### 19-4. 성능

현재 MVP 가 객체탐지 + 세그멘테이션 + 호모그래피 + 폭 계산에 5초다.
목표는 1~2초다.

★ **먼저 5초의 내역을 재야 한다.** 최적화 방향이 거기서 갈린다.

**BEV 이미지를 만들지 않는다.** 폭 계산에 필요한 것은 마스크 경계점의 지면
좌표뿐이다. warp 는 O(픽셀) 수백만인데 점 변환은 O(점) 수백이다. 시각 확인용
BEV 는 디버그 플래그 뒤에 둔다.

세그멘테이션 모델과 호모그래피는 **한 프로세스**에서 돈다. 프레임을 프로세스
밖으로 내보내지 않는다. 통신으로 나누면 성능 · 대역폭 · 개인정보 셋이 다
나빠진다. 경계는 함수 시그니처다.

### 19-5. 폭 계산의 함정

지면 좌표계에서 도로 방향 기준 0.5m 간격 횡단선을 긋고, 각 횡단선에서 폭을
구한 뒤 전체 중 **최솟값**을 취한다. 각 횡단선에서 구하는 것은 "빈 공간의 합"이
아니라 **"끊기지 않고 이어지는 빈 구간 중 제일 긴 것"** 이다.

    담 |■■■■■차량■■■■■| 2.0m |화분| 1.2m | 담

빈 공간을 합하면 3.2m 지만 실제로 지나갈 수 있는 것은 2.0m 다. 합산으로
구현하면 결과가 **조용히 낙관 방향으로** 틀어진다. "막혔는데 통과 가능"은
소방차가 골목에 갇히는 오류라 반대 방향보다 비용이 훨씬 크다.
