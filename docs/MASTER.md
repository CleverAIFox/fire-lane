## 1. 무엇을 만들었나

전남광주통합특별시 동구 동명동과 그 접근 회랑의 **1,087개 구간**에 대해
소방차가 지나갈 수 있는지를 판정한다. 판정 근거와 **판정할 수 없는 이유**를
함께 남기는 것이 이 시스템의 핵심이다.

> 노딩 산출물과 교차로 파편이 정리된 것**이다. §3-8 참조.

## 2. 현재 판정 (2026-08-13)

| 판정 | 구간 | 뜻 |
|---|---:|---|
| `clear` 통행 가능 | 443 | 양쪽 주차가 있어도 통과. 영상판정 불필요 |
| `needs_cv` 판정 보류 | 191 | 상습주차 여부로 갈린다. 영상판정 대상 |
| `blocked` 통행 불가 | 57 | 차가 없어도 통과 불가 |
| `unknown` 영상판정 불가 | 396 | CCTV 25m 밖. 영상판정 자체가 불가능 |

```
segments 1087 · 경로사용 567 · sha 963838eeebc3f8fe
```

**`unknown` 396 은 전부 `no_cctv` 다.** 8/12 에 127 개였던 `width`(폭 산출 불가)는
8/13 에 0 이 됐다. 회색은 이제 한 가지 뜻만 갖는다 — 카메라가 없어 못 본다.

```
CCTV 유효범위(25m) 안   379 / 1,087   (34.9%)
동명동 안               412 구간
```

> `1087 − 396 = 691` 이 아니다. `unknown` 은 "판정 보류인데 CCTV 사각"인
> 것만 센다. `blocked`·`clear` 는 도면으로 확정되므로 CCTV 유무와 무관하게
> 판정되고, 그중에도 사각지대가 많다. **골목의 65%는 여전히 영상판정이
> 불가능하다**(§3-5).

### 판정 기준의 출처

임의 임계값이 아니다. **소방청 「2025 화재현장 골든타임 확보 종합대책」**을 따른다.

```
진입불가   폭 2m 이하, 구간 100m 이상
진입곤란   폭 3m 이상 + 장애물·상습주차, 구간 100m 이상
기준 차량  중형펌프차량 폭 2.5m
```

```
TRUCK = 3.0     차량 전폭 2.5 + 미러·조향 여유 0.5
PARK  = 2.0     주차 1대 노면 점유
blocked   최대 폭(담~담) < 3.0
clear     최소 폭 >= 3.0 + 2 x 2.0 = 7.0      양쪽 주차를 가정한다
```

소방청 지정 기준(연속 100m 이상)을 충족하는 구간은 **139개**, 최장 연속 505.5m 다.
구간 길이는 중앙 37.0m · 최대 282.1m · 100m 초과 52 개다.

## 3. 이 프로젝트가 발견한 것

### 3-1. "222구간"은 근거가 없었다

기존 문서의 세그먼트 수를 검증한 결과 출처를 찾지 못했다.
정식 행정경계로 재산출하여 **641**로 확정했다.

```
도로명주소 도로구간   206
실폭도로              219
노딩 후 세그먼트      641   ← 동명동만 (8/11)
스코프 확장 후       1266   ← 접근 회랑 포함 (8/11)
노드접합·병합 후     1087   ← 현재 판정 단위 (8/13). §3-9 · §3-10
```

179 가 줄어든 것은 도로가 사라진 것이 아니라 **길이 0.0m 짜리 노딩 산출물
224개와 교차로 파편이 정리된 것**이다.

### 3-2. 도로명주소는 위상이 보장되지 않는다

원본은 "도로명 하나 = 선 하나"라 교차로에서 분할되지 않는다.
노딩 후에도 밀리미터 단위 좌표 오차로 구간이 분리된다(**T자 접합**).

| 처리 | 연결요소 | 최대요소 연장비 |
|---|---:|---:|
| 원본 | 40 | 93.29% |
| `set_precision(0.5)` | 22 | 97.74% |
| **끝점 투영 스냅 0.5m** | **6** | **99.76%** |

잔여 5구간(77m)은 알고리즘 한계가 아니라 **도로명 미부여 구간**이다.
그중 3곳이 관리폭 1.0~1.5m로 소방차 진입이 원천 불가하다.
**데이터의 공백 자체가 위험구간 지표다.**

### 3-3. `ROAD_BT`는 폭 값으로 쓰면 안 된다

도로대장의 명목 폭은 **171구간(84%)에서 실측 트랜섹트보다 넓다.**
중앙 차이 +1.00m. 못 지나가는 길을 지나간다고 판정하는 방향이다.

**단, 2026-08-13 부터 한 가지 예외를 둔다.** 폭을 끝내 못 잰 구간에 한해
명목폭이 `TRUCK`(3.0m) 미만이면 `blocked` 으로 확정한다. 폭이 안 나오는 것과
잴 만한 도로가 아닌 것은 다르다. 명목폭 1.0m 짜리 부속 통로를
"CCTV 없어 판정 보류" 회색으로 두면 영상판정으로 메울 수 있다는 뜻이 되는데,
카메라를 갖다 대도 소방차는 못 들어간다. 실측값이 하나라도 있으면
그쪽이 항상 우선하므로 이 규칙은 폭 미산출 구간에만 걸린다(적용 2건). §16 참조.

### 3-4. 폭은 하나로 못 정한다

| 이름 | 데이터 | 성격 |
|---|---|---|
| 노면폭 하한 | 실폭도로 폴리곤 | 확실히 비어 있는 폭 |
| 담~담 상한 | 건물 폴리곤 | 물리적 최대 통로폭 |

담~담이 전 구간에서 넓고 중앙 차이 **+2.08m**. 그 사이에
전신주·화분·실외기·계단·주차 차량이 들어 있다.
**밴드를 좁히는 것이 영상판정과 실측의 역할이다.**

### 3-5. ★ 골목의 64%는 영상판정이 불가능하다

CCTV 유효범위를 25m로 잡으면(25m 초과 시 호모그래피 오차 급증):

```
CCTV 유효범위 안         379 / 1,087  (34.9%)   ← 2026-08-13 기준
CCTV 거리 중앙값          38.6m
최대                      129m
영상판정 불가 구간         195개 · 6,745m (전체 연장의 28%)
```

**영상 기반 진입 판정 시스템을 만들어도 골목의 64%에는 적용할 수 없다.
알고리즘의 한계가 아니라 인프라의 한계다.**

완화 요소: 영상판정 불가 구간이 담당하는 소방 통행량은 **11%**다.
주요 동선에는 대체로 CCTV가 있다.

### 3-6. 출동은 소방서가 아니라 119안전센터에서 나간다

대인(서 1.0km) · 지산(동 1.2km). 둘 다 동명동 밖이다.

```
동 경계 진입점                60곳
실사용 진입점                 23곳
출동 통행의 80%를 담당         5곳
출동 통행의 50%를 담당         2곳
```

**진입점 5곳에 대책을 집중하면 출동의 80%가 개선된다.**

### 3-7. 소화전은 동명동에 1개뿐이다

```
동부소방서 관할   지상식 431 + 일반지하식 157 = 588
공개된 것         31개 (5%)
그중 동명동       1개
```

588 의 출처는 `hydrant_summary`(소방용수시설 현황, 관할서별 5행)다.
**공개 데이터에는 분모가 없다.** 이 표가 유일한 근거이므로 발표에 쓸 때 함께 인용할 것.

데이터 공백 자체가 결과다.

### 3-8. 런타임 프루닝은 폭이 아니라 경로로 한다

정적 폭 기준으로는 61%가 영상판정 대상으로 남는다(동명동이 원래 좁다).
반면 실제 최단경로에 등장하는 엣지는:

```
1회 이상 사용        665 / 4,227  (15.7%)
통행량 80% 담당      177개  (4.2%)
통행량 50% 담당       71개  (1.7%)
```

**71개 엣지가 출동 통행의 절반을 처리한다.** 여기부터 영상판정을 걸면 된다.

### 3-9. ★ 길이 0.0m 짜리 구간 40개가 "통행 가능"으로 표출되고 있었다

노딩이 노드를 **밀리미터 반올림**으로 식별했다. 4cm 떨어진 두 점이 별개 노드가
되고 그 사이에 길이 0.04m 짜리 엣지가 생긴다. §3-2 에서 T자 접합에
`SNAP_TOL 0.5m` 관용을 줬으면서 노드 식별에는 안 줬던 것이다.

`NODE_TOL 0.5m` 로 끝점을 묶자 자기루프 224 개가 사라졌다.

```
엣지 3675 → 3444        노드 최대이동 0.359m
판정 변화  clear -40 · needs_cv -10 · blocked ±0 · unknown -40
```

**폭 미산출 51 개만 문제인 줄 알았는데 나머지 절반은 조용히 초록으로 통과하고
있었다.** `blocked` 이 0 변동인 것이 접합이 실제 좁은 구간을 지우지 않았다는 증거다.

### 3-10. ★ 교차로 안에서는 그 도로의 폭을 잴 수 없다

교차로 안의 한 점에서 도로 A 에 수직으로 법선을 그으면, 그 법선은 **교차하는
도로 B 를 따라 길이 방향으로 달린다.** 나오는 값은 폭이 아니라 "도로 B 가
60m 안에서 얼마나 뻗어 있나"다.

```
제봉로          3.3m 구간 → 폭 55.39m
필문대로218번길  4.2m 구간 → 폭 45.63m
경양로          7.3m 구간 → 폭 45.33m
```

기하학적으로 정의되지 않는 것이지 측정 기법의 한계가 아니다.
그래서 교차로 파편은 **독립 피처로 두지 않고** 동일선상(30° 이내) 이웃과
하나의 산출단위로 묶는다. 그래프 `G` 는 라우팅·교차로 노드 정본이므로
손대지 않고, 산출 단위만 병합한다.

> 이 문제를 "교차로 제외를 풀고 재기"로 풀려다 폐기했다. 큰 값은 눈에 띄어
> 걸러지지만 `동계로1번길 7.03` `동명로98번길 7.31` 처럼 임계 7.0 을 간신히
> 넘겨 `clear` 가 된 골목들이 그럴듯한 채로 지나간다. **반복 금지.**

### 3-11. ★ 폐기한 `min()` 이 표본 축에 남아 있었다

결정 63 으로 소스 축의 `min()` 은 폐기했는데, 구간 폭을 내는
`wmin = min(A)` 의 `A` 는 **표본마다 다른 소스가 채택된 혼합 집합**이었다.
표본 1 이 1:1,000 의 3.2m, 표본 2 가 실폭도로의 1.8m 인데 그 둘의 최솟값을
구간 폭이라고 불렀다.

값을 낸 최우선 소스 하나로 고정하고 그 소스의 표본만으로 최솟값을 낸다.

```
채택 소스   ngii1k 925 · ngii 131 · silpok 29 · null 2
            (8/13 오전 802 / 128 / 155 에서 이동)
1k 부분커버 302 구간 · 그중 채택소스가 1k 가 아닌 것 0
```

커버율이 높은 소스를 고르지 않는다. 실폭도로가 0.955 로 가장 높은데
그것을 채택하면 결정 63 을 정면으로 뒤집는다.

## 4. 외부 검증 — 소방서 지정 구간과의 대조

동부소방서 「소방통로확보대상 지역 현황」(2025-07-31, 20구간 7,120m 3,452세대)의
기록 폭과 우리 산출값을 비교했다.

### ★ 이 대조는 2026-08-13 까지 한 번도 실행되지 않았다

`segments.py` 의 대조 블록이 `ROOT/"data"/"raw"/...` 를 보고 있었는데
raw 는 `$FIRE_LANE_RAW` 다. `if fa.exists()` 가 항상 거짓이라 코드는 있는데
죽어 있었다. 8/11 에 문서에 적힌 표는 당시 별도 스크립트로 낸 값이다.

**우리 폭에 대한 유일한 외부 대조 수단이 꺼져 있었다.** 8/13 에 경로를 고쳐
파이프라인 안에서 매 실행 출력된다.

### 대조 결과 (2026-08-13, 도로명 매칭 7구간)

| 도로명 | 소방서 | 우리(중앙) | 편차 | 세그 |
|---|---:|---:|---:|---:|
| 필문대로289번길 | 8m | 7.79m | **-0.21** | 30 |
| 필문대로205번길 | 8m | 7.65m | **-0.35** | 40 |
| 동명로20번길 | 5m | 5.00m | **+0.00** | 36 |
| 밤실로4번길 | 5m | 6.00m | +1.00 | 3 |
| 제봉로184번길 | 5m | 6.18m | +1.18 | 19 |
| 중앙로272번길 | 5m | 3.50m | -1.50 | 4 |
| 동계로9번길 | 6m | 8.97m | +2.97 | 18 |

**절대편차 합 7.24m.** 8/13 오전 시작 시점은 12.6m 였다.

이 표가 오늘 폭 수정 세 건의 판정 기준이었다. 기하학적 논증만으로
"고쳤다"고 하지 않고, 매번 이 편차가 줄어드는지로 채택 여부를 갈랐다.

```
소스별 snap 도입      필문대로289번길 -4.78 → -1.77
구간단위 소스채택      필문대로289번길 -1.77 → -0.21
```

### 대조의 한계

소방서 데이터에 **좌표가 없다.** 도로명으로만 매칭되므로 도로 전체(대로 구간
포함)를 잡는다. 그래서 구간 대표폭인 중앙값과 비교하며, 최솟값으로 비교하면
교차로 근처 극협소 지점을 잡아 -3~-7m 로 벌어진다.

정밀 대조에는 구간 좌표가 필요하며 D-30 인터뷰 요청 항목이다.

## 6-2. 데이터 보관 전략

### 현재 — 로컬 + 환경변수

```
data/raw        2.2GB · 저장소 밖 · FIRE_LANE_RAW 로 위치 지정
data/processed  로컬 생성물 · *.gpkg / *.tif 는 git 제외
web/data        13MB · git 포함 (UI 담당이 raw 없이 작업해야 한다)
```

**심링크는 쓰지 않는다.** `data/raw` 를 심링크로 걸었더니 git 이 추적했고,
exFAT 에서 `git reset --hard` 시 경로 문자열 파일로 체크아웃되면서
원본 2.5GB 가 소실됐다(2026-08-11). `src/etl/paths.py` 의 환경변수 방식으로 대체했다.

```bash
export FIRE_LANE_RAW="/mnt/f/.../FIRE_LANE/data/raw"     # 리눅스
setx FIRE_LANE_RAW "D:\...\FIRE_LANE\data\raw"        # 윈도우
```

미설정 시 `<repo>/data/raw` 를 쓴다. 단일 머신이면 그걸로 충분하다.

`web/data` 는 CI 가 **60MB 상한**을 감시한다. 타일이 늘어 넘으면 머지가 막힌다.

### 향후 — AWS S3

raw 를 S3 로 옮기고 GitHub Actions 와 엮으면 데이터 파이프라인이 완성된다.

```
S3  fire-lane-gis-raw/        원본
    fire-lane-gis-processed/  중간 산출물
Actions  raw 갱신 감지 → ingest → segments → publish → Pages 배포
```

`paths.py` 만 `s3://` 를 받도록 고치면 되고, 나머지 스크립트는 그대로다.
그래서 지금 환경변수로 분리해둔 것이다.

**다만 지금은 이르다.** 2.2GB 를 위해 S3 비용과 IAM·CI 설정을 감수할 단계가 아니고,
D-25 실측과 A* 가 먼저다. 4달 일정 중반쯤 파이프라인이 안정되면 옮긴다.

### 3-9. 단속 이력의 쓰임 — 시간대는 못 쓰고 빈도는 쓴다

```
85,380건 · 2022-01 ~ 2023-10 · 위반장소명(도로명주소) 보유
고유 장소 2,123개
14시 33,412건 = 39.1%   ← 입력 기본값. 시간대 분석 불가
```

**구간별 발생 빈도는 유효하다.** 도로명 상위: 충장로 5,068 · 구성로 3,797 ·
금남로 3,739 · 백서로 2,462 · 동계천로 2,432.

이것이 상습주차 추정 모델의 **레이블**이 된다.
CCTV 가 없어 영상판정이 불가능한 223구간의 주차 압력을
도면 특징(도로 폭·상가 밀도·주차장 거리 등)으로 추정하고 이 빈도로 학습한다.

**출동 시점의 상태가 아니라 사전 위험도다.** 그 구분을 흐리면 안 된다.
시점 정보는 CCTV 유효범위 안에서만 얻을 수 있고, 그 밖은 확률로 대비하는 수밖에 없다.

```
1. node_link + turn_restriction 투입     A* 필수. 이미 보유
2. A* 비용함수 설계                      거리 + 폭 + 통행제한 ∞ + 경사
3. 영상판정(호모그래피) 모듈 연결         needs_cv 191구간
4. D-25 레이저 실측                       width_verified: false → true
5. D-30 인터뷰                            소화전 좌표 + 소방통로 구간 좌표
6. 5m DEM 신청
7. ngii1k 를 pipeline STEPS 에 편입        재현성 구멍
8. streetlight ingest kind 처리            csv_point 핸들러 없음
```

**7·8 번은 2026-08-13 에 실제로 발목을 잡았다.** 기기를 옮겼더니
`ngii1k_5186.gpkg` 가 없는 채로 파이프라인이 돌아 폭 주 소스가 실폭도로로
떨어졌고(`clear` 392 → 346), 원인을 찾는 데 시간을 썼다. 두 단계가
파이프라인 밖에 있어 `pipeline.py` 한 명령으로 재현되지 않는다.

**1번이 먼저다.** 새 데이터 없이 되고, 이것 없이 A*를 만들면 역주행 경로가 나온다.

### 알려진 근사

- `length_m` 은 **수평거리**다. 경사 보정 전이며 실주행거리는 0.05~1.2% 더 길다.
  보정에는 5m DEM 이 필요하다.
- 지도의 지형은 공개DEM 90m 를 보간한 **표현용**이다. `exaggeration` 기본값은
  1.0(실제 비율)이며, 올리면 표고가 왜곡되므로 발표에 쓸 때는 명시해야 한다.
- **CCTV 유효범위 25m 는 미확인 값이다.** 이 하나로 1,266구간의 판정이 갈린다.
  호모그래피 담당(백진욱)의 확인이 필요하다. 값이 바뀌면 전체가 재산출된다.

### 아직 검증되지 않은 것

- **폭 실측 0건.** 8/6 답사는 GPS 미기록으로 무효. 다만 8/12 네이버 지도
  실측 대조로 소스 우선순위가 정해졌고(결정 63), 8/13 소방서 지정 7구간
  대조로 절대편차 합 7.24m 까지 좁혔다. 현장 실측은 여전히 D-25 다.
- **CCTV 25m**는 잠정값이다. D-25 실측 검증 대상.
  `segments.py`의 `CCTV_RANGE` 한 줄이며 바꾸면 전체가 재계산된다.
  이 값 하나가 396 구간(회색 전부)의 판정을 가른다.
- **`width_cov` 0.5 미만 69구간.** 채택 소스가 그 구간의 절반도 못 덮었다는
  뜻이다. 표본 축 소스 혼합을 없앤 대가이며(§3-11), 혼합할 때는 다른 소스
  값에 섞여 보이지 않던 것이다. **D-25 실측 1순위.**
- `inherited` 는 더 이상 쓰지 않는다(항상 false). 상속은 8/12 에 폐기했다.
- `wmax`(담~담)가 교차로에서 46~57m 로 샌다. `min(B)` 라 판정 영향은 작지만
  `width_max_m` 필드 자체는 신뢰할 수 없다.

## 8. 역할

| | 담당 | 영역 |
|---|---|---|
| 오창준 `@AIMasterFox` | GIS | `src/etl/` · `sources.yaml` · `data/` |
| 우지혜 `@marscoolcat` | UI · 3D | `web/index.html` |
| 경계 | CI | `tests/test_contract.py` |

브랜치 `gis` 정본. 작업은 `gis-*` · `ui/*` 에서 하고 PR로 합친다.
`gis/*` 는 `gis` 브랜치와 ref 충돌로 생성 불가하다.
`gis` 는 보호 브랜치이며 직푸시가 막힌다. **오창준도 PR 이 필요하다.**

파일이 겹치지 않으므로 동시에 작업하고 각자 푸시하면 된다.

```
GIS   src/etl/ · sources.yaml · data/ · docs/
UI    web/index.html · app.js · config.js · style.css
```

매일 푸시를 권장한다. 완성해야 푸시하는 게 아니라 동작하는 지점마다 푸시한다.
**미커밋 변경을 워킹트리에 쌓아두지 않는다** — 8/12~13 에 기기를 옮기며
같은 수정을 두 번 작성한 일이 있었다.

## 9. 이 프로젝트의 성격

숫자를 만들어내는 것이 아니라 **어디까지 알 수 있고 어디부터 모르는지를 긋는 것**이다.

- 골목의 42%는 도면만으로 판정이 안 된다 → 주황으로 표시한다
- 그중 다시 64%는 CCTV가 없어 영상판정도 안 된다 → 회색으로 표시한다
- 폭 값은 실측 전이다 → 화면 상단에 상시 경고한다

**모르는 것을 모른다고 표시하는 것**이 이 지도의 설계 원칙이다.
전부 초록으로 칠하면 첫 질문에 무너진다.

| 빨강 | 통행 불가 | 최대 폭 < 3.0m | 중형펌프차 폭 미달. 장애물이 없어도 못 지나간다 |
| 회색 | 영상판정 불가 | — | CCTV 25m 밖. 카메라가 없어 못 본다 |

**색은 4종 고정이다.** `unknown_reason` 은 회색의 하위 구분이지 다섯 번째
색이 아니다. 범례에 별도 줄로 올리지 않는다 — 색이 5종으로 보이고
합계도 안 맞아 보인다. 하위 구분은 툴팁이나 상세 패널에 넣는다.

> 8/12 에 `out_of_scope` 와 `conflict` 로 5번째 색을 두 번 만들었다가 둘 다
> 지웠다. 8/13 에는 범례에 `CCTV 없어 보류` 갈색 줄이 올라가 있던 것을
> 내렸다. **다시 만들지 마라.**

#### 기준의 출처

임의로 정한 값이 아니다. **소방청 「2025 화재현장 골든타임 확보 종합대책」**을 따른다.

```
진입불가지역   폭 2m 이하, 또는 이동불가 장애물로 진입 불가한 구간이 100m 이상
진입곤란지역   폭 3m 이상 도로 중 장애물·상습주차로 상시 장애, 구간 100m 이상
기준 차량      중형펌프차량 폭 2.5m
```

```
TRUCK = 3.0     차량 전폭 2.5 + 미러·조향 여유 0.5
PARK  = 2.0     주차 1대 노면 점유
blocked   최대 폭(담~담) < 3.0
clear     최소 폭 >= 3.0 + 2 x 2.0 = 7.0
```

`clear` 는 **양쪽 주차**를 가정한다. 한쪽만 가정하면 5.0m 지만, 양방 주차가
상시인 골목에서 한쪽만 보는 것은 낙관 방향이다.
"왜 하필 그 숫자냐"는 질문에 국가 기준 + 명시된 여유값이라고 답할 수 있다.

#### 연속 구간 (`run_length_m`)

소방청 지정 기준의 **"구간 100m 이상"**은 세그먼트 하나가 아니라
같은 판정이 이어지는 **연속 구간 전체**의 길이다. 5m짜리 조각 하나로는 지정되지 않는다.

```
소방청 지정 기준 충족   139구간
연속 구간 최장           505.5m
```

`nfa_designated`가 `true`면 툴팁에 표시된다.

**주황 191개가 이 프로젝트의 미완성 부분이다.** 전체의 17.6% 다.
영상판정이 붙으면 이 191개가 초록·빨강으로 갈린다.
회색 396개는 영상판정으로도 안 갈린다 — CCTV 배치가 선행돼야 한다.

### 폭이 왜 두 개인가

같은 골목을 두 가지로 잰다. 하나로 못 정하는 게 아니라 **둘 사이가 답이기 때문**이다.

| 화면 표기 | 필드명 | 데이터 | 뜻 |
|---|---|---|---|
| **최소 폭** | `width_min_m` | 실폭도로 폴리곤 | 장애물이 없을 때 확실히 비어 있는 폭 |
| **최대 폭** | `width_max_m` | 건물 폴리곤 | 양쪽 건물 벽 사이 거리. 물리적 최대 |

> 이전에 쓰던 "노면폭 하한 / 담~담 상한"은 **최소 폭 / 최대 폭**으로 통일했다.
> 문서·UI·발표 자료 전부 이 표기를 쓴다.

최대 폭이 최소 폭보다 **전 구간에서** 넓고 중앙값 차이가 2.08m다.
그 사이에 전신주·화분·에어컨 실외기·계단·주차 차량이 들어 있다.

3.0m 기준으로 보면 **최소 폭 기준 125구간 vs 최대 폭 기준 35구간**이 걸린다.
즉 90구간(47%)은 어느 쪽을 믿느냐에 따라 판정이 뒤집힌다.
**이 밴드를 좁히는 것이 영상판정과 현장 실측의 역할이다.**

> `ROAD_BT`(도로대장의 명목 폭)는 쓰지 않는다. 실측 대비 84% 구간에서
> 1m씩 넓게 나온다. 못 들어가는 길을 들어간다고 판정하는 방향이라 가장 위험하다.

### 소방 동선 (`route_usage`)

**이 골목을 소방차가 얼마나 자주 지나는가.**

119안전센터 2곳(대인·지산)에서 동명동 건물출입구 358곳까지
최단경로를 **전부** 계산한 뒤, 각 골목이 몇 개의 경로에 등장하는지 센 값이다.

**선 굵기는 이 값이 아니다.** 선 굵기는 최소 폭이다(아래 참조).

> 소방 동선은 현재 지도 화면에서 빼두었다. `route_usage` 필드는 데이터에 남아 있으므로
> 필요할 때 다시 꺼내 쓸 수 있다. 프루닝 근거로는 계속 유효하다.

```
1,087개 중 실제로 쓰이는 것           567개
출동 통행의 50%를 담당하는 골목        71개
출동 통행의 80%를 담당하는 골목       177개
```

**왜 중요한가.** 영상판정을 1,087개 전부에 돌리면 출동할 때마다 계산이 쌓인다.
실제로 밟히는 골목만 보면 대상이 확 준다. 이게 프루닝이다.

### 선 굵기 = 최소 폭

화면의 선 두께가 곧 그 골목의 폭이다. 미터 단위로 그려지므로
확대·축소해도 실제 비율이 유지된다. 굵은 선이 넓은 길이다.

폭을 못 잰 구간(회색)은 최소 굵기로 가늘게 그린다.

### 길이 (`length_m`)

그 구간의 **수평거리**(m). 평면 좌표계(EPSG:5186)에서 잰 값이다.

**경사 보정 전이다.** 실제 주행거리는 `수평거리 / cos(경사)` 이므로 더 길다.

```
동명동 평균 경사 1.8°  →  실주행거리 +0.05%   (100m 당 5cm)
최대 경사      9.0°  →              +1.2%    (100m 당 1.2m)
```

무시할 만한 수준이지만 **"같다"가 아니라 "차이가 이만큼이고 반영하지 않았다"** 가 정확하다.
보정하려면 구간별 경사가 필요하고, 그러려면 5m DEM 이 있어야 한다.
공개DEM 90m 로는 한 픽셀이 골목 20개를 덮어 산출이 불가능하다.

**폭은 경사 영향을 받지 않는다.** 폭은 진행 방향과 수직으로 재므로
도로가 기울어도 좌우 거리는 변하지 않는다. 다만 횡단경사(편경사)가 있으면
유효폭이 줄어드는데, 이 역시 90m 격자로는 잡을 수 없다.

### 세그먼트 / 노딩

**세그먼트** = 교차로에서 잘라낸 도로 조각. 판정의 기본 단위다.

원본 데이터(도로명주소 도로구간)는 "도로명 하나 = 선 하나"라
제봉로가 중앙로를 가로질러도 통짜 한 줄이다. 그대로는 경로 탐색이 안 된다.
교차점마다 잘라서 그래프로 만드는 것이 **노딩**이다.

```
원본 도로구간   206개
노딩 후         641개 세그먼트   ← 동명동만
접근 회랑 포함  1,266개
노드접합·병합   1,087개          ← 현재 판정 단위
```

> 기존 문서의 "222구간"은 근거를 찾지 못했다. 641 → 1,266 → 1,087 로 바뀌었다.
> **구간 수는 고정값이 아니다.** 노딩 규칙이 바뀌면 바뀐다.

### 스코프

지도가 보여주는 범위. **동명동 + 접근 회랑 + 안전센터 반경 300m**, 약 2.8 × 1.4km.

동명동만 보면 안 되는 이유는 **119안전센터가 동 밖에 있기 때문**이다
(대인 서쪽 1.0km · 지산 동쪽 1.2km). 출동 경로가 화면에서 잘린다.

**접근 회랑** = 안전센터에서 동명동까지 오는 길. 최단경로 중 동 밖 구간이다.
광주 전체가 아니라 얇은 리본이다.

화면 밝기가 3단계다.

```
동명동      밝게        판정 대상
접근 회랑   살짝 어둡게  오는 길
그 밖       덮음        스코프 밖
```

이 범위 밖으로는 이동도 축소도 안 된다. 작업 범위가 구조적으로 고정된다.

### 시설 마커

마커는 전부 **3D 입체**다. 2D 점은 기울인 화면에서 지면에 붙어 안 보인다.
원기둥 3~4개를 쌓아 실제 시설의 실루엣을 근사한다.

| 마커 | 색 | 형상 | 건수 |
|---|---|---|---|
| **119안전센터** 출동 시작점 | 빨강 | 기둥 + 헤드 + 첨두 | 2 |
| 동부소방서(본서) | 주황 | 본체 + 안테나 | 1 |
| 소화전 | 파랑 | 받침 + 몸통 + 플랜지 + 캡 | 11 (동명동 **1**) |
| CCTV | 보라 | 지주 + 하우징 + 렌즈 | 104지점 312대 |

**비율은 실물을 따르되 크기는 약 5배 과장했다.** 소화전 실물은 0.9m라
실제 치수로 그리면 1km 시야에서 점 하나가 되어 보이지 않는다.

소화전이 안 보인다면 버그가 아니라 **동명동 안에 1개뿐**이기 때문이다.

**CCTV 커버리지**는 반경 30m 원으로 표시된다. 촬영방면이 전부 360도라
방향 콘이 아니라 원이다. **커버리지가 닿지 않는 골목**을 보이게 하는 것이 목적이다.

> CCTV 원본은 설치연도별로 행이 쪼개져 있다. 동명동 53행이 실제로는 29지점 90대다.
> 좌표로 묶어 지점 단위로 집계했고, `설치회차`에 증설 횟수가 남는다.

**소화전이 동명동에 1개인 것은 버그가 아니다.**
동부소방서 관할 588개 중 공개된 것이 31개(5%)뿐이고 그중 동명동이 1개다.
이 희소성 자체가 발표 논거다. 패널의 `1 / 11`이 그 표기다.

가로등은 2026-08-12 에 확보했다(동구 3,805등 / 264지점). 좌표가 지번 대표점이라
지도 마커로는 못 쓰고 `light_count`(반경 50m 등 수) 로만 쓴다. §6 참조.

# 12. 협업

브랜치는 `gis` 하나다. 각자 작업 브랜치를 파서 PR 로 합친다.

### 하루 시작

```bash
git checkout gis
git pull
git checkout -b ui/오늘작업이름     # 또는 gis/오늘작업이름
```

### 하루 끝 — 푸시를 권장한다 (강제 아님)

```bash
git add -A
git commit -m "ui: 판정 색상 대비 조정"
git push -u origin ui/오늘작업이름
```

GitHub 에서 `gis` 로 PR 을 연다. 미완성이면 **Draft PR** 로 열어두면 된다.

**왜 매일 푸시하나**

- 로컬에만 있는 작업은 없는 것과 같다. 노트북이 죽으면 그대로 날아간다.
- 상대가 뭘 하고 있는지 보인다. 4달짜리 프로젝트에서 이게 제일 크다.
- CI 가 매번 돌아 계약이 깨졌는지 즉시 안다. 일주일 뒤에 알면 못 고친다.

완성해야 푸시하는 게 아니다. **동작하는 지점마다 푸시한다.**

### 자동으로 도는 것

| 워크플로 | 시점 | 하는 일 |
|---|---|---|
| `contract` | `gis` 로 push·PR | 계약 14종 검증. 깨지면 머지 차단 |
| `지도 배포` | `gis` 의 `web/**` 변경 | GitHub Pages 갱신 |

CI 가 데이터를 다시 만들지는 **않는다.** `data/raw` 2.5GB 가 저장소에 없기 때문이다.
파이프라인은 오창준 로컬에서만 돈다.

```bash
uv run python src/etl/ingest.py        # raw → processed (15종)
uv run python src/etl/segments.py      # 노딩 → 폭 → 판정
uv run python src/etl/terrain.py       # 공개DEM → Terrain-RGB 타일
uv run python src/etl/ortho.py         # 항공정사영상 → 배경 타일 (25cm)
uv run python src/etl/publish_web.py   # → web/data
uv run pytest tests/test_contract.py   # 계약 확인
```

이 4줄을 돌린 뒤 `web/data` 를 커밋하면 지혜님이 `git pull` 만으로 새 판정을 받는다.

### 왜 락이 3중인가

| 층 | 막는 것 | 한계 |
|---|---|---|
| `.gitignore` | `data/raw` 커밋 | 이미 있음 |
| `CODEOWNERS` | GIS 코어 무단 수정 | 리뷰 강제일 뿐, 승인하면 통과 |
| **계약 테스트** | **구조 파괴** | **실제로 막는 건 이것** |

CODEOWNERS는 "누가 봐야 하는가"를 정하고, 계약 테스트는 "무엇이 깨지면 안 되는가"를
정한다. 후자가 본체다. 좌표계가 5186으로 나가거나 `verdict`에 새 값이 생기면
CI가 즉시 잡는다.

### 락을 거는 대상은 값이 아니라 스키마다

폭 값은 **미검증 상태(`width_verified: false`)**다. D-25 레이저 실측 후 바뀐다.
값을 얼리면 거짓말이 되고, 스키마를 얼리면 UI가 안 깨진다.

```
얼린다:  좌표계 · 필드명/타입 · verdict 어휘 4종
바뀐다:  width_min_m · width_max_m · 각 구간의 verdict · route_usage
```

실측 후 갱신은 이 순서다. **UI 코드는 손대지 않는다.**

```bash
python src/etl/segments.py       # 폭 재산출
python src/etl/publish_web.py    # web/data 갱신
pytest tests/test_contract.py    # 계약 유지 확인
```

### 4. 지도 스택 결정

**MapLibre GL JS + V-World 타일.** Mapbox도 Naver도 아니다.

- MapLibre는 Mapbox GL v1 포크라 기존 `dongmyeong_map.html` 코드가 거의 그대로 붙는다
- V-World가 한국 배경(건물·지명·지적·항공영상)을 국토부 원본으로 제공한다
- Naver의 "한국 로컬 데이터 풍부" 이점이 사라지고, GeoJSON 데이터 기반 스타일링은
  MapLibre가 압도적이다
- 상가 POI는 `poi_store`로 직접 얹으므로 Naver가 필요 없다

`dongmyeong_map_naver.html`은 갱신 중단. 두 벌 유지가 구버전 폭을 물고 있던 원인이다.

`apply.py` 가 하는 일

```

2. 해시 비교 → 달라지는 파일만 백업
3. 병합 + 잔재 정리
4. pipeline.py 실행
```

## 파이프라인은 한 명령이다

```bash
python src/etl/pipeline.py              # 전체
python src/etl/pipeline.py --check      # 실행 없이 상태만
python src/etl/pipeline.py --from segments   # 그 단계부터 끝까지
python src/etl/pipeline.py --only terrain ortho
```

```
ingest → segments → terrain → ortho → publish → 계약 테스트 → 기대값 대조
```

**단계를 하나씩 손으로 치면 반드시 빠뜨린다.** terrain 을 건너뛰면 지형이 안 뜨고,
publish 를 건너뛰면 지도가 옛 데이터를 본다. 순서도 중요하다 —
publish 는 terrain/ortho 가 기록한 타일 범위를 읽어 보존한다.

실패하면 그 단계에서 멈추고 재개 명령을 알려준다.

끝나면 기대값과 대조한다.

```
세그먼트 1087  OK
  clear      443  OK
  needs_cv   191  OK
  blocked     57  OK
  unknown    396  OK
지형 타일 22장 · 항공영상 388장 · web/data 12MB

이 숫자가 다르면 뭔가 잘못된 것이다. `src/etl/pipeline.py` 의 `EXPECT` 에 있다.

몇 번을 돌려도 결과가 같다. 두 번째부터는 "동일" 로 표시되고 백업도 안 생긴다.

> | 지적도 | 소유권 경계 ≠ 통행 노면 |
>
> (가로등은 2026-08-12 에 확보. 이 표에서 제외한다)
> | 항공정사영상 | 판정에는 미사용. 배경 텍스처 전용 |
>
> **경사는 검토 후 배제했다.** 공개DEM 90m 기준 동명동 표고 33.3~75.3m,
> 기복 42m, 평균 경사 1.8°, 최대 9.0° 로 소방차 등판 한계(11~17°)를 넘지 않는다.
> 경사는 진입 제약 요인이 아님을 확인했다.

# 16. 결정사항

문서와 코드가 다르면 **코드가 정본이고 문서를 고친다.** 아래는 그 반대 방향의
기록이다 — 코드에 들어간 판단 중 문언으로 못박아야 하는 것.

| # | 일자 | 결정 | 상태 |
|---|---|---|---|
| 63 | 08-12 | 폭 소스는 **우선순위 채택**. `ngii1k` > `ngii` > `silpok` | **개정 승인 필요** |
| 64 | 08-12 | 채택 소스를 `width_src` 에 기록한다 | 적용 |
| 65 | 08-13 | 노드 식별에 `NODE_TOL 0.5m` 접합을 적용한다 | **승인 필요** |
| 66 | 08-13 | 교차로 파편은 산출단위로 병합한다. 그래프 `G` 는 불변 | **승인 필요** |
| 67 | 08-13 | snap 은 소스별로 독립 판정한다 | **승인 필요** |
| 68 | 08-13 | `snap_dist <= v/2` 자기일관성 게이트 | **승인 필요** |
| 69 | 08-13 | 구간 폭은 **단일 소스**의 표본만으로 낸다 | **승인 필요** |
| 70 | 08-13 | 폭 미산출 + `ROAD_BT < TRUCK` → `blocked` | **승인 필요** |
| 71 | 08-13 | `seg_id` "불변 키" 문언 폐기. 런 내 불변 | **승인 필요** |

### 63 개정 사유

문언은 "수치지도 주 소스"인데 구현은 3소스 우선순위다. 그리고 결정 63 을
넣고도 **실제로는 주 소스가 무력화되고 있었다**(결정 67 참조). 문언을
구현에 맞춰야 한다.

### 65~66 — 왜 승인이 필요한가

`seg_id` 와 구간 수가 바뀐다. 1266 → 1087. 대외 자료에 1,266 을 쓴 것이
있으면 전부 갱신 대상이다.

### 70 — `ROAD_BT` 금지의 예외

§3-3 에서 `ROAD_BT` 를 폭 값으로 쓰지 않기로 했다. 70 은 그 예외다.
**폭 값으로 쓰는 것이 아니라 "잴 만한 도로인가"의 판정에만 쓴다.**
실측값이 하나라도 있으면 그쪽이 항상 우선하므로 폭 미산출 구간에만 걸린다.

# 17. 작업 원칙

**지킬 것**

```
측정이 안 되면 원인을 찾는다. 통계로 덮지 않는다.
값을 못 내면 회색으로 도망치지 않는다. 정확한 소스로 푼다.
색과 사유를 새로 만들지 않는다.
문서에 적힌 값과 코드가 다르면 코드가 정본이고, 문서를 고친다.
숫자가 바뀌면 EXPECT 를 같이 바꾸고 커밋 메시지에 남긴다.
고치기 전에 검증 게이트를 먼저 정한다. 실패하면 그 안을 버린다.
진단 없이 함수를 고치지 않는다. 사유 코드를 먼저 찍는다.
재구현 진단 스크립트를 만들지 않는다. 파이프라인 안에 계측을 넣는다.
```

**어겼던 것 — 반복 금지**

```
확인 없이 "정상 동작"이라고 판정했다 (08-12, 네 건이 버그였다)
RDS_DPN_SE 를 측도라고 단정했다 (1145건 76% 라 측도일 수 없었다)
min() 대신 5% 분위수를 제안했다 (측정 결함을 분포로 가리려 한 것)
out_of_scope · conflict 로 5번째 색을 두 번 만들었다
같은 함수를 진단 없이 세 번 고쳤다
기준값을 못 뽑아놓고 검증 게이트를 세웠다 (nfa_designated)
미커밋 변경을 워킹트리에 쌓아둔 채 기기를 옮겼다 (같은 수정을 두 번 작성)
