`pipeline.py` 의 `EXPECT["unknown_reason"]` 이 매 실행 이것을 대조한다.

> 판정되고, 그중에도 사각지대가 많다. **골목의 65%는 여전히 영상판정이

## 3. 이 프로젝트가 발견한 것

### 3-1. "222구간"은 근거가 없었다

기존 문서의 세그먼트 수를 검증한 결과 출처를 찾지 못했다.
정식 행정경계로 재산출하여 **641**로 확정했다.

```
도로명주소 도로구간   206
실폭도로              219
노딩 후 세그먼트      641   ← 동명동만 (8/11)
스코프 확장 후       1266   ← 접근 회랑 포함 (8/11)
노드접합·병합 후     1087   ← 현재 판정 단위 (8/13). §3-9 · §3-10
```

179 가 줄어든 것은 도로가 사라진 것이 아니라 **길이 0.0m 짜리 노딩 산출물
224개와 교차로 파편이 정리된 것**이다.

### 3-2. 도로명주소는 위상이 보장되지 않는다

원본은 "도로명 하나 = 선 하나"라 교차로에서 분할되지 않는다.
노딩 후에도 밀리미터 단위 좌표 오차로 구간이 분리된다(**T자 접합**).

| 처리 | 연결요소 | 최대요소 연장비 |
|---|---:|---:|
| 원본 | 40 | 93.29% |
| `set_precision(0.5)` | 22 | 97.74% |
| **끝점 투영 스냅 0.5m** | **6** | **99.76%** |

잔여 5구간(77m)은 알고리즘 한계가 아니라 **도로명 미부여 구간**이다.
그중 3곳이 관리폭 1.0~1.5m로 소방차 진입이 원천 불가하다.
**데이터의 공백 자체가 위험구간 지표다.**

### 3-3. `ROAD_BT`는 폭 값으로 쓰면 안 된다

도로대장의 명목 폭은 **171구간(84%)에서 실측 트랜섹트보다 넓다.**
중앙 차이 +1.00m. 못 지나가는 길을 지나간다고 판정하는 방향이다.

**단, 2026-08-13 부터 한 가지 예외를 둔다.** 폭을 끝내 못 잰 구간에 한해
명목폭이 `TRUCK`(3.0m) 미만이면 `blocked` 으로 확정한다. 폭이 안 나오는 것과
잴 만한 도로가 아닌 것은 다르다. 명목폭 1.0m 짜리 부속 통로를
"CCTV 없어 판정 보류" 회색으로 두면 영상판정으로 메울 수 있다는 뜻이 되는데,
카메라를 갖다 대도 소방차는 못 들어간다. 실측값이 하나라도 있으면
그쪽이 항상 우선하므로 이 규칙은 폭 미산출 구간에만 걸린다(적용 2건). §16 참조.

### 3-4. 폭은 하나로 못 정한다

| 이름 | 데이터 | 성격 |
|---|---|---|
| 노면폭 하한 | 실폭도로 폴리곤 | 확실히 비어 있는 폭 |
| 담~담 상한 | 건물 폴리곤 | 물리적 최대 통로폭 |

담~담이 전 구간에서 넓고 중앙 차이 **+2.08m**. 그 사이에
전신주·화분·실외기·계단·주차 차량이 들어 있다.
**밴드를 좁히는 것이 영상판정과 실측의 역할이다.**

### 3-5. ★ 골목의 64%는 영상판정이 불가능하다

CCTV 유효범위를 25m로 잡으면(25m 초과 시 호모그래피 오차 급증):

```
CCTV 유효범위 안         379 / 1,087  (34.9%)   ← 2026-08-13 기준
CCTV 거리 중앙값          38.6m
최대                      129m
영상판정 불가 구간         195개 · 6,745m (전체 연장의 28%)
```

**영상 기반 진입 판정 시스템을 만들어도 골목의 64%에는 적용할 수 없다.
알고리즘의 한계가 아니라 인프라의 한계다.**

완화 요소: 영상판정 불가 구간이 담당하는 소방 통행량은 **11%**다.
주요 동선에는 대체로 CCTV가 있다.

### 3-6. 출동은 소방서가 아니라 119안전센터에서 나간다

대인(서 1.0km) · 지산(동 1.2km). 둘 다 동명동 밖이다.

```
동 경계 진입점                60곳
실사용 진입점                 23곳
출동 통행의 80%를 담당         5곳
출동 통행의 50%를 담당         2곳
```

**진입점 5곳에 대책을 집중하면 출동의 80%가 개선된다.**

### 3-7. 소화전은 동명동에 1개뿐이다

```
동부소방서 관할   지상식 431 + 일반지하식 157 = 588
공개된 것         31개 (5%)
그중 동명동       1개
```

588 의 출처는 `hydrant_summary`(소방용수시설 현황, 관할서별 5행)다.
**공개 데이터에는 분모가 없다.** 이 표가 유일한 근거이므로 발표에 쓸 때 함께 인용할 것.

데이터 공백 자체가 결과다.

### 3-8. 런타임 프루닝은 폭이 아니라 경로로 한다

정적 폭 기준으로는 61%가 영상판정 대상으로 남는다(동명동이 원래 좁다).
반면 실제 최단경로에 등장하는 엣지는:

```
1회 이상 사용        665 / 4,227  (15.7%)
통행량 80% 담당      177개  (4.2%)
통행량 50% 담당       71개  (1.7%)
```

**71개 엣지가 출동 통행의 절반을 처리한다.** 여기부터 영상판정을 걸면 된다.

### 3-9. ★ 길이 0.0m 짜리 구간 40개가 "통행 가능"으로 표출되고 있었다

노딩이 노드를 **밀리미터 반올림**으로 식별했다. 4cm 떨어진 두 점이 별개 노드가
되고 그 사이에 길이 0.04m 짜리 엣지가 생긴다. §3-2 에서 T자 접합에
`SNAP_TOL 0.5m` 관용을 줬으면서 노드 식별에는 안 줬던 것이다.

`NODE_TOL 0.5m` 로 끝점을 묶자 자기루프 224 개가 사라졌다.

```
엣지 3675 → 3444        노드 최대이동 0.359m
판정 변화  clear -40 · needs_cv -10 · blocked ±0 · unknown -40
```

**폭 미산출 51 개만 문제인 줄 알았는데 나머지 절반은 조용히 초록으로 통과하고
있었다.** `blocked` 이 0 변동인 것이 접합이 실제 좁은 구간을 지우지 않았다는 증거다.

### 3-10. ★ 교차로 안에서는 그 도로의 폭을 잴 수 없다

교차로 안의 한 점에서 도로 A 에 수직으로 법선을 그으면, 그 법선은 **교차하는
도로 B 를 따라 길이 방향으로 달린다.** 나오는 값은 폭이 아니라 "도로 B 가
60m 안에서 얼마나 뻗어 있나"다.

```
제봉로          3.3m 구간 → 폭 55.39m
필문대로218번길  4.2m 구간 → 폭 45.63m
경양로          7.3m 구간 → 폭 45.33m
```

기하학적으로 정의되지 않는 것이지 측정 기법의 한계가 아니다.
그래서 교차로 파편은 **독립 피처로 두지 않고** 동일선상(30° 이내) 이웃과
하나의 산출단위로 묶는다. 그래프 `G` 는 라우팅·교차로 노드 정본이므로
손대지 않고, 산출 단위만 병합한다.

> 이 문제를 "교차로 제외를 풀고 재기"로 풀려다 폐기했다. 큰 값은 눈에 띄어
> 걸러지지만 `동계로1번길 7.03` `동명로98번길 7.31` 처럼 임계 7.0 을 간신히
> 넘겨 `clear` 가 된 골목들이 그럴듯한 채로 지나간다. **반복 금지.**

### 3-11. ★ 폐기한 `min()` 이 표본 축에 남아 있었다

결정 63 으로 소스 축의 `min()` 은 폐기했는데, 구간 폭을 내는
`wmin = min(A)` 의 `A` 는 **표본마다 다른 소스가 채택된 혼합 집합**이었다.
표본 1 이 1:1,000 의 3.2m, 표본 2 가 실폭도로의 1.8m 인데 그 둘의 최솟값을
구간 폭이라고 불렀다.

값을 낸 최우선 소스 하나로 고정하고 그 소스의 표본만으로 최솟값을 낸다.

```
채택 소스   ngii1k 1014 · silpok 84 · ngii 1 · null 2     ← 2026-08-18 확정
            ngii1k  925 · ngii 131 · silpok 29 · null 2    ← 2026-08-13

★ `silpok` 폴백이 베이스라인과 같은 84 다. 구 원본(NGI 20도엽)이 덮던
  범위를 V-WORLD 74 + NGI 143도엽이 온전히 대체했다는 뜻이다.

★ `ngii` 가 사실상 이탈했다(131 → 1). 버그가 아니라 제품 교체의 결과다.
  B030 국가기본공간정보 → B020 연속수치지도로 바뀌면서 도로경계면 밀도가
  줄었다(스코프 내 216건). 레이어명도 NF_A_A01000 → N3A_A0010000 이다.
  `ngii1k` 가 그 자리까지 덮어 폭 산출 자체에는 영향이 없다.
  `rvwd`(도로폭 속성)는 소실이 아니라 도로중심선 N3L_A0020000 으로
  옮겨갔다 — `datasets.ngii_road_center` 로 등재했고 교차검증에 쓸 수 있다.

> ### 08-17 서술 정정
>

### 왜 나눴나 (2026-08-18)

`segments.py` 는 1,168줄이었고 `main()` 하나가 1,041줄이었다. 중첩 함수 8개가
바깥 로컬을 폐포로 잡고 있어 **단위 테스트가 물리적으로 불가능**했다.
`verdict`(이 프로젝트의 결론), `widths`(폭 소스 우선순위), `road_name`
(도로명 되붙이기) 셋 다 테스트가 0개였다.

나눈 기준은 취향이 아니라 **폐포 의존성 실측**이다. AST 로 각 중첩 함수가
잡는 바깥 이름을 세어, 항상 같이 움직이는 것끼리 묶었다.

    폐포 5    _rn_geo/_rn_nm/_rn_dpn/_rn_bt/_rn_tree → seg/roadname (RoadNameIndex)
    폐포 6    ngii1k_u · ngii_u · rw_u · bld_u · xn · xsec_poly → seg/width (WidthEngine)

산출물이 바뀌지 않았다는 것은 `tools/golden.py` 가 단계마다 증명했다.
지문 `846422a86f541bf1` · 1101구간 · 판정 분포 전부 동일.

## 6-2. 데이터 보관 전략

### 현재 — 로컬 + 환경변수

```
data/raw        2.2GB · 저장소 밖 · FIRE_LANE_RAW 로 위치 지정
data/processed  로컬 생성물 · *.gpkg / *.tif 는 git 제외
web/data        13MB · git 포함 (UI 담당이 raw 없이 작업해야 한다)
```

**심링크는 쓰지 않는다.** `data/raw` 를 심링크로 걸었더니 git 이 추적했고,
exFAT 에서 `git reset --hard` 시 경로 문자열 파일로 체크아웃되면서
원본 2.5GB 가 소실됐다(2026-08-11). `src/etl/paths.py` 의 환경변수 방식으로 대체했다.

```bash
export FIRE_LANE_RAW="/mnt/f/.../FIRE_LANE/data/raw"     # 리눅스
setx FIRE_LANE_RAW "D:\...\FIRE_LANE\data\raw"        # 윈도우
```

미설정 시 `<repo>/data/raw` 를 쓴다. 단일 머신이면 그걸로 충분하다.

`web/data` 는 CI 가 **60MB 상한**을 감시한다. 타일이 늘어 넘으면 머지가 막힌다.

### 향후 — AWS S3

raw 를 S3 로 옮기고 GitHub Actions 와 엮으면 데이터 파이프라인이 완성된다.

```
S3  fire-lane-gis-raw/        원본
    fire-lane-gis-processed/  중간 산출물
Actions  raw 갱신 감지 → ingest → segments → publish → Pages 배포
```

`paths.py` 만 `s3://` 를 받도록 고치면 되고, 나머지 스크립트는 그대로다.
그래서 지금 환경변수로 분리해둔 것이다.

**다만 지금은 이르다.** 2.2GB 를 위해 S3 비용과 IAM·CI 설정을 감수할 단계가 아니고,
D-25 실측과 A* 가 먼저다. 4달 일정 중반쯤 파이프라인이 안정되면 옮긴다.

### 3-9. 단속 이력의 쓰임 — 시간대는 못 쓰고 빈도는 쓴다

```
85,380건 · 2022-01 ~ 2023-10 · 위반장소명(도로명주소) 보유
고유 장소 2,123개

매일 푸시를 권장한다. 완성해야 푸시하는 게 아니라 동작하는 지점마다 푸시한다.
**미커밋 변경을 워킹트리에 쌓아두지 않는다** — 8/12~13 에 기기를 옮기며
같은 수정을 두 번 작성한 일이 있었다.

## 9. 이 프로젝트의 성격

숫자를 만들어내는 것이 아니라 **어디까지 알 수 있고 어디부터 모르는지를 긋는 것**이다.

- 골목의 42%는 도면만으로 판정이 안 된다 → 주황으로 표시한다
- 그중 다시 64%는 CCTV가 없어 영상판정도 안 된다 → 회색으로 표시한다
- 폭 값은 실측 전이다 → 화면 상단에 상시 경고한다

**모르는 것을 모른다고 표시하는 것**이 이 지도의 설계 원칙이다.
전부 초록으로 칠하면 첫 질문에 무너진다.

### 판정 4종

| 색 | 라벨 | 기준 | 뜻 |
|---|---|---|---|
| 초록 | 통행 가능 | 최소 폭 ≥ 7.0m | 양쪽에 주차가 있어도 통과. 영상판정 불필요 |
| 주황 | **판정 보류** | 그 사이 | **상습주차 여부로 갈린다. 영상판정 대상** |
| 빨강 | 통행 불가 | 최대 폭 < 3.0m | 중형펌프차 폭 미달. 장애물이 없어도 못 지나간다 |
| 회색 | 영상판정 불가 | — | CCTV 25m 밖. 카메라가 없어 못 본다 |

**색은 4종 고정이다.** `unknown_reason` 은 회색의 하위 구분이지 다섯 번째
색이 아니다. 범례에 별도 줄로 올리지 않는다 — 색이 5종으로 보이고
합계도 안 맞아 보인다. 하위 구분은 툴팁이나 상세 패널에 넣는다.

> 8/12 에 `out_of_scope` 와 `conflict` 로 5번째 색을 두 번 만들었다가 둘 다
> 지웠다. 8/13 에는 범례에 `CCTV 없어 보류` 갈색 줄이 올라가 있던 것을
> 내렸다. **다시 만들지 마라.**

#### 기준의 출처

임의로 정한 값이 아니다. **소방청 「2025 화재현장 골든타임 확보 종합대책」**을 따른다.

```
진입불가지역   폭 2m 이하, 또는 이동불가 장애물로 진입 불가한 구간이 100m 이상
진입곤란지역   폭 3m 이상 도로 중 장애물·상습주차로 상시 장애, 구간 100m 이상
기준 차량      중형펌프차량 폭 2.5m
```

```
TRUCK = 3.0     차량 전폭 2.5 + 미러·조향 여유 0.5
PARK  = 2.0     주차 1대 노면 점유
blocked   최대 폭(담~담) < 3.0
clear     최소 폭 >= 3.0 + 2 x 2.0 = 7.0
```

`clear` 는 **양쪽 주차**를 가정한다. 한쪽만 가정하면 5.0m 지만, 양방 주차가
상시인 골목에서 한쪽만 보는 것은 낙관 방향이다.
"왜 하필 그 숫자냐"는 질문에 국가 기준 + 명시된 여유값이라고 답할 수 있다.

#### 연속 구간 (`run_length_m`)

소방청 지정 기준의 **"구간 100m 이상"**은 세그먼트 하나가 아니라
같은 판정이 이어지는 **연속 구간 전체**의 길이다. 5m짜리 조각 하나로는 지정되지 않는다.

```
소방청 지정 기준 충족   139구간
연속 구간 최장           505.5m
```

`nfa_designated`가 `true`면 툴팁에 표시된다.

**주황 191개가 이 프로젝트의 미완성 부분이다.** 전체의 17.6% 다.
영상판정이 붙으면 이 191개가 초록·빨강으로 갈린다.
회색 396개는 영상판정으로도 안 갈린다 — CCTV 배치가 선행돼야 한다.

### 폭이 왜 두 개인가

같은 골목을 두 가지로 잰다. 하나로 못 정하는 게 아니라 **둘 사이가 답이기 때문**이다.

| 화면 표기 | 필드명 | 데이터 | 뜻 |
|---|---|---|---|
| **최소 폭** | `width_min_m` | 실폭도로 폴리곤 | 장애물이 없을 때 확실히 비어 있는 폭 |
| **최대 폭** | `width_max_m` | 건물 폴리곤 | 양쪽 건물 벽 사이 거리. 물리적 최대 |

> 이전에 쓰던 "노면폭 하한 / 담~담 상한"은 **최소 폭 / 최대 폭**으로 통일했다.
> 문서·UI·발표 자료 전부 이 표기를 쓴다.

최대 폭이 최소 폭보다 **전 구간에서** 넓고 중앙값 차이가 2.08m다.
그 사이에 전신주·화분·에어컨 실외기·계단·주차 차량이 들어 있다.

3.0m 기준으로 보면 **최소 폭 기준 125구간 vs 최대 폭 기준 35구간**이 걸린다.
즉 90구간(47%)은 어느 쪽을 믿느냐에 따라 판정이 뒤집힌다.
**이 밴드를 좁히는 것이 영상판정과 현장 실측의 역할이다.**

> `ROAD_BT`(도로대장의 명목 폭)는 쓰지 않는다. 실측 대비 84% 구간에서
> 1m씩 넓게 나온다. 못 들어가는 길을 들어간다고 판정하는 방향이라 가장 위험하다.

### 소방 동선 (`route_usage`)

**이 골목을 소방차가 얼마나 자주 지나는가.**

119안전센터 2곳(대인·지산)에서 동명동 건물출입구 358곳까지
최단경로를 **전부** 계산한 뒤, 각 골목이 몇 개의 경로에 등장하는지 센 값이다.

**선 굵기는 이 값이 아니다.** 선 굵기는 최소 폭이다(아래 참조).

> 소방 동선은 현재 지도 화면에서 빼두었다. `route_usage` 필드는 데이터에 남아 있으므로
> 필요할 때 다시 꺼내 쓸 수 있다. 프루닝 근거로는 계속 유효하다.

```
1,087개 중 실제로 쓰이는 것           567개
출동 통행의 50%를 담당하는 골목        71개
출동 통행의 80%를 담당하는 골목       177개
```

**왜 중요한가.** 영상판정을 1,087개 전부에 돌리면 출동할 때마다 계산이 쌓인다.
실제로 밟히는 골목만 보면 대상이 확 준다. 이게 프루닝이다.

### 선 굵기 = 최소 폭

화면의 선 두께가 곧 그 골목의 폭이다. 미터 단위로 그려지므로
확대·축소해도 실제 비율이 유지된다. 굵은 선이 넓은 길이다.

폭을 못 잰 구간(회색)은 최소 굵기로 가늘게 그린다.

### 길이 (`length_m`)

그 구간의 **수평거리**(m). 평면 좌표계(EPSG:5186)에서 잰 값이다.

**경사 보정 전이다.** 실제 주행거리는 `수평거리 / cos(경사)` 이므로 더 길다.

```
동명동 평균 경사 1.8°  →  실주행거리 +0.05%   (100m 당 5cm)
최대 경사      9.0°  →              +1.2%    (100m 당 1.2m)
```

무시할 만한 수준이지만 **"같다"가 아니라 "차이가 이만큼이고 반영하지 않았다"** 가 정확하다.
보정하려면 구간별 경사가 필요하고, 그러려면 5m DEM 이 있어야 한다.
공개DEM 90m 로는 한 픽셀이 골목 20개를 덮어 산출이 불가능하다.

**폭은 경사 영향을 받지 않는다.** 폭은 진행 방향과 수직으로 재므로
도로가 기울어도 좌우 거리는 변하지 않는다. 다만 횡단경사(편경사)가 있으면
유효폭이 줄어드는데, 이 역시 90m 격자로는 잡을 수 없다.

### 세그먼트 / 노딩

**세그먼트** = 교차로에서 잘라낸 도로 조각. 판정의 기본 단위다.

원본 데이터(도로명주소 도로구간)는 "도로명 하나 = 선 하나"라
제봉로가 중앙로를 가로질러도 통짜 한 줄이다. 그대로는 경로 탐색이 안 된다.
교차점마다 잘라서 그래프로 만드는 것이 **노딩**이다.

```
원본 도로구간   206개
노딩 후         641개 세그먼트   ← 동명동만
접근 회랑 포함  1,266개
노드접합·병합   1,087개          ← 현재 판정 단위
```

> 기존 문서의 "222구간"은 근거를 찾지 못했다. 641 → 1,266 → 1,087 로 바뀌었다.
> **구간 수는 고정값이 아니다.** 노딩 규칙이 바뀌면 바뀐다.

### 스코프

지도가 보여주는 범위. **동명동 + 접근 회랑 + 안전센터 반경 300m**, 약 2.8 × 1.4km.

동명동만 보면 안 되는 이유는 **119안전센터가 동 밖에 있기 때문**이다
(대인 서쪽 1.0km · 지산 동쪽 1.2km). 출동 경로가 화면에서 잘린다.

**접근 회랑** = 안전센터에서 동명동까지 오는 길. 최단경로 중 동 밖 구간이다.
광주 전체가 아니라 얇은 리본이다.

화면 밝기가 3단계다.

```
동명동      밝게        판정 대상
접근 회랑   살짝 어둡게  오는 길
그 밖       덮음        스코프 밖
```

이 범위 밖으로는 이동도 축소도 안 된다. 작업 범위가 구조적으로 고정된다.

### 시설 마커

마커는 전부 **3D 입체**다. 2D 점은 기울인 화면에서 지면에 붙어 안 보인다.
원기둥 3~4개를 쌓아 실제 시설의 실루엣을 근사한다.

| 마커 | 색 | 형상 | 건수 |
|---|---|---|---|
| **119안전센터** 출동 시작점 | 빨강 | 기둥 + 헤드 + 첨두 | 2 |
| 동부소방서(본서) | 주황 | 본체 + 안테나 | 1 |
| 소화전 | 파랑 | 받침 + 몸통 + 플랜지 + 캡 | 11 (동명동 **1**) |
| CCTV | 보라 | 지주 + 하우징 + 렌즈 | 104지점 312대 |
| 가로등 | 회색+주황 | 지주 + 암 + 등기구. **굵기 = √(등 수)** | 46지점 573등 |

**비율은 실물을 따르되 크기는 약 5배 과장했다.** 소화전 실물은 0.9m라
실제 치수로 그리면 1km 시야에서 점 하나가 되어 보이지 않는다.

소화전이 안 보인다면 버그가 아니라 **동명동 안에 1개뿐**이기 때문이다.

**커버리지 원은 마커마다 의미가 다르다.**

```
CCTV   실선   반경 25m         "이 범위를 본다"
가로등  점선   반경 50m         "폴이 이 안 어딘가에 있다"
```

CCTV 는 촬영방면이 전부 360도라 방향 콘이 아니라 원이다.
**커버리지가 닿지 않는 골목**을 보이게 하는 것이 목적이다.
가로등 원은 정반대로 **좌표의 부정확성**을 그린 것이다. 지번 단위 대표점이라
실제 폴 위치가 아니다. 의미가 반대이므로 선 종류로 구분한다.

> CCTV 원본은 설치연도별로 행이 쪼개져 있다. 동명동 53행이 실제로는 29지점 90대다.
> 좌표로 묶어 지점 단위로 집계했고, `설치회차`에 증설 횟수가 남는다.

**소화전이 동명동에 1개인 것은 버그가 아니다.**
동부소방서 관할 588개 중 공개된 것이 31개(5%)뿐이고 그중 동명동이 1개다.
이 희소성 자체가 발표 논거다. 패널의 `1 / 11`이 그 표기다.

**가로등 마커는 지점당 등 수를 굵기로 표현한다** (2026-08-14 개정, §6 · 결정 83).
스코프 내 46지점 573등이고 지점당 중앙 12등 · 최대 41등이다.
`distinct` 로 좌표당 1행만 남기면 등 수의 93% 가 사라지므로 금지한다.
좌표가 지번 대표점이라 반경 50m 점선 원을 같이 그려 불확실성을 드러낸다.

### `config.js` — 지혜님이 만지실 값

**2026-08-14 구조 변경.** 마커를 추가할 때 6곳을 고쳐야 했던 것을 고쳤습니다.
이제 **마커에 관한 모든 것이 `config.js` 한 곳**에 있습니다.
`app.js` 는 이 선언을 읽어 실행만 합니다.

```js
/* 판정 색상. style.css 의 --blocked 등과 같은 값을 유지할 것 */
verdict: {
  blocked : { color:[255, 77, 61], label:"통행 불가", desc:"…" },
  needs_cv: { color:[255,171, 46], label:"판정 보류",   desc:"…" },
  clear   : { color:[ 74,209,143], label:"통행 가능", desc:"…" },
  unknown : { color:[ 90, 98,114], label:"판정 불가",   desc:"…" },
},

noCctvColor: [168,132,78],   // CCTV 사각으로 죽은 구간. 주황+회색 혼합

/* 출동 모드 — 지혜님 기능 */
dispatch: {
  clearWidthScale: 1.6,   // 통과 구간 선 굵기 배수

  pulseMs        : 1200,  // 소화전 물결 주기(ms). 작을수록 빠르다
},

minimap: { showFromZoom: 16 },   // 이 줌 이상에서 미니맵이 뜬다
markers: [ … ],                  // 마커 — 아래 참조

#### 마커 스펙 — 한 덩어리가 자기 것을 전부 든다

```js
{ id:"m-light",              // 레이어 식별자. 토글 data-t 와 같은 값
  label:"가로등",             // 범례·토글에 뜨는 이름. 여기가 정본
  data:"streetlights",       // web/data/{이름}.geojson 을 자동으로 읽는다
  kind:"center",             // (선택) 같은 파일에서 properties.kind 로 거를 때

  /* (선택) 값에 따라 굵기를 바꾼다. by = 속성명 */
  scale:{ by:"n_lights", mode:"sqrt", k:0.28 },

  /* (선택) 반경 원을 같이 그린다. 토글과 함께 켜지고 꺼진다.
     radius  고정 반경(m)          — CCTV 25m
     by      속성에서 반경을 읽음   — 가로등 pos_accuracy_m
     style   "solid" | "dashed"
     color   색. themed 가 있으면 그쪽이 우선
     themed  CONFIG 의 다른 키에서 색을 가져온다(라이트/다크 전환용) */
  cover:{ by:"pos_accuracy_m", style:"dashed", color:"#ffd678" },

  /* (선택) 클릭 팝업. 여기가 정본입니다. app.js 에 POPUP 딕셔너리는 없습니다 */
  popup: p=>`<b>가로등</b> ${p.n_lights}등`,

  /* 3D 형상. 원기둥(r) 또는 박스(hw/hl) 를 쌓습니다.
     z = 바닥 높이, h = 그 조각의 높이, c = [r,g,b] */
  parts:[ {r:0.35, z:0, h:11, c:[120,124,138]}, … ] }
```

#### 마커를 추가하려면

```
1. 데이터를 web/data/{이름}.geojson 으로 발행한다 (GIS 담당)
2. config.js 의 markers 에 스펙 한 덩어리를 추가한다
```

**끝입니다.** 토글 행·팝업·데이터 로딩은 `app.js` 가 `config.js` 를 읽어
자동으로 만듭니다. `index.html` 도 안 고쳐도 됩니다.

> 계약 테스트 `test_marker_spec_self_contained` 가 이 구조를 지킵니다.
> `app.js` 에 손딕셔너리(`MK_SRC`·`POPUP`)나 마커 id 특수분기가 되살아나면
> 테스트가 실패합니다. 그때는 선언으로 빼주세요.

#### 굵기(`scale`)의 뜻

```
mode:"sqrt"   반지름 ∝ √값.  면적이 값에 비례해 보인다
k             배수 계수. 1등=1.0 배, 41등=약 2.7 배
```

★ **높이로 표현하지 않습니다.** 가로등 41등을 높이로 그리면
"41층짜리 가로등"이 되어 시설 위계가 무너집니다.

#### 원(`cover`)의 뜻은 마커마다 다릅니다

```
CCTV   실선   "이 범위를 본다"          radius 25m
가로등  점선   "폴이 이 안 어딘가에 있다"  by pos_accuracy_m (50m)
```

**의미가 정반대라 선 종류로 구분합니다.** 범례에도 그렇게 적어주세요.
가로등 좌표는 지번 단위 대표점이라 실제 폴 위치가 아닙니다.

**임계값(3.0 / 7.0 / 25.0)의 정본은 `src/etl/segments.py` 입니다.**
`config.js` 의 같은 숫자는 화면 설명용 사본이라 바꿔도 판정은 안 바뀝니다.

**3D 마커** — 119안전센터 · 소방서 · 소화전 · CCTV. 원기둥을 쌓아 실루엣을 만듭니다.
비율은 실물, 크기는 약 5배 과장했습니다. 소화전 실물이 0.9m 라 실제 치수로는 안 보입니다.

**지형** — 공개DEM 90m 를 보간한 Terrain-RGB 타일. 지면이 실제로 휩니다.
동명동은 2.8km 에 기복 42m 라 완만합니다. `exaggeration` 기본은 **1.0(실제 비율)** 입니다.
올리면 보기는 좋아지지만 표고가 왜곡되므로, 발표에 쓸 때는 그 사실을 명시해야 합니다.

### 값은 바뀝니다. 구조는 안 바뀝니다.

폭 값은 아직 **미검증**입니다(`width_verified: false`). 레이저 실측 후 바뀌고,
일부 구간의 `verdict` 도 바뀝니다.

그때 UI 를 다시 만들지 않으려면 세 가지만 지키면 됩니다.

**1. 숫자가 아니라 `verdict` 문자열로 분기**

```js
if (p.verdict === "blocked") …     // 이렇게
if (p.width_max_m < 3.0)  …        // 이러면 안 됨
```

**2. 색 매핑은 `config.js` 한 곳에만**

**3. `verdict` 는 이 4개가 전부**

`tests/test_contract.py` 가 CI 에서 검증합니다. 깨지면 머지가 막힙니다.

| 항목 | 보장 |
|---|---|
| 좌표계 | `EPSG:4326` 고정 |
| 필드명·타입 | 고정 |
| `verdict` 어휘 | 4종 고정 |

> **`seg_id` 는 불변 키가 아니다.** 런 내에서만 불변이다. 노딩·병합 결과가
> 하나만 달라져도 전부 밀린다. UI 상태(선택·북마크·필터)의 영구 키로 쓰면
> 다음 파이프라인 실행에 깨진다. 영구 식별이 필요하면 `road_name` + 좌표를 쓸 것.

- 로컬에만 있는 작업은 없는 것과 같다. 노트북이 죽으면 그대로 날아간다.

### 왜 락이 3중인가

| 층 | 막는 것 | 한계 |
|---|---|---|
| `.gitignore` | `data/raw` 커밋 | 이미 있음 |
| `CODEOWNERS` | GIS 코어 무단 수정 | 리뷰 강제일 뿐, 승인하면 통과 |
| **계약 테스트** | **구조 파괴** | **실제로 막는 건 이것** |

CODEOWNERS는 "누가 봐야 하는가"를 정하고, 계약 테스트는 "무엇이 깨지면 안 되는가"를
정한다. 후자가 본체다. 좌표계가 5186으로 나가거나 `verdict`에 새 값이 생기면
CI가 즉시 잡는다.

### 락을 거는 대상은 값이 아니라 스키마다

폭 값은 **미검증 상태(`width_verified: false`)**다. D-25 레이저 실측 후 바뀐다.
값을 얼리면 거짓말이 되고, 스키마를 얼리면 UI가 안 깨진다.

```
얼린다:  좌표계 · 필드명/타입 · verdict 어휘 4종
바뀐다:  width_min_m · width_max_m · 각 구간의 verdict · route_usage
```

실측 후 갱신은 이 순서다. **UI 코드는 손대지 않는다.**

```bash
python src/etl/segments.py       # 폭 재산출
python src/etl/publish_web.py    # web/data 갱신
pytest tests/test_contract.py    # 계약 유지 확인
```

### 3. 오늘 확인된 것 — 기존 문서와 어긋나는 부분

#### ★ 3-1. 도로구간이 교차로에서 안 끊겨 있다 (D-05)

```
도로명주소 도로구간   교차 노드    19개 / 미분할 접점 2,338개   ← 그래프 성립 불가
표준노드링크         교차 노드   452개 / 미분할 접점     7개   ← 정상
```

도로명주소는 "도로명 하나 = 선 하나"라 제봉로가 중앙로를 가로질러도 통짜 한 줄이다.
**노딩 없이 networkx에 넣으면 다익스트라가 "경로 없음"을 뱉는다. 코드 문제가 아니다.**

노딩 결과(bbox 기준): `1,812 → 4,336 세그먼트 / 노드 3,702 / 연결요소 338개(최대 80%)`

> **"222구간"의 근거를 찾지 못했다.** 정식 행정경계 확보 후 재산출하여 전 문서를 교체할 것.

#### ★ 3-2. 도로폭 소스 3종이 서로 다른 값을 준다

동일 구간(`ROAD_BT`=2.0)을 세 방법으로 측정:

| 소스 | 폭 |
|---|---:|
| `ROAD_BT` (명목값) | 2.00 |
| 실폭도로 `TL_SPRD_RW` 트랜섹트 | 1.76 |
| 수치지도 `NF_A_A01000` 트랜섹트 | 3.86 |

**`ROAD_BT` 사용 금지 확정.** 정수 비율 90%, 값의 30%가 정확히 2.0에 몰려 있다.
실측값이 아니라 도로명 부여 기준의 명목 관리 폭이다.
게다가 실제보다 **크게** 나오는 방향이라 D-03의 미탐(막혔는데 통과 판정) 쪽으로 편향된다.
가장 위험한 방향이다.

수치지도가 실폭도로보다 넓게 나오는 이유는 대상이 다르기 때문이다
(수치지도=포장면 전체, 실폭도로=도로명주소 관리 실폭).
**어느 쪽이 맞는지는 현장 실측만이 판정할 수 있다.**
8/6 실측은 GPS 미기록으로 무효 처리된 상태이므로, D-25 레이저 거리계 확보 후 재실측이
우선순위 1번인 이유가 이것이다.

#### 3-3. 수치지도는 최협소 골목을 그리지 않는다 (문서 §4 확인됨)

표본 100개 중 **70개만** 도로경계면 폴리곤이 존재. 나머지는 `road_rw` 폴백 필요.
문서의 "수치지도 207 + 실폭도로 폴백 14 = 221/222" 구조가 실측으로 재확인됐다.

#### 3-4. `rvwd` 컬럼 — 문서에 없던 것

수치지도 도로경계면에 도로폭 속성이 있다. `1.5 ~ 46.0m`, 정수 비율 76%
(`ROAD_BT`는 90%). `ROAD_BT`보다 세분화돼 있다.
**지오메트리 계산과 병행해 교차검증용으로 쓸 것.** 둘이 크게 어긋나는 구간이 계산 오류 구간이다.

#### 3-5. 교차로 blob 문제 재현

```
천변좌로434번길  ROAD_BT 2.0 → 수치지도 트랜섹트 60.00m
필문대로         ROAD_BT 4.0 → 수치지도 트랜섹트 56.01m
```

중심선이 교차로 폴리곤 위를 지나며 폭이 폭발한다(문서 §4 "최대 39m 관측"과 동일 현상).
**해법은 최솟값을 쓰는 게 아니라 교차로를 빼는 것이다.**
노드 반경 5m 안의 샘플을 버린 뒤 최솟값을 잡아야 한다. 현재 `width_min_m` 정의에 이 조건이 없다.

#### 3-6. 전남광주통합특별시 개편 (2026-07-01)

시군구 코드가 전면 변경됐다.

| | 구 | 신 |
|---|---|---|
| 광주 동구 | 29110 | **12210** |
| 시도 | 29 | **12** |

기존 파이프라인이 `29110`으로 필터링하면 **오늘 받은 데이터에서 아무것도 안 걸린다.**
단 상가정보의 `건물관리번호`는 구 코드(`2911...`)를 유지하므로 조인키로는 유효하다.

#### 3-7. 숫자 정정

| 항목 | 기존 문서 | 실제 |
|---|---|---|
| CCTV | 53개소 | **고유 27지점 / 카메라 86대** (설치연도별 행 분리 탓) |

#### 3-8. 소방서가 아니라 119안전센터가 출발점

**출동은 안전센터에서 나간다.** 동명동은 서쪽(대인 1.0km)·동쪽(지산 1.2km) 양방향

문서 §5의 소방서 하드코딩 좌표(126.922737, 35.136010)와 다르므로 확인 필요.

#### 3-9. 단속 이력 시간 필드 오염

입력 기본값이다. **시간대 분석에 쓸 수 없다.** 문서 §10의

### 4. 지도 스택 결정

**MapLibre GL JS + V-World 타일.** Mapbox도 Naver도 아니다.

- MapLibre는 Mapbox GL v1 포크라 기존 `dongmyeong_map.html` 코드가 거의 그대로 붙는다
- V-World가 한국 배경(건물·지명·지적·항공영상)을 국토부 원본으로 제공한다
- Naver의 "한국 로컬 데이터 풍부" 이점이 사라지고, GeoJSON 데이터 기반 스타일링은
  MapLibre가 압도적이다
- 상가 POI는 `poi_store`로 직접 얹으므로 Naver가 필요 없다

`dongmyeong_map_naver.html`은 갱신 중단. 두 벌 유지가 구버전 폭을 물고 있던 원인이다.

## 파이프라인은 한 명령이다

```bash

python src/etl/pipeline.py --from segments   # 그 단계부터 끝까지
python src/etl/pipeline.py --only terrain ortho
```

```
ingest → segments → terrain → ortho → publish → 계약 테스트 → 기대값 대조

**단계를 하나씩 손으로 치면 반드시 빠뜨린다.** terrain 을 건너뛰면 지형이 안 뜨고,
publish 를 건너뛰면 지도가 옛 데이터를 본다. 순서도 중요하다 —
publish 는 terrain/ortho 가 기록한 타일 범위를 읽어 보존한다.

실패하면 그 단계에서 멈추고 재개 명령을 알려준다.

지형 타일 22장 · 항공영상 388장 · web/data 12MB

### 71 완료 — 72 로 대체

`seg_id` "불변 키" 문언을 폐기하고 `seg_uid` 를 신설했다. `seg_id` 는 실행 내
표시용 일련번호로 강등한다. **외부 참조 금지.**
형식 `DM-192745-283620-WQ35` (지역-중점X-중점Y-도로명해시).
게이트는 `NODE_TOL`/`SNAP_TOL` 0.5→0.6 흔들기에서 유지율 90% 이상이며
실측 99.4%(1087 중 6개만 갈림)였다. sha 는 바뀌었으므로 기하는 실제로 흔들렸다.

### 73 — 왜 구간 단위가 아닌가

굽은 골목은 지점마다 도로가 뻗은 방향이 다르다. 밤실로4번안길 37m 구간에서
75.2° → 73.9° 로 돌아간다. 구간 하나에 방위 하나를 주면 끝부분에서 횡단선이
비스듬히 잘려 폭이 과대추정된다. **새 데이터가 필요 없다. 중심선에서 나온다.**

### 79 — 왜 커버율로 '고르지' 않는가

실폭도로가 커버율 0.955 로 가장 높다. 커버율로 소스를 고르면 그것이 항상 이겨
**결정 63 이 정면으로 뒤집힌다.** 그래서 우선순위는 유지하고 **자격 미달만
거른다.** 탈락하면 다음 순위가 자동으로 올라간다.

근거: 정상 구간의 채택소스 커버율은 중앙 1.0 · p10 0.667 인데 `width_min>30m`
이상값 43건은 0.038~0.286 이다. **두 무리가 겹치지 않는다.**
준법로(DM01608)는 `ngii` 가 26표본 중 1개(cov 0.038)를 쟀고 그 값이 53.2m 로
구간 폭이 됐다. 나머지 23개는 `silpok` 1.30m 였다. 적용 후 1.3m 로 정정됐다.

### 80 — blocked 는 왜 유지하는가

표본이 하나면 커버율이 자동으로 1.0 이 되어 `COV_MIN` 검사도 통과한다.
`clear` 는 "영상판정조차 불필요"라는 가장 강한 주장이라 근거가 필요하다.
`blocked` 는 막는 쪽이므로 표본 1개여도 유지한다(§4-4 미탐:오탐 = 100:1).

★ `widths()` 에서 `None` 을 반환하는 방식으로 시도했다가 3m 미만 구간이
  `fragment` 로 떨어져 **44개가 산출물에서 사라지는 것**을 발견하고 원복했다
  (1087→1043). 판정 단계에서 막아야 한다.

### 81 — 고정 반경이 왜 틀렸나

`XSEC_EXCL 5.0m` 은 근거 없는 임의값이었다. 실제 교차부 등가반경은 **중앙 3.2m · p90 7.5m** 라
작은 교차부는 과잉 제외로 표본을 죽이고, 큰 교차부는 오염이 샜다.
동명로25번길 t=29·31(끝에서 5.1m)이 후자다.

`A0080000` 평면교차점으로 대체한다. 폴리곤이 10m 안에 있으면 폴리곤만 신뢰하고,
없는 교차로만 반경 폴백. 과잉 제외로 `fragment` 로 죽던 구간이 살아나 1080→1123,
짧은 조각의 교차부 예외까지 제거해 최종 1102.

★ `or` 로 반경 폴백을 항상 같이 걸면 폴리곤이 무의미해진다. 한 번 실패했다.

### 82 — 0.500 을 결측 처리하면 안 되는 이유

폭 0.5m 도로는 없으므로 결측으로 보였다. **스코프 내 7건을 전수 확인했다**
(네이버 거리뷰·지도, 2026-08-14).

```
지산동 산17-1 일대 4건   무등산 등산로. 네이버 지도에 도로 표기조차 없다
동명동 25       1건       볼라드 + 난간으로 차량 차단
중앙로 253-13   1건       건물 사이 통로. 네이버 실측 1.7m

```

전부 **차량 통행 불가 통로**다. 결측이 아니라 정보다. `non_vehicular` 플래그로

★ 무등산 4건은 네이버가 도로로 그리지도 않는다. **이 구간에 한해 우리 데이터가
  더 정밀하다.**

### 83 — 선언과 결선이 갈려 있었다

가로등 마커 하나를 추가하는 데 **6곳**을 고쳐야 했다.

```
streetlight.py · publish_web.py · pipeline.py
config.js(스펙) · app.js(fetch 배열 · MK_SRC · 굵기 특수분기 · POPUP)
index.html(토글 행)
```

`config.js` 주석은 "config.js만 고치면 재발행 없이 반영된다"고 적고 있었다.
**선언은 config 로 뺐는데 결선이 코드에 남아 그 약속이 깨져 있었다.**

이제 스펙이 `data` · `popup` · `scale` · `cover` 를 전부 든다.
`app.js` 는 `CONFIG.markers` 를 돌며 선언대로 실행만 한다.
`index.html` 의 토글 행도 `app.js` 가 생성한다.

→ **마커 추가 = `config.js` 한 곳 + 데이터 발행 한 곳**

계약 테스트 `test_marker_spec_self_contained` 가 이 구조를 지킨다.
손딕셔너리(`MK_SRC`·`POPUP`)나 마커 id 특수분기가 되살아나면 실패한다.
실제로 지혜님 PR 과 충돌을 푸는 과정에서 `spec.id === "m-cctv"` 분기를
되살렸다가 이 테스트에 걸렸다. 테마 연동은 `cover.themed` 선언으로 뺐다.

### 63 개정 사유

문언은 "수치지도 주 소스"인데 구현은 3소스 우선순위다. 그리고 결정 63 을
넣고도 **실제로는 주 소스가 무력화되고 있었다**(결정 67 참조). 문언을
구현에 맞춰야 한다.

### 65~66 — 왜 승인이 필요한가

`seg_id` 와 구간 수가 바뀐다. 1266 → 1087. 대외 자료에 1,266 을 쓴 것이
있으면 전부 갱신 대상이다.

### 70 — `ROAD_BT` 금지의 예외

§3-3 에서 `ROAD_BT` 를 폭 값으로 쓰지 않기로 했다. 70 은 그 예외다.
**폭 값으로 쓰는 것이 아니라 "잴 만한 도로인가"의 판정에만 쓴다.**
실측값이 하나라도 있으면 그쪽이 항상 우선하므로 폭 미산출 구간에만 걸린다.

# 18. 데이터 관리

## 18-1. 계층

여섯 계층이고 각 계층에 **깨면 안 되는 규칙이 하나씩** 있다.

| 계층 | 경로 | 불변 규칙 |
|---|---|---|
| `landing` | 외장 SSD `fire-lane-data/` | 다운로드 원본을 그대로 던져두는 수집소. 규칙 없음 |
| `quarantine` | `data/_quarantine/` | 대장에 없는 파일. **삭제하지 않고 격리한다** |
| `raw` | `data/raw/` | **절대 수정하지 않는다.** 읽기 전용. 인코딩조차 고치지 않는다 |
| `norm` | `data/norm/` | raw 를 형식만 정규화한 것. **값은 안 바꾼다** |
| `interim` | `data/interim/` | 중간 산출물. 언제든 지워도 재생성된다 |
| `processed` | `data/processed/` | 파이프라인 정본. 사람이 손으로 만들지 않는다 |
| `field` | `data/field/` | 실측 원자료. **사람이 만드는 유일한 데이터**. raw 와 같은 등급으로 보호 |
| `web` | `web/data/` | 표출용 경량 사본. 생성물. 직접 수정 금지 |

`norm` 이 새로 생기는 계층이다. 지금은 `normalize_raw.py` 가 raw 안에서 이름만
바꾸고 있는데, 그러면 **원본과 정규화본이 같은 폴더에 섞인다.** 원본이 훼손됐는지
아닌지 나중에 알 수 없다. 분리한다.

```
data/raw/    받은 그대로. 압축도 안 푼다면 그대로 zip
data/norm/   압축 해제 + 인코딩 통일 + 확장자 통일 + 파일명 규칙 적용
```

`field` 를 raw 등급으로 두는 이유: **실측은 다시 못 만든다.** 파이프라인은
언제든 재실행되지만 8월 20일 오전 10시의 그 골목은 다시 안 온다.

## 18-2. 파일명 규칙

## raw

원본 파일명을 그대로 둔다. 대신 **폴더**로 구분한다.

제공기관 폴더는 이 여덟이다.

```
juso     도로명주소(주소기반산업지원)     its      국가교통정보센터
ngii     국토정보플랫폼                  vworld   브이월드
safety   공공데이터포털(안전)             gjcity   공공데이터포털(광주 동구)
sbiz     공공데이터포털(소상공인)         eais     건축HUB
```

★ `ngii` 와 `vworld` 를 나눈다. 같은 수치지형도라도 **원천이 다르면 폴더가 다르다.**
  섞으면 어느 판인지 파일명만으로 구분되지 않는다. (2026-08-17)

```
data/raw/{dataset_key}/{download_date}/{원본파일명 그대로}
예: data/raw/ngii1k/2026-07-28/(B0010)수치지도_광주동구_368112.zip
```

원본 파일명을 안 바꾸는 이유: 제공기관 문의나 재다운로드 때 대조가 안 된다.
한글·괄호·공백이 있어도 그대로 둔다. 어차피 코드가 직접 열지 않는다.

## norm 이후 — 여기서 규칙을 강제한다

```
{dataset_key}_{region}_{vintage}_{crs}_v{n}.{ext}

ngii1k_gwangju-donggu_2026q2_5186_v1.gpkg
streetlight_gwangju-donggu_2025_4326_v1.csv
```

| 토큰 | 규칙 |
|---|---|
| `dataset_key` | `sources.yaml` 의 키와 **문자열까지 동일**. 다르면 대장이 무의미해진다 |
| `region` | 소문자 로마자, 하이픈. 한글·공백 금지 |
| `vintage` | 데이터 기준 시점. 다운로드 날짜가 아니다. `2026q2`, `2025`, `20260728` |
| `crs` | EPSG 숫자만. **좌표계를 파일명에 박는 이유는 이게 제일 자주 나는 사고이기 때문** |
| `v{n}` | 같은 소스를 다시 받았을 때 증가. 덮어쓰지 않는다 |

**금지**: 한글, 공백, 대문자, `final`, `최종`, `수정본`, `real_final2`.
`v{n}` 이 있는데 `final` 을 쓰면 어느 쪽이 최신인지 모른다.

## 확장자 정규화

| 원본 | → | 이유 |
|---|---|---|
| `.shp` (+dbf/shx/prj) | `.gpkg` | 4파일 세트라 하나만 빠져도 못 읽는다. 인코딩 정보도 부실 |
| `.xlsx`, `.xls` | `.csv` (UTF-8) | 수식·서식이 값처럼 읽힌다. git diff 가 안 된다 |
| `.csv` (cp949) | `.csv` (UTF-8, BOM 없음) | **인코딩은 norm 단계에서 한 번만 처리한다** |
| `.json` (좌표 포함) | `.geojson` | 도구가 공간 데이터로 인식 |
| `.tif` (미압축) | `.tif` (COG, DEFLATE) | 388타일이 통째로 메모리에 안 올라간다 |

★ **인코딩 변환은 값 변경이 아니라 형식 변경이다.** 그래서 norm 에서 허용한다.
   결측 처리, 컬럼명 변경, 좌표 변환은 **값 변경**이라 norm 에서 금지하고
   `interim` 이후로 미룬다. 이 선을 흐리면 "원본이 뭐였는지" 추적이 끊긴다.

## 18-3. 대장 — `sources.yaml` 하나

사람이 손으로 쓰는 대장은 이것 하나다.
사이드카 `.meta.json` 도, 스크립트 주석 메타데이터도 쓰지 않는다.
**손대장이 둘이 되는 순간 반드시 어긋난다.**

```yaml
version: 2

datasets:
  ngii1k:
    title: 1:1,000 수치지형도 도로경계
    provider: 국토지리정보원
    portal: https://www.ngii.go.kr/...
    license: 공공누리 제1유형
    vintage: 2026q2
    acquired: 2026-07-28
    crs_native: 5186
    kind: vector
    raw_glob: "ngii1k/2026-07-28/*.zip"
    norm: ngii1k_gwangju-donggu_2026q2_5186_v1.gpkg
    normalize: [unzip, shp2gpkg]
    # 협업용 — 이 데이터가 무엇이고 어디에 쓰이나
    what: 도엽 20장 병합. 도로경계면 폴리곤. 폭 산출 주 소스
    used_for: [width_primary]
    caveats:
      - 도엽 경계에서 폴리곤이 끊긴다. 병합 후 노딩 필요
      - 실폭도로와 정의가 다르다(경계면 vs 노면). 대조 시 주의
    refresh: 연 1회
    verified: false          # 실측 검증 여부

outputs:
  segments:
    produced_by: src/etl/segments.py
    path: data/processed/segments.geojson
    inputs: [ngii1k, ngii_road, road_rw, building, boundary_emd, cctv]
    stable_key: seg_uid
    consumers:
      - web/app.js
      - src/etl/publish_web.py
      - src/etl/sample_design.py
      - tests/test_contract.py
    what: 구간 단위 통행 판정. 1,087행
    verified: false
    known_issues:
      - 폭 실측 검증 0건. 소방서 7구간 대조는 학습셋이라 검증 아님
```

## 필드의 의무

| 필드 | 없으면 생기는 일 |
|---|---|
| `what` | 3개월 뒤 이 파일이 뭔지 아무도 모른다 |
| `used_for` / `consumers` | 소스 하나 바꿀 때 뭐가 깨지는지 모른다 |
| `caveats` | 같은 함정에 두 번 빠진다 |
| `crs_native` | 좌표계 사고. 이 프로젝트에서 이미 겪었다 |
| `verified` | 미검증 값이 검증된 값처럼 쓰인다 |
| `license` | 발표·공개 때 막힌다 |

`consumers` 가 네가 말한 **"이 데이터가 지금 어디에 쓰이고 있는가"** 다.
GIS 는 협업이라 이게 없으면 소스 하나를 못 건드린다.

## 18-3b. 계약(contract) — 사람을 언제 부르는가

대장에 **기대(expectation)를 선언**하고, 어긋날 때만 사람을 부른다.
데이터 레이크·dbt·Great Expectations 가 쓰는 방식이다.

```yaml
ngii1k:
  provider: vworld
  contract:
    crs:      5186
    layers:   [A0010000, A0020000, A0033320, A0080000, C0220000]
    fields:
      A0020000: [도로폭, 일방통행, 차로수, 도로명]
    rows_min: {A0020000: 400}      # 도엽당 하한
```

### 판정

```
계약 일치            통과. 로그만 남긴다. 사람 개입 0
컬럼 추가            통과 + 알림   "자동차전용 이 생겼다"
컬럼 소실 · 타입 변경  ★ 중단. 합의 필요
건수 ±30% 초과       ★ 중단. 합의 필요
CRS 변경            ★ 중단. 무조건
```

**소실은 막고 추가는 통과시킨다.** 추가는 파이프라인을 안 깨지만 소실은 깬다.

### 합의가 필요한 시점

```
초기화           계약을 처음 쓸 때. 1회
계약 변경        스키마가 실제로 바뀌었을 때. 드물다
계약 위반 발생    위 ★ 항목
```

**그 외 업서트는 전부 자동이다.** "매번 합의"가 아니라 "합의가 필요한 것만

## 18-4. 매니페스트 — 사람이 안 쓰고 파이프라인이 쓴다

`data/processed/_manifest.json` 은 지금 생성 시각과 bbox 만 담는다. 부족하다.

```json
{
  "run": {
    "at": "2026-08-14T21:03:11+09:00",
    "git_sha": "faf9774",
    "git_dirty": false,
    "python": "3.11.9",
    "key_pkgs": {"geopandas": "1.0.1", "shapely": "2.0.4"}
  },
  "outputs": {
    "segments.geojson": {
      "sha256": "3f9a...",
      "rows": 1087,
      "crs": 4326,
      "bbox": [126.911, 35.140, 126.941, 35.161],
      "produced_by": "src/etl/segments.py",
      "input_shas": {"ngii1k": "a11b...", "building": "77c2..."},
      "params": {"TRUCK": 3.0, "PARK": 2.0, "CCTV_RANGE": 25.0}
    }
  }
}
```

`git_dirty: true` 로 만들어진 산출물은 **재현 불가**다.
계약 테스트에서 경고를 띄운다. 커밋 안 한 채로 돌린 결과가 발표 자료가 되는 걸 막는다.

`input_shas` 가 있으면 "이 산출물이 어느 버전의 입력으로 나왔는가"가 남는다.
입력이 바뀌었는데 산출물이 안 바뀌었으면 파이프라인이 안 돈 것이다.

`params` 를 박는 이유: 임계값 3.0/7.0/25.0 을 바꾼 뒤 옛날 산출물과 비교할 때
어느 쪽이 어떤 임계로 나왔는지 알아야 한다.

> ### ★ 강제되지 않는 규약은 장식이다 (2026-08-18)

> R1~R7 은 2026-08-09 부터 여기 적혀 있었다. 그 사이 `tools/` 에 일회성
> 패처 9개가 쌓였고, 전부 이 규약 위반이었다. 문서를 갱신하는 것으로는
> 아무것도 막지 못했다 — 규약은 사람이 읽어야 작동하고, 사람은 급하면
> 안 읽는다.

**R18. 같은 설명이 여러 곳에 살면 어긋남을 검사한다**
문서 축 설명이 README · PLAN 머리 · MASTER 세 곳에 있다. 2026-08-18 에
생애주기 규칙을 도입하면서 README 와 MASTER 만 고치고 PLAN 머리의 표는 옛
3축(DECISIONS 없음)으로 남았다. **테스트 154개가 전부 통과했다** —
`test_no_fifth_doc` 은 문서 개수만 세고 각 문서가 자기 축을 옳게 적었는지는
아무도 안 봤기 때문이다. 없앨 수 없는 중복이라면 최소한 어긋남은 잡는다.

**R15~R17. 문서도 코드처럼 어긋남을 검사한다**
2026-08-18 리팩으로 `seg/` 6모듈이 생기고 `tools/` 8개가 사라졌는데 README 는
옛 구조를 적고 있었다. §7 은 이미 끝난 일을 남은 일로 적고 있었다. 문서가
낡는 것을 사람의 성실성에 맡기면 반드시 낡는다.
미결정은 `PLAN §5-7` 이 정본이고 MASTER 는 **가리키기만** 한다 — 선택지를
두 곳에 적으면 한쪽만 고치는 날이 온다.

**R13. 계보 검사는 key 가 아니라 파일 단위로 한다**
한 key 가 여러 파일을 낸다. `ngii1k` 하나가 도로경계·중심선·보도·평면교차점·
가로등 10개를 만든다. key 만 보면 그중 `ngii1k_xsec_5186.gpkg` 가 옛 실행
것으로 남아도 통과한다. 교차부 제외 형상이 바뀌면 폭 표본이 달라지고 판정이
조용히 갈린다 — 1093 사고가 한 단계 아래에서 그대로 재현되는 경로다.
`_manifest.json` 의 `outputs` 목록과 디스크를 대조한다.

**R14. 한 항목은 한 문서에만 산다**
문서 셋은 병렬 축이 아니라 한 항목의 **생애주기**다.

    PLAN(미래)  →  도래  →  MASTER(현재)  →  회고  →  DECISIONS(과거)

두 곳에 있으면 생애주기 단계가 둘인 셈이고, 한쪽만 고치는 날이 온다.
구 7·8번(ngii1k pipeline 편입 · streetlight ingest kind)이 08-17~18 에
해소됐는데 08-18 오후까지 MASTER §7 에 남은 일로 남아 있었다.
그래서 남은 일 목록은 `PLAN §1` 하나뿐이고, MASTER §7 은 "현재 산출물의
한계"만 적는다 — 근사와 미검증은 남은 일이 아니라 현재 상태다.

**R12. 방어를 넣을 때는 그 방어가 실패하는 경로도 한 번 태워본다**
2026-08-18, `segments.py` 의 계보 검사와 공간 커버리지 검사가 `sys.exit` 을
쓰면서 `import sys` 가 없었다(`import sys as _sys` 는 경로 삽입용이다).
두 방어 다 실패하면 안내 메시지 대신 `NameError` 로 죽는 상태였고, 한 번도
실패한 적이 없어서 80초짜리 실행이 내내 멀쩡히 돌았다. 계약 테스트도 golden 도
**성공 경로의 산출물**만 보므로 이런 것을 못 잡는다.
출처는 `tools/stale_guard_20260818.py` 다 — 붙이기만 하고 붙인 결과를 아무도
실행하지 않았다. R9 가 금지하는 방식의 전형적인 결과다.

**R11. 코드를 옮길 때는 산출물이 같다는 것을 증명하고 옮긴다**
`baseline.py` 는 *소스가 바뀌었을 때* 판정이 어떻게 달라졌나를 본다.
`golden.py` 는 반대로 *아무것도 달라지면 안 되는 상황*에서 쓴다.
리팩 시작 전에 `golden.py lock`, 한 덩어리 옮길 때마다 `golden.py check`.
다르면 그 자리에서 되돌린다. 쌓아두고 나중에 찾는 것이 08-17/18 에
반나절씩 태운 방식이다.

**R1. 스크립트는 입력과 출력을 상단에 선언한다**

```python
"""
segments.py — 도로 중심선 + 폭 → 구간 판정

IN   norm/ngii1k_*.gpkg · norm/building_*.gpkg · processed/cctv_5186.gpkg
OUT  processed/segments_5186.gpkg · processed/segments.geojson
PARAM TRUCK=3.0 PARK=2.0 CCTV_RANGE=25.0
"""
```

**R2. 파라미터는 전부 파일 상단 대문자 상수. 함수 안에 숫자를 쓰지 않는다**
`if w < 3.0` 이 함수 중간에 박히면 임계 변경이 누락된다.

**R3. 상수를 옮길 때는 정본을 하나만 둔다**
`config.js` 의 3.0/7.0/25.0 은 **표시용 사본**이고 정본은 `src/etl/seg/params.py` 다.
(2026-08-18 Stage 1 에서 `segments.py` 에서 꺼냈다. 값은 불변, 위치만 이동.
`test_seg_geom.py::test_params_are_not_redefined_in_segments` 가 재정의를 막는다.)
이건 이미 주석에 적혀 있다. 유지한다.

**R4. 랜덤이 들어가면 시드를 파일 상단에 고정하고 매니페스트에 기록한다**
`sample_design.py` 의 `SEED = 20260814`. 시드 없는 표본 설계는 표본 설계가 아니다.

**R5. 단계 스킵은 캐시로 하되 캐시 키에 입력 sha 를 넣는다**
`if out.exists(): return` 은 금지다. 입력이 바뀌어도 안 돈다.
`if out.exists() and manifest[out].input_shas == current_shas: return`

**R6. 실패는 조용히 넘기지 않는다**

```python
except Exception:
    ngii1k = None
    print("  ! ngii1k 없음 — 1:5,000 으로 대체")
```

지금 이 패턴이 실제로 있다. 대체가 일어났다는 사실이 **산출물에 남아야 한다.**
`width_src` 컬럼이 그 역할을 하고 있으니 그건 잘 돼 있다.
다만 매니페스트의 `warnings: []` 에도 쌓아라. 콘솔은 사라진다.

**R7. 새 파생 컬럼은 스키마 주석에 동시에 추가한다**
`segments.py` 하단 스키마 dict 가 이미 있다. 컬럼만 추가하고 주석을 안 쓰면
그 컬럼은 "누가 왜 만들었는지 모르는 컬럼"이 된다.
계약 테스트에 **컬럼 집합 == 스키마 키 집합** 검사를 넣는다.

**R8. 일회성 스크립트는 돌리고 지운다. 날짜를 파일명에 박지 않는다**
`tools/docfix_20260817.py` 류 9개가 그렇게 쌓였다. 적용 뒤에는 no-op 이고
둘은 앵커가 깨져 재실행조차 불가능했다. 돌릴 수도 없고 돌릴 필요도 없는
코드 1,000줄이 남는다. 남길 값이 있으면 **이유만** `docs/DECISIONS.md` 로
옮긴다. `tools/` 에는 날짜 없는 재실행 가능한 도구만 둔다.

**R9. 소스는 직접 고쳐서 커밋한다. 고치는 스크립트를 커밋하지 않는다**
문자열 치환 패처는 git 이 이미 하는 일의 열등한 사본이다. 진짜 코드가
어디 있는지 두 곳이 되고, 리뷰어가 diff 대신 OLD/NEW 문자열 쌍을 읽어야
한다. 앵커가 깨지면 그 기록은 실행도 안 되는 텍스트가 된다.

## 18-6. 메타데이터를 어디에 붙이나

세 후보를 전부 검토했고 결론은 형식마다 다르다.

| 형식 | 메타 부착 | 방식 |
|---|---|---|
| GeoPackage | **가능** | `gpkg_metadata` 테이블. `gdal` 이 지원 |
| GeoParquet | **가능** | 파일 헤더 key-value. 권장 |
| GeoJSON | **불가** | 표준에 자리가 없다 → 매니페스트로 |
| CSV | 불가 | → 매니페스트로 |

**결론**

```
사람이 쓰는 것        sources.yaml          하나. 손으로
기계가 쓰는 것        _manifest.json        전부. 자동으로
파일에 박히는 것      gpkg / parquet 헤더    자동으로 (매니페스트와 동일 내용)
```

파일에 박는 게 필요한 이유: **파일이 레포 밖으로 나갈 때** 매니페스트가 안 따라간다.
팀원한테 `.gpkg` 하나 보냈는데 좌표계랑 출처를 모르면 그 파일은 쓰레기다.

→ `processed` 를 GeoParquet 으로 전환할 때 이걸 같이 넣는다(PLAN §13-9).

## 18-7. 의존 그래프

`sources.yaml` 의 `inputs` / `consumers` 로 자동 생성한다. 손으로 안 그린다.

```bash
uv run python src/etl/datalog.py graph        # → docs/lineage.mmd (mermaid)
uv run python src/etl/datalog.py impact ngii1k  # ngii1k 바꾸면 깨지는 것 전부
```

`impact` 가 실무에서 제일 자주 쓴다. 소스 갱신 전에 이걸 돌린다.

## 18-8. 백업

```
1벌  작업 노트북 (git + 로컬 디스크)
2벌  외장 SSD    (raw + field + processed 전체)
검증 sha256 매니페스트 대조
```

3-2-1 은 이 규모에 오버다. **2벌 + 검증**이면 된다.
핵심은 벌수가 아니라 **검증**이다. exFAT 에서 2.5GB 를 날렸을 때 문제는
백업이 없어서가 아니라 백업이 깨진 걸 몰랐던 것이다.

```bash
uv run python src/etl/datalog.py backup /Volumes/FIRELANE   # 복사 + sha 기록
uv run python src/etl/datalog.py verify  /Volumes/FIRELANE  # 대조
```

- `raw` 와 `field` 는 **매 실측 당일** 백업한다. 다시 못 만드는 데이터다
- `processed` 는 주 1회. 재생성 가능하지만 재생성에 시간이 든다
- **월 1회 복원 훈련.** 외장에서 빈 폴더로 복원해서 파이프라인이 도는지 본다.
  복원해 본 적 없는 백업은 백업이 아니다

## 18-9. DB 확장

지금은 파일로 충분하다. 옮길 시점은 **네비 API 가 붙을 때**다.

`sources.yaml` 이 곧 DDL 이 되게 설계한다.

```sql
CREATE SCHEMA core;      -- 파이프라인 산출. 읽기 전용
CREATE SCHEMA field;     -- 실측. 사람이 쓴다
CREATE SCHEMA serving;   -- API 노출. core+field 의 뷰

CREATE TABLE core.segment (
  seg_uid      TEXT PRIMARY KEY,        -- ★ seg_id 가 아니다
  run_id       BIGINT REFERENCES core.run(run_id),
  geom         geometry(LineString, 5186),
  width_min_m  REAL, width_max_m REAL,
  width_src    TEXT, verdict TEXT,
  ...
);
CREATE TABLE core.run (                  -- 매니페스트가 그대로 테이블이 된다
  run_id BIGSERIAL PRIMARY KEY,
  git_sha TEXT, dirty BOOL, ran_at TIMESTAMPTZ, params JSONB
);
```

**세 가지 원칙**

1. **PK 는 `seg_uid` / `obs_id`.** `seg_id` 를 PK 로 쓰면 다음 실행에 전부 깨진다
2. **파이프라인 결과는 append + `run_id`.** 덮어쓰지 않는다.
   그래야 "지난달 판정과 지금 판정이 왜 다른가"에 답할 수 있다
3. **API 는 `serving` 스키마만 본다.** 프론트가 판정을 재계산하지 않는다

## 18-11. 지금 상태와 격차

| 항목 | 현재 | 목표 |
|---|---|---|

| 매니페스트 | 시각·bbox | sha·rows·git·input_shas·params |
| 의존 그래프 | 없음 | `datalog.py graph` |

## 18-12. 획득·업서트 게이트

```
landing (외장 SSD fire-lane-data/)     다운로드 원본. 손 안 댐
        ↓  acquire.py stage  — 대장 매칭
data/raw/<제공기관>/                    매칭됨. 원본 파일명 유지
data/_quarantine/                      매칭 안 됨. 삭제하지 않고 격리
        ↓  normalize_raw.py
data/norm/                             규칙 파일명 + 인코딩·확장자 통일
        ↓  inventory.py  — 계약 대조(§18-3b)
data/processed/
```

### 세 판정

```
대장에 있음 + 파일 있음   →  raw 편입
대장에 있음 + 파일 없음   →  ★ 결손 경고
대장에 없음 + 파일 있음   →  _quarantine. 사람이 대장 추가 or retired 등재
```

**두 번째가 제일 중요하다.** 2026-08-14 에 외장 백업이 중단됐는데 아무도
몰랐다. raw 7개 폴더 중 4개만 넘어간 상태로 다른 기기에서 파이프라인을
돌렸고 거기서야 발견했다. **"없는 것을 없다고 말하는 것"이 안 돼서였다.**

### 원칙 다섯

```
1. 원본 파일명을 바꾸지 않는다
   재다운로드·문의 때 대조가 안 된다. 개명은 normalize_raw.py 가 한다
2. 기존 판을 덮지 않는다
   새 판은 vintage 가 다른 별개 파일이다.
   덮으면 "언제부터 값이 달라졌는가"에 답할 수 없다
3. 받은 즉시 대장을 고친다
   provider · updated · acquired · scope · crs. 나중에 적으면 틀린다
4. 계약 대조를 통과해야 편입이다 (§18-3b)
5. 편입 후 impact 를 돌린다
   그 소스를 쓰는 산출물과 소비자가 전부 나온다. 재생성 대상이다
```

### 대장 메타 항목

URL 은 적지 않는다. **자주 깨지고, provider + scope 면 다시 찾을 수 있다.**

```yaml
provider:  국토정보플랫폼        # 어느 사이트
updated:   2026-03-07           # 데이터 갱신일 (다운로드일 아님)
acquired:  2026-08-17           # 우리가 받은 날
scope:     광주 동구 74도엽       # 공간 범위 + 건수
crs:       5186                 # ★ 선언 근거를 함께. prj/xml 명시 vs 추정
```

★ `crs` 는 **"명시"와 "추정"을 구분해서 적는다.** 포털 CSV 처럼 좌표계가
  안 적힌 것은 우리가 가정한 것이고, 그 가정이 틀리면 전부 어긋난다.

### CRS 검증 3단계

```
1. 선언 확인   .prj · .xml 을 읽는다. 있으면 그게 정답
               수치지도 xml → EPSG:5186 명시
               연속수치지도 prj → EPSG:5179 명시  ★ 둘이 다르다
2. 범위 검사   5186 은 X 190k~210k · Y 260k~300k (광주)
               5179 는 900k~1100k · 4326 은 126~127 / 35~36
               자릿수만 봐도 갈린다
3. 교차 정합   서로 다른 소스를 겹친다
               건물 폴리곤 위에 CCTV 점이 얹히는가
               좌표계를 틀리면 수백 미터 어긋나 즉시 드러난다
```

**3번이 진짜 검증이다.** 1·2번은 형식이고 3번은 물리다.
