1 · 시작 — 방향이 둘이다

이것 하나만 정확히 알면 충돌의 대부분이 안 난다.

origin/dev남들이 올린 것
→받는다
매일
feat/내작업내 브랜치
feat/내작업내 브랜치
→준다
끝났을 때만
part/gisPR 로 머지
★ Draft 여도 받는다. Draft 는 "남들이 내 것을 못 받는다" 는 뜻이지 "내가 남의 것을 못 받는다" 가 아니다. git merge origin/dev 는 내 브랜치 안에서만 일어나고 남에게 아무 영향이 없다.

⚠ 2026-08-31 에 part/gis 가 dev 를 20커밋 안 받아 충돌 10건이 났다. 하루치를 매일 받으면 git 이 대개 알아서 합친다. 안 받고 미루면 그 비용이 제곱으로 는다.

첫날 — 두 줄

git config core.hooksPath .githooks    # 커밋 시점 검사. 클론 후 1회
uv sync                                # 의존성. uv.lock 그대로 깐다
⚠ 훅을 안 걸면 커밋 시점 검사가 안 돌고 CI 에서 뒤늦게 잡힌다. 그때는 이미 히스토리에 박혀 있다.
⚠ 의존성을 더할 때는 uv add 를 쓴다. pip install 은 uv.lock 을 안 고쳐서 내 컴퓨터에선 되는데 CI 에선 안 되는 상태를 만든다.

매일

  1. 아침에 받는다 — git switch feat/내작업 && git merge origin/dev
  2. 작업은 feat/ 브랜치에서. 자유롭게 만들고 지운다
  3. 푸시하면 Draft PR 을 연다. 완성 안 됐어도 연다
  4. 끝나면 Ready for review → 머지 → 브랜치 삭제
왜 Draft 로 여나
· CI 가 돈다 — 빨간불을 하루라도 빨리 본다
· 남들이 진행 상황을 본다 — 같은 파일을 동시에 고치는 것을 미리 안다
· 실수로 머지되지 않는다

왜 하루 단위로 쪼개나
사흘짜리 하나는 매일 받아도 사흘치 diff 가 쌓인다. 하루짜리 셋이면 매일 착지한다. 하루에 못 끝낼 것 같으면 쪼갠다. 쪼갤 수 없으면 그건 설계가 안 된 것이다.

2 · 하루 흐름

아침 — 받고 시작
남들 작업을 먼저 받는다
git fetch origin
git switch part/gis
git merge origin/dev
git switch -c feat/gis-오늘작업이름
저녁 — 밀고 연다
로컬에만 있는 작업은 없는 것과 같다
git add -A
git commit -m "gis: 판정 색상 대비 조정"
git push -u origin feat/gis-오늘작업이름
# PR:  base part/gis  ←  compare feat/...
#      미완이면 Draft 로

커밋 메시지 접두사

gis:   데이터 · 파이프라인 · 판정
cv:    마스킹 · 세그멘테이션 · 호모그래피
api:   FastAPI · 스케줄러 · DB
ui:    화면 · 스타일 · 인터랙션
docs:  문서
fix:   버그
★ 게이트를 통과한 시점마다 커밋한다. 여러 작업을 한 커밋에 묶으면 나중에 "언제부터 깨졌나" 를 못 가른다. 2026-08-31 에 실제로 한 커밋 안에서 원인을 못 갈라 되짚는 데 시간을 태웠다.

⚠ 브랜치는 폴더가 아니다. part/gis 에도 src/cv/ 와 src/api/ 가 다 있다. 차이는 하나 — dev 에 아직 안 올라간 커밋이 몇 개 더 있느냐. 파트 브랜치는 "우리 파트 전용 공간" 이 아니라 dev 보다 조금 앞선 저장소 전체다.

⚠ 접두사를 섞지 마라. 통합은 part/, 임시는 feat/ 다. 둘 다 feat/ 로 두면 룰셋이 구분하지 못한다.
⚠ dev 브랜치가 있으므로 dev/무엇 은 ref 충돌로 만들 수 없다. part 라는 이름의 브랜치도 만들지 마라.

4 · 룰셋 — 게이트는 main 하나다

룰셋대상승인Code Owners필수 검사머지 방식
releaserefs/heads/main1✓shared · strictMerge
trunkrefs/heads/dev0—sharedMerge
partrefs/heads/part/**0—sharedSquash
—feat/**————
왜 승인이 0인가
① 자기 PR 은 자기가 승인할 수 없다(GitHub 사양). GIS·infra 는 1인 파트라 승인 1을 걸면 영구 차단된다.
② 5인 중 다수가 남의 파트 코드를 이해하지 못한다. 이해 못 하는 승인은 도장이다.
③ 실제로 막는 것은 승인이 아니라 contract-shared 다. 2026-08-31 하루에만 충돌 마커 · 문법 오류 · 계약 위반 · 계보 소실을 검사가 잡았고, 사람 눈으로는 3주 동안 아무도 못 봤다.

그래서 게이트를 main 하나로 모은다. 게이트가 여럿이면 우회 유인이 생기고, 우회가 습관이 되면 강제자 전체가 무력해진다.

★ 승인은 사람이 둘 이상일 때만 성립한다. 파트 인원이 늘면 feat → part 승인 1로 올린다.
⚠ Code Owners 는 승인 1과 짝이다. 승인 수가 0이면 .github/CODEOWNERS 는 효력 없는 텍스트 파일이 된다. 파일이 저장소에 있다는 것과 리뷰가 강제된다는 것은 다르다.

⚠ CODEOWNERS 의 팀은 저장소 write 권한이 있어야 한다. 없으면 GitHub 이 조용히 무시하고 그 경로는 리뷰 없이 머지된다. 검사는 팀 존재만 보고 권한은 못 본다.

⚠ 보호는 룰셋 한 벌이다. 구식 Branch protection rules 를 같이 켜지 마라. 규칙이 둘이면 끄는 사람이 무엇을 껐는지 모른다.

⚠ main 은 Merge 단독이다. squash 로 올리면 조상 관계가 끊겨 다음 흡수 때마다 충돌한다. 2026-08-27~30 에 여섯 번 같은 자리에서 넘어졌다.

5 · 막히면

상황대응
CI 빨간불실패 메시지를 끝까지 읽는다. 고치는 법이 그 안에 있다
uv.lock 충돌git checkout --theirs uv.lock && uv lock — 손으로 풀지 않는다
web/data 충돌git checkout --theirs web/data/ 후 재생성. 생성물이다
그 외 충돌아침에 git merge origin/dev 를 빼먹은 것이다
레이크가 안 붙는다드라이브 문자는 기계마다 다르다. ls 가 비어도 붙은 게 아니다 —
sudo mount -t drvfs D: /mnt/d. 자세한 것은 .env.example
main 에 잘못 머지됨GitHub Revert 버튼. force push 를 쓰지 않는다
브랜치 실수로 지움룰셋이 막는다. feat/** 이면 git reflog
★ 검사가 통과했다고 옳은 것은 아니다. 각 검사는 자기가 보는 것만 본다 — golden 은 segments.geojson 하나만 읽으므로 문법 오류·대장 파손·계보 소실 위에서도 초록불을 낸다. 초록불의 범위를 오해하지 마라. 전체는 bash tools/verify.sh 가 본다.

6 · 릴리즈 — dev → main

요일로 고정하지 않는다. 갭으로 판단한다.

git rev-list --count origin/main..origin/dev

이 값이 10~15 를 넘으면 릴리즈 PR 을 연다. 릴리즈 매니저는 김재웅(@diyon13)이다.

확인명령
main 이 dev 의 조상인가git merge-base --is-ancestor origin/main origin/dev
내 브랜치가 얼마나 뒤처졌나git rev-list --count HEAD..origin/dev
내보내도 되는가uv run python tools/ship.py
⚠ 릴리즈 후에는 dev 가 main 을 다시 흡수해야 한다. 머지 커밋이라 부모 관계가 살아야 다음 릴리즈에서 충돌하지 않는다.

7 · 한시 완화 대장

⚠ §4 표는 목표값이고 아래가 현재값이다. 둘이 같으면 이 표는 비어 있어야 한다.

★ 2026-08-31 재구축. 룰셋 셋을 지우고 release(main) · trunk(dev) · part(part/**) 로 다시 만들었다. bypass actor 도 지웠다 — 한 사람이 PR 요구를 우회할 수 있었고 그 사실이 어느 문서에도 없었다. 이제 예외가 없다.

★ 실물로 확인했다. `main` · `part/gis` 직푸시가 둘 다 remote rejected 로 막혔다. 켰다고 믿지 않고 빨간불을 눈으로 본다.
대상방침(§4)현재내린 날되돌릴 날사유
비어 있다. §4 목표값과 실물이 일치한다 — 2026-08-31 룰셋 재구축.
⚠ 한시는 적어두지 않으면 영구가 된다. 이 저장소는 같은 형태로 당했다 — contract-strict 가 --ignore 110개로 넓혀진 채 Required 로 초록불을 뜨는 물건이 됐다(DECISIONS §76).

★ 완화할 때 지킬 것 셋 — ① 이 표에 먼저 적는다 ② 되돌릴 날을 함께 적는다 ③ 승인을 낮춰도 검사는 낮추지 않는다. 승인은 사람이고 검사는 기계다.
⚠ 강제자가 없다. 룰셋은 저장소 밖이라 코드가 못 본다. 이 표는 사람이 손으로 적는다. 실물 확인은 gh api repos/:owner/:repo/rulesets 로 한다. 2026-08-31 에 이 표가 실물과 달랐다 — 문서는 승인 1이라 적었는데 룰셋에는 애초에 없었다.
★ 강제자가 생겼다 — tools/ruleset_check.py
실물 룰셋을 읽어 §4 표와 대조한다. 승인 수 · Code Owners · 머지 방식 · 필수 검사 · bypass actor 를 본다.

uv run python tools/ruleset_check.py

★ 언제 치나 — 릴리즈 직전. 어차피 그때 main 을 건드리므로 잊을 자리가 없다.

⚠ CI 에 붙이지 않는다. 룰셋 읽기에는 관리자 토큰이 필요하고, 그 토큰을 CI 시크릿에 두면 룰셋을 지킬 물건이 룰셋을 바꿀 수 있게 된다. 사람이 친다.
